# AUTOSAR 산출물 추적 지도 (Artifact Traceability Map)

AUTOSAR 프로젝트의 흩어진 산출물 사이 관계를 기계적으로 복원해 탐색 가능하게 만든다.

**이 스킬이 하는 일은 "시각화"가 아니라 "추적성 확보"다.** 화면은 결과물의 한 형태일 뿐이고, 본체는 정규화된 관계 데이터(`graph.json`)다. 이 점을 설계·설명 양쪽에서 유지한다.

## 추출하는 관계

```
정의 ARXML (BSWMD)  ──정의──▶  모듈  ◀──값── 값 ARXML (ECUC)
                                 │
                                 ├──생성──▶ 생성 소스 (*_Cfg.h, *_PBcfg.c ...)
                                 ├──구현──▶ 정적 소스 (벤더 제공)
                                 ├──포트──▶ 서비스 컴포넌트 (Swcd_*.arxml)
                                 └──의존──▶ 다른 모듈 (ECUC 참조 + #include)
```

## 4단계 파이프라인

스크립트는 `scripts/autosar_map.py` 하나다 (표준 라이브러리만, 읽기 전용, 인터넷 불필요).

```
python autosar_map.py "<과제 루트>" --stage 0|1|2|3|4|all
```

사용자가 제공하는 것은 **과제 최상위 폴더 경로 하나**다. 출력 폴더는 지정하지 않으면 과제 폴더 옆에 `<과제명>_map`으로 자동 생성된다 (`-o`로 바꿀 수 있으나 보통 불필요). 모드 A에서는 항상 복사·실행 가능한 완성된 명령을 만들어 전달한다.

| 단계 | 하는 일 | 출력 (JSON = 다음 단계 입력) | 사람이 확인하는 것 |
|---|---|---|---|
| 0 | 사전 점검 (스캔 안 함) | `stage0_env.json` + stdout | Python 3.10+, 경로·쓰기 권한, 최상위 구성 |
| 1 | 폴더 구조 분석·계층 판정 (ARXML 안 엶) | `stage1_structure.json` + `1_structure.html` | 폴더 트리, 계층 색, ETC 비율 |
| 2 | ARXML 분류·해석 | `stage2_arxml.json` + `2_arxml.html` | 정의/값/SWCD/시스템/해석 실패 |
| 3 | 모듈 조립·소스 매칭·의존 수집 | `stage3_modules.json` + `3_modules.html` + `report.txt` | 모듈 수, 미사용, 매칭 실패 |
| 4 | 의존 그래프·지도 렌더링 | `graph.json` + `map.html` | 노드-링크 지도 |

**단계 4는 파일 시스템을 읽지 않는다.** `stage3_modules.json`만으로 렌더링하므로, 화면(map.html)만 고친 새 스크립트를 받으면 `--stage 4` 재실행(수 초)으로 다시 그린다. 재스캔 불필요 — 화면 반복 개선은 이 루프로 돌린다.

각 단계는 stdout에 텍스트 요약을 찍는다. 이것이 모드 A에서 사용자가 붙여넣는 내용이다.

## 실행 모드 판정 (가장 먼저)

**모드 A — 사용자 로컬 실행** (기본. 보안상 소스를 반출할 수 없는 회사 과제):
1. `scripts/autosar_map.py`를 present_files로 전달한다.
2. 사용자가 로컬에서 실행: 먼저 `--stage 0`으로 사전 점검 후, 단계별(`--stage 1` ...)로 진행한다. 익숙해지면 `--stage all`로 한 번에 돌려도 된다: `python autosar_map.py "D:\과제경로" --stage 0`
3. 사용자가 stdout 요약(또는 report.txt)을 붙여넣으면 아래 단계별 게이트 기준으로 해석·보정한다.
4. HTML은 사용자가 브라우저로 직접 연다. 화면 수정 요청이 오면 렌더링 부분만 고친 스크립트를 다시 전달하고 `--stage 4`만 재실행하게 한다.

**모드 B — Claude 직접 실행** (Claude가 과제 폴더에 직접 접근 가능한 환경일 때 — Claude Code, Cowork, 컨테이너에 폴더 업로드/마운트된 경우):
Claude가 0~4단계를 직접 실행하고 게이트 판정·보정·해석까지 해 준다. 사용자 왕복이 필요 없다. 컨테이너 환경에서는 출력 HTML을 present_files로 전달하고, Code/Cowork 환경에서는 출력 폴더 위치를 알려준다. 단, 이 모드는 파일 내용이 Claude에 전송될 수 있으므로 반출 금지 과제에는 쓰지 않는다 — 요청 장소와 무관하게 보안 성격을 먼저 확인한다.

## 단계별 게이트 워크플로

한 단계 실행 → HTML/요약 확인 → 이상하면 보정 후 그 단계만 재실행 → 다음 단계. 첫 실행이 저품질이어도 정상이다 — **보정 상수를 고쳐 재실행하는 것까지가 이 스킬의 워크플로다** (검증된 과제 기준 3회 이내 수렴). 상수는 스크립트 상단에 모여 있다: `LAYER_RULES`, `SYSTEM_ARXML_RULES`, `DEFINITION_TAGS`, `REF_NOISE`, `GENERATED_*`.

### 단계 0 게이트 — 스캔을 시작해도 되는가
스캔 전에 대화로 수집·확인한다:
1. **과제 루트 경로** — 과제 '하나'의 루트인지. 여러 과제가 모인 상위 폴더면 결과가 뒤섞인다.
2. **출력 폴더** — 기본은 과제 폴더 옆 `<과제명>_map` 자동 생성이므로 사용자가 정할 필요 없다. 별도 요청이 있을 때만 `-o`로 지정한다 (과제 내부로 지정하면 스캔에서 자동 제외되지만 권장하지 않는다).
3. **실행 모드** — A(사용자 로컬) / B(컨테이너).
4. **벤더 스택** — 모빌진 클래식이면 검증된 규칙 그대로, 다른 스택이면 규칙 보정 라운드를 예고한다.
5. **(선택) 과제 배경** — MCU 이름, 주요 통신(CAN/LIN), 예상 규모. 이후 게이트에서 "CAN 과제인데 Can이 미사용" 같은 상식 판단의 기준이 된다.

`--stage 0` 실행 결과(Python 버전, 경로·쓰기 권한, **최상위 폴더 구성 미리보기**, 대략 파일 수)를 보고, **최상위 구성이 의도한 과제가 맞다고 사용자가 확인하면** 1단계로 넘어간다. 문제가 있으면(버전 미달, 경로 오타) 해결 후 0단계를 재실행한다.

### 단계 1 게이트 — 계층 판정이 맞는가
- **ETC(미판정) 비율 > 3%** → `LAYER_RULES`가 이 과제 폴더 구조와 안 맞는 것. ETC 목록의 공통 경로 조각을 찾아 규칙을 추가한다. 순서 주의: 위에서부터 먼저 맞는 규칙이 이기므로 구체적인 것을 앞에 둔다.
- 폴더 트리의 우세 계층 색이 상식과 다르면 (예: Static_Code가 MCAL로) 규칙 순서 문제다.

### 단계 2 게이트 — ARXML 분류가 맞는가
- **해석 실패 > 5%** → 새로운 ARXML 종류가 있다는 신호. 실패 목록의 정체를 사용자에게 묻거나 경로로 추정해, 모듈 소속이 아니면 `SYSTEM_ARXML_RULES`에, 새 정의 템플릿이면 `DEFINITION_TAGS`에 추가한다.
- 시스템 레벨로 분류된 파일이 실제로는 모듈 것이면 규칙이 과하게 넓은 것이다.

### 단계 3 게이트 — 모듈 구성이 맞는가
- **모듈 수가 상식 밖** (모빌진 클래식 통합 과제 기준 130~150개, 이보다 크게 벗어나면 의심): 의심 모듈명 목록(1글자·소문자 시작)을 보고 `REF_NOISE`에 노이즈 이름을 추가한다.
- **매칭 실패 소스 > 1%** → 벤더 고유 명명 규칙 가능성. 실패 목록에서 접두사 패턴을 찾는다. (MemMap.h, modules.h 같은 공용 헤더 몇 개는 정상.)
- 미사용 모듈 목록이 과제 성격과 맞는지 사용자에게 확인 (예: CAN 과제인데 Can이 미사용으로 나오면 오판).
- 알려진 함정 6가지와 벤더 고유 모듈 14종은 `references/mobilgene-classic.md` 참조. **규칙을 고치기 전에 반드시 이 문서와 대조한다** (예: Configuration/ECU 직속 값 ARXML은 무조건 BSW — Dem·EcuM 오분류 방지 규칙을 되돌리지 말 것).

### 단계 4 — 지도 확인·화면 개선 루프
- `map.html`: **지도는 하나의 화면**이다. 전체 모듈 노드-링크(레벨별 열 배치, MCAL이 L0)와 모든 연결선(연한 회색)이 처음부터 표시된다. 모듈 클릭 시 화면 전환 없이 그 자리에서 하이라이트 — 선택 노드와 이웃만 진하게, 연결선은 주황(사용함)/초록(사용됨), 나머지는 흐려진다. 빈 곳 클릭으로 해제.
- 파일 노드는 우측 패널에 색상 사각형 그리드(정의/값/SWCD/생성/정적)로 표시된다. 사각형 클릭 시 ARXML이면 정의·값·참조 목록, 소스면 생성/정적 구분·#include 목록이 뜬다.
- 레벨 배치는 SCC(순환 묶음) 기반 휴리스틱이다. 순환(EcuM↔BswM 등)에 속한 모듈은 같은 레벨에 놓인다. 배치가 어색하면 `compute_levels()`와 `TEMPLATE_MAP`을 함께 손본다.
- **화면 수정 요청 처리**: 렌더링 부분(`TEMPLATE_MAP` 또는 `compute_levels`)만 고친 스크립트 전달 → 사용자는 `--stage 4`만 재실행. 스캔 로직을 건드리지 않았다면 절대 전체 재실행을 시키지 않는다.

## 결과 해석 — 아키텍처 설명 (4단계 완료 후)

숫자를 읽어주는 게 아니라 구조를 설명한다:
- **통신 경로 복원**: Can → CanIf → PduR → Com/Dcm 흐름이 지도에서 세로 방향으로 보이는지, 이 과제가 쓰는 통신 스택이 무엇인지.
- **규모 순위**: 생성 파일 수 상위 모듈(보통 Rte, SchM, Com, Dcm)이 곧 설정 복잡도 순위다.
- **미사용 모듈**: 정의만 있고 값·코드가 없는 모듈은 벤더 패키지에는 있으나 이 과제가 안 쓰는 것 — 지도에서 빼고 봐야 실제 구조가 보인다.
- **특이 구조**: 매칭 실패·해석 실패에 남은 것들이 오히려 과제 고유의 커스텀 코드일 수 있다.
- **벤더 고유 모듈**: 표준 AUTOSAR에 없는 이름(CanCM, Nml, Mdw 등)은 `references/mobilgene-classic.md`의 목록과 대조해 설명한다.

## 하지 않는 것

- 파라미터 단위 추적 (파일 단위까지만)
- 산출물 내용의 적정성 판단 (그건 ASPICE 오디트 스킬 소관)
- 프로젝트 파일 수정 — 스크립트는 읽기 전용이며, 출력은 별도 폴더에만 쓴다
- 모드 A에서 소스 코드 내용을 요구하는 것 (경로·파일명·요약 수치만으로 진단한다)

## 참고 자료
