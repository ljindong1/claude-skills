# canoe-project-setup

CANoe 차종별 측정 컨피그를 **통폴더에서 뽑아내고, 저장소와 대조한다.**

2026-09-22~23 HE1i PSU 실기 작업을 근거로 만들었다. 그때 밟은 함정이 전부
`references/troubleshooting.md` 에 있다.

## 이 작업의 성격 — 복제가 아니라 추출이다

원본은 보통 **컨피그 여러 개가 CAPL / PANEL / CAN DB / CDD 를 공유하는
통폴더**다. HE1i 작업의 원본(`15.SP3i_PSU`)은 140MB 에 cfg 21개가 들어 있었고,
그중 HE1i 이름으로 존재한 것은 `.cfg` / `.stcfg` / `.run\` 셋뿐이었다.
CDD·PANEL·CAPL 은 전부 SP3i 것을 참조하고 있었다.

그래서 **새 차종을 만들 때 기존 차종 폴더를 복제하면 안 된다.** 복제되는 것이
정확히 차종에 묶인 것들(CDD·PANEL·CAPL)이고, 복제 후 이름만 바꾸면 남의 차종
자산이 이 차종 것처럼 보이게 된다. 실제로 그렇게 만들어진 CDD 는 DTC 408개가
전부 원래 차종 기준이다.

이 스킬은 **통폴더에서 해당 cfg 가 실제로 참조하는 것만 따라가 뽑아내고,
파일마다 출처를 남긴다.**

## 절대 규칙

- **원본 통폴더는 읽기만 한다.** 수정·삭제하지 않는다.
- **저장소(`psu_app`)도 읽기만 한다.** DB 를 가져다 쓸 뿐이다.
- 대상 폴더가 **이미 있고 비어 있지 않으면 중단**한다. 덮어쓰지 않는다.
- **측정(계측 시작)은 하지 않는다.** `check` 는 컨피그를 열어 구성만 읽는다.
  버스로 프레임을 내보내는 것은 사람이 판단할 일이다.
- **제어기가 다르면 = 다른 프로젝트다.** 아래 2절. 자산을 물려쓰지 않는다.
- `create` 는 `verify` 통과를 확인한 뒤에만 완료로 보고한다.

## 도구

`scripts/canoesetup.py` 가 결정적으로 처리한다. Claude 는 입력 확인과 결과
해석만 한다. **cfg 를 직접 편집하지 말고 스크립트를 쓴다.**

```
survey --pool <통폴더> --repo <psu_app>      설치·COM·컨피그 목록·저장소 DB
plan   --pool <통폴더> --cfg <이름> --repo   추출 대상과 변경 예정 (파일 무변경)
create --pool ... --cfg ... --repo ... --yes 추출 + 갱신 + 안내문 + 검증
verify --dir <폴더> --repo <psu_app> --model <차종>
check  --dir <폴더>                          CANoe COM 읽기 전용 확인
```

옵션: `--out` 대상 폴더, `--model` 차종 코드 지정, `--rename` 남의 차종 자산을
목표 차종 이름으로 정리.

### CANoe 를 띄우는 명령은 하나뿐이다

| 명령 | CANoe 를 띄우나 | 무엇으로 판단하나 |
|---|---|---|
| `survey` `plan` `create` `verify` | **아니오** | 파일만 읽는다. 순수 파이썬 |
| `check` | 예 (창은 숨김) | CANoe 에게 직접 물어본다 |

**추출·대조는 전부 CANoe 없이 된다.** 참조 무결성, DB 현행 여부, CDD 가 물려
있는지 — 전부 `.cfg` 를 파싱해서 나온다. CANoe 가 깔려 있지 않아도 돌아간다.

`check` 만 CANoe 가 필요하다. "CANoe 가 이 경로를 실제로 어떻게 해석하는가"는
파일만 봐서는 알 수 없기 때문이다. 창은 `Visible = $false` 로 숨긴다.

### cfg 를 손으로 고치지 않는 이유

`.cfg` 는 줄 단위 텍스트지만 **utf-8 로도 cp949 로도 통째로 디코드되지 않는다** —
바이너리 조각이 섞여 있다. 스크립트는 전 과정을 latin-1 왕복으로 처리해
바이트를 보존한다. 일반 편집기로 열어 저장하면 깨진다.

참조 태그도 세대가 갈린다. CANoe 11 이 만든 컨피그는 `<VFileName V7 …>`,
CANoe 19 에서 한 번 저장하면 `V9` 로 올라간다. 통폴더에는 두 세대가 섞여 있다.

**`QL` 만 보면 안 된다.** CDD 참조는 `BQL` 태그에 `base=cfg` 를 달고 들어온다.
`QL` 만 훑으면 진단 설정을 통째로 놓친다.

Claude Code CLI(사용자 PC). `survey` 로 확인한다.

```
C:\Program Files\Vector Hardware Manager  채널·보율 설정 (파일로는 못 읽는다)
```

## 전체 흐름

```
survey   →   plan   →   [사용자 확인]   →   create   →   verify   →   보고
                             │
                    차종 / 제어기 / 도너 자산 / 이름 정리 여부
```

## 1. 저장소에서 읽어내는 것

`plan --repo <psu_app>` 이 자동으로 읽는다.

| 항목 | 출처 |
|---|---|
| 차종 · 제어기 | `References\01_HSM_Framework\*.sre` 의 `rel_<차종>_<제어기>_V` |
| 현행 CAN DB | `References\DB\` **최상위** (구버전은 `unused\` 로 내려가 있다) |
| 네트워크 구성 | `Configuration\System\DBImport\BCAN.arxml` · `L1CAN.arxml` |
| 보율 | `Configuration\Ecu\Mcal\Ecud_Can.arxml` |
| 진단 주소 | `Configuration\Ecu\Ecud_CanIf.arxml` |

**`References\DB` 의 `unused\` 관례가 핵심이다.** 최상위에 무엇이 있는지가 곧
"지금 맞는 DB" 이므로, 저장소만 보면 DB 교체 판단이 끝난다.

차종 표기는 **HSM 파일명을 기준으로 삼는다** — 폴더는 `OEUK_HE1I`(대문자),
`.project` 는 `he1i`(소문자)라 서로 다르다. cvd-project-setup 과 같은 근거다.

## 2. 프로젝트 경계 — 가장 중요하다

두 경우를 반드시 구분한다. 판단 근거는 **제어기 코드**다.

| | 같은 프로젝트 · 다른 차종 | **다른 프로젝트** |
|---|---|---|
| 예 | PSU 의 HE1i / SP3i / BJ1 / NQ6a / SX3e | RWPC · WPC · MKBD … |
| 저장소 | 같다 | **다르다** |
| 진단 사양 | 부품번호 공통 (예 `95486_02`) | **다르다** |
| Local CAN DB | 공통 | **다르다** |
| CAPL / PANEL | 신호가 겹쳐 공유가 성립 | **성립 안 한다** |

**같은 프로젝트**면 자산 공유가 실제로 타당하다. 원본 통폴더가 그 전제로
만들어져 있다. `--rename` 으로 차종 이름을 정리하고 출처를 안내문에 남긴다.

**다른 프로젝트**면 남의 프로젝트 컨피그를 도너로 쓰지 않는다. 그 프로젝트의
원본 CANoe 폴더를 받아야 한다. 저장소 제어기와 통폴더 제어기가 다르면
**중단하고 그렇게 보고한다** — cvd-project-setup 이 MCU 계열이 다른 도너를
거부하는 것과 같은 규칙이다.

## 3. 사용자 확인 (1회)

`plan` 결과를 표로 보여주고 확인받는다. **확인 없이 `create` 하지 않는다.**

- 차종 · 제어기 · 대상 폴더명
- **남의 차종 자산을 쓰고 있는지**, 쓴다면 그 목록
- **`--rename` 여부** — 이름을 정리할지, 공유 사실이 보이게 그대로 둘지
- CAN DB 를 저장소 현행으로 갱신할지
- 대상 폴더가 이미 있으면 그 사실

## 4. 생성

`create … --yes`. 스크립트가 순서대로 한다.

1. cfg 본체와 형제 파일(`.stcfg` `.cfg.ini`) 복사
2. cfg 가 참조하는 **폴더 안** 파일만 따라가 복사 (`QL` + `BQL` 둘 다)
3. CAPL `.can` 의 `#include` 를 따라가 `.cin` 복사
4. 이름으로 아는 보조 파일 복사 — 환경변수 `.ini` 는 cfg 에 **파일 참조로
   안 나오고** 심볼트리 키로만 나와서, 이름 규칙으로 찾지 않으면 통째로 빠진다.
   남의 차종 것(`PSM_envvars_RG3_EV_PE.ini`)은 거른다
5. `.run\<cfg이름>\` 복사
6. `--rename` 이면 남의 차종 코드를 목표 차종으로 치환 (바이트 단위, CRLF 보존)
7. CAN DB 를 저장소 현행으로 교체
8. `읽어보세요.txt` 생성 — **파일별 출처표** 포함
9. `verify` 자동 실행

## 5. 검증

`verify` 가 보는 것.

```
폴더 안 참조가 전부 실재하나        없으면 [실패]
다른 차종 이름이 남아 있나          남았으면 [주의]
진단 기술(.cdd)을 참조하나          폴더에 있는데 참조 안 하면 [실패]
CAN DB 가 저장소 현행과 같나        다르면 [실패]
폴더 밖을 가리키는 참조             [정보] — 출처별로 묶어 보여준다
참조 태그 밖의 맨 절대경로          [정보] — CAPL 컴파일 출력 경로
컨피그가 참조하지 않는 파일          [정보]
```

하나라도 `[실패]` 면 **완료로 보고하지 않는다.**

> **`VBasicDiagnosticStreamer` 의 숫자로 진단 로드를 판단하지 말 것.**
> CDD 가 물려 있는 원본에서도 그 값은 `0` 이다. 판단 근거는 `.cdd` 참조다.

## 6. 보고

```
## CANoe 컨피그 추출 결과

| 항목 | 값 |
| 대상 | HE1i / PSU |
| 폴더 | …\CANoe_HE1i |
| 원본 | …\15.SP3i_PSU  (cfg 21개 중 HE1i_PSU_MCar_R1.cfg) |
| 세대 | CANoe 11 이 만든 컨피그 |
| 남의 차종 자산 | SP3i 10개 — CDD 1 / PANEL 4 / CAPL 5 |
| CAN DB | 2025-12 → 2026-05 (저장소 현행) |
| 검증 | 전체 통과 |

출처는 폴더의 읽어보세요.txt 참조.
```

**남의 차종 자산을 쓰고 있으면 보고에 반드시 넣는다.** 특히 CDD 는
"이 차종 진단 사양서가 아니다"를 명시한다. 진단 검증의 전제가 달라진다.

## 7. `check` — CANoe COM 읽기 전용 확인

```
python scripts\canoesetup.py check --dir <폴더>
```

`CANoe.Application` COM 으로 컨피그를 열어 **DB 목록과 시뮬레이션 노드를 읽고
닫는다.** 측정을 시작하지 않으므로 **버스로 아무것도 내보내지 않는다.**

로그는 단계마다 덧붙여 쓰므로 실패해도 어디까지 갔는지 남는다.

| 로그 마지막 | 뜻 |
|---|---|
| 로그 없음 | PowerShell 이 스크립트를 실행하지 못했다 |
| `STEP=start` | COM 객체를 못 만들었다 — 설치 / 라이선스 |
| `STEP=com_ok` | 컨피그를 못 열었다 — 경로 / 다른 CANoe 인스턴스 |
| `STEP=opened` | DB 목록을 못 읽었다 |
| `STEP=done` | 전부 통과 |

산출물은 `<폴더>\_autorun\` 에 남는다 (`check.ps1`, `check_log.txt`).

**창은 뜨지 않는다.** `$app.Visible = $false` 로 숨긴 채 돌린다. 사람이 쓰던
화면을 가리지 않는다. 실패해도 `finally` 에서 `Quit` 하므로 유령 프로세스가
남지 않는다.

다만 **CANoe 프로세스 자체는 뜬다.** 파일만 보는 `verify` 와 달리, 이 명령은
CANoe 에게 직접 물어보는 것이라 프로그램이 실행돼야 한다. CANoe 를 이미 열어
두고 작업 중이면 그 인스턴스와 충돌할 수 있으니 닫고 돌린다.

세대가 낮은 컨피그(CANoe 11)를 CANoe 19 로 열면 변환 확인 대화상자가 떠서
무인 실행이 멈출 수 있다. 창을 숨겨 두면 그 대화상자가 안 보인 채 시간초과로
끝나므로, 그때는 사람이 한 번 열어 저장한 뒤 다시 돌린다.

### 측정까지는 자동화하지 않는다

측정을 시작하면 시뮬레이션 노드가 **버스로 송신한다.** 실차나 실보드에 붙은
상태에서 그것을 스킬이 임의로 하지 않는다. 사람이 CANoe 에서 시작한다.

## 8. 조작·문제 해결 질문을 받으면

파일을 만들지 말고 참고 문서를 읽고 답한다.

- `references/usage.md` — 컨피그 열기, DB 교체, 채널 배정, 진단(CDD) 물리기,
  측정 시작 전 확인, 빌드가 새로 나왔을 때
- `references/troubleshooting.md` — **데이터가 안 나올 때 CAN FD 부터 본다**,
  에러 프레임 폭주, 참조 깨짐, CDD 가 사라지는 경우, 세대 변환,
  남의 프로젝트 경로 잔재

### 데이터가 안 나온다는 문의를 받으면

**첫 번째 의심 대상은 채널이 CAN FD 가 아니라 Classic CAN 으로 설정된 것이다.**

이 설정은 `.cfg` 안에 없다. Vector Hardware Manager 에 있고 저장 형식이
바이너리(`Startup.Profile`)라 **파일로는 확인도 수정도 못 한다.** 그래서
컨피그는 완벽한데 수신이 0 인 상태가 된다. HE1i 작업에서 가장 오래 잡아먹은
것이 이것이다.

그다음 순서: 전원·IGN → 디버거로 CPU 를 세워 둔 것은 아닌지 → 종단저항 →
채널 배정.

## 범위 밖

- **측정 수행·판정** — 시작은 사람이 한다
- CVD / T32 보드 라이팅 — `cvd-project-setup` 담당
- CAPL 코드 작성·수정, PANEL 설계
- CDD 작성·수정 — CANdelaStudio 영역이다. 이 스킬은 물려 있나만 본다
- 원본 통폴더의 수정·정리
- Vector Hardware Manager 설정 변경 — 바이너리라 읽지도 쓰지도 않는다
