# python-can 모드

CANoe 없이 Vector 장비에 파이썬으로 직접 붙는다. 레스트버스로 DUT 주변 ECU
인 척 주기 송신해 DUT 를 깨우고, DUT 가 보내는 프레임을 DBC 와 대조한다.

## 실행 환경

```
파이썬     D:\Ljindong\python-tutorial\.venv\Scripts\python.exe
           (Python 3.12 — tomllib 필요 / python-can 4.6.1 / cantools)
프로젝트   스킬을 부른 폴더 (예: D:\Mobase\psu_master) — 기본정보를 여기서 읽는다
작업폴더   <스킬>\scripts\pycan      can_bench·CanDbc 는 반드시 여기서 실행한다
설정       <스킬>\projects\<이름>.toml
기록       <스킬>\projects\trace\     --trace 로 준다. git 에 올리지 않는다
장비       Vector XL Driver Library (vxlapi64.dll) — Vector Driver Setup
```

**폴더가 둘이다.** 프로젝트 정보는 스킬을 부른 폴더에서 읽고, 벤치 스크립트는
`scripts\pycan` 에서 돌린다. 벤치 스크립트끼리 `from CanModule import …` 로
불러오는 플랫 모듈이라 그 폴더에서 실행해야 하기 때문이다. 그래서 **작업폴더로
옮기기 전에 프로젝트 폴더를 기억해 둔다.**

```powershell
$proj  = (Get-Location).Path                                   # 스킬을 부른 폴더
$skill = "$env:USERPROFILE\.claude\skills\can-bench-setup"
$py    = "D:\Ljindong\python-tutorial\.venv\Scripts\python.exe"
& $py "$skill\scripts\project_info.py" $proj --json            # ① 프로젝트 정보
Set-Location "$skill\scripts\pycan"
& $py can_bench.py ..\..\projects\psu_drv.toml                 # ⑤ 이후
```

serial 방식(`app_name` 없음)이라 Vector Hardware Manager 에 채널을 배정할
필요가 없다.

## 순서

```
① 조용히 확인 ─ ② 시작 질문 ─ ③ 설정 반영 ─ ④ DB 점검 ─ ⑤ 계획 ─ ⑥ 실행 ─ ⑦ 보고
 연결 안 함       한 번에 묻기                  장비 없이    연결 안 함  고른 만큼
```

**묻는 것은 ②에서 한 번에 끝낸다.** 그 뒤로는 답한 대로 끝까지 가고, 중간에
다시 묻지 않는다. 멈추는 것은 오류가 나거나 ②의 답과 다른 상황을 만났을 때뿐이다
(예: 고른 설정의 채널을 가진 장비가 없다).

### ① 조용히 확인 — 연결하지 않는다, 묻지 않는다

②의 선택지를 만들 재료를 모은다. 결과는 ②의 질문 설명에 녹이고, 따로
보고하지 않는다. 문제가 있을 때만 알린다.

1. **프로젝트 정보 — 지금 폴더에서 읽는다.** 스킬은 보통 프로젝트 폴더
   (예: `D:\Mobase\psu_master`)에서 실행한다.
   ```
   & $py "$skill\scripts\project_info.py" $proj --json
   ```
   폴더는 저장소 루트여도, 앱 폴더(`psu_app`)여도, 그 하위 폴더여도 된다.
   읽는 것:

   | 항목 | 출처 |
   |---|---|
   | 차종 · 제어기 | `References\01_HSM_Framework\*.sre` 의 `rel_<차종>_<제어기>_V` |
   | 빌드 변형 | `PJ_Define.h` 의 켜진 `#define OEUK_*` |
   | 브랜치 | git |
   | **빌드에 들어간 DB** | `Configuration\System\DBImport\<망>_version.h` 의 `Path` |
   | 최신 DB | `References\DB` 최상위, 같은 버스면 날짜가 가장 늦은 것 |
   | 보율 · 샘플포인트 · BRS | `Ecud_Can.arxml` 컨트롤러별. SP = (1+Prop+Seg1)/(1+Prop+Seg1+Seg2) |
   | 시험 대상 노드 | `Ecud_CanNm.arxml` 의 `CanNmNodeId` → DB 에서 그 번호의 NM 메시지를 보내는 노드 |

   종료 코드 2(앱 폴더 없음)면 프로젝트 폴더에서 부른 게 아니다. ②에서
   프로젝트 폴더를 묻거나, 설정 파일만으로 진행한다.
2. 원본이 앞서 있는지 — `SOURCE.txt` 의 방법.
3. 파이썬 환경
   ```
   & $py -c "import sys, can, cantools; print(sys.version.split()[0], can.__version__, cantools.__version__)"
   ```
4. 장비 목록 — 연결·송신하지 않고 목록만 본다 (작업폴더 `scripts\pycan`)
   ```
   & $py -c "from CanModule import CanBase; print(CanBase.detect(['vector']))"
   ```
5. 설정 목록 — `projects\*.toml`. 각 설정의 `name`, `dut.node`, 버스별 `channel`·`dbc`.
6. **프로젝트와 설정 맞대기** — 1의 결과와 5의 각 설정을 비교한다.

   | 비교 | 같은 것으로 보는 조건 |
   |---|---|
   | 대상 | `dut.node` == 1의 시험 대상 노드 |
   | DB | 버스별 `dbc` 파일 이름 == 1의 빌드 DB |
   | 보율 | `bitrate` `data_bitrate` `sample_point` `data_sample_point` == 1의 값 |

   대상이 같은 설정이 **이 프로젝트의 설정**이다. DB·보율이 다르면 ②에서
   그 차이를 보여 준다. 대상이 같은 설정이 없으면 ②에서 "프로젝트 정보로 새
   설정 만들기" 를 추천으로 올린다.

### ② 시작 질문 — AskUserQuestion 한 번

①에서 모은 실제 값으로 선택지를 만든다. 질문은 최대 4개. 이미 답이 정해진
것은 묻지 않는다 — 사용자가 호출할 때 말했거나(예: "받기만 해 줘"), 선택지가
하나뿐인 경우다. 그때는 질문 대신 "○○ 로 한다"고 한 줄 적는다.

질문 앞에 ①의 프로젝트 정보를 두세 줄로 먼저 적는다 (차종·제어기·브랜치,
시험 대상, 빌드 DB). 사용자가 **다른 프로젝트 폴더에서 부른 것**을 여기서
알아챌 수 있게 한다.

| # | 질문 | 선택지 (①의 값으로 채운다) |
|---|---|---|
| 1 | 어느 설정으로 할까요? | 이 프로젝트의 설정 (추천) / 다른 `.toml` / 프로젝트 정보로 새 설정 만들기 |
| 2 | DB 는 무엇을 쓸까요? | **빌드에 들어간 DB** (추천) / 저장소 최신 DB / 설정에 적힌 DB / 다른 판 직접 지정 |
| 3 | 어디까지 할까요? | 계획까지 (연결 안 함) / 받기만 (송신 없음) / 받기 + 깨워서 판정 (**송신함**) |
| 4 | 실험대에 실물 ECU 가 같이 붙어 있나요? | 없다 — 전부 흉내 / 있다 — 이름을 알려 준다 (`exclude` 에 넣는다) |

- 질문 1 — 프로젝트 폴더가 아니면 첫 선택지를 `projects\` 의 설정들로 바꾸고,
  "프로젝트 폴더 경로를 알려 준다" 를 넣는다.
- 질문 2 — **추천은 빌드에 들어간 DB** 다. 보드에 올라간 소프트웨어가 그 DB 로
  만들어졌으니 판정 기준도 그것이어야 한다. 셋(빌드·최신·설정)이 같으면 이
  질문은 빼고 "DB 는 빌드 DB = 최신 = 설정 (2026-05) 로 한다" 고 적는다. 다르면
  설명에 버스별로 어느 것이 다른지 적는다. 빌드 DB 가 최신과 다르면 "새 DB 가
  들어왔지만 아직 빌드에 반영되지 않았다" 는 뜻이다.
- 질문 3 의 기본 추천은 **받기 + 깨워서 판정**이다. 제어기는 보통 자고 있어서
  받기만으로는 "수신 없음"만 나온다. 설명에 송신할 ECU 수를 적는다.
- 질문 4 는 질문 3 에서 송신이 들어갈 때만 의미가 있다. 같이 묻되, 3 에서
  송신 없는 쪽을 고르면 무시한다. 설정에 이미 `exclude` 가 있으면 그 목록을
  설명에 적는다.
- **질문 3 에서 송신을 고른 것이 이번 실행의 송신 허락이다.** ⑥ 직전에 다시
  묻지 않는다. 다음 실행에는 다시 묻는다.
- 수신 시간(기본 10초)은 묻지 않는다. 사용자가 말하면 `--seconds` 로 준다.
- 설정의 보율이 프로젝트와 다르면 질문하지 않고 **프로젝트 값으로 이번만**
  바꾼다(③의 임시 복사본). 보고에 적는다. 보율이 틀리면 에러 프레임으로 버스를
  망가뜨리므로 틀린 쪽을 고를 이유가 없다.

### ③ 설정 반영

②의 답을 설정에 반영한다.

| 답 | 하는 일 |
|---|---|
| DB 설정 그대로 · exclude 변경 없음 | 설정 파일을 그대로 쓴다 |
| exclude 를 넣음, 보율을 프로젝트 값으로 맞춤 | 설정을 `projects\trace\_run_<이름>.toml` 로 복사해 그 복사본만 고친다. 원래 설정은 안 건드린다 |
| DB 가 설정과 다른 것을 고름 (빌드 DB·최신 DB) | 이번만 바꾼다 — 위와 같이 임시 복사본. 설정 파일에 저장할지는 보고 끝에 한 줄로 제안한다 |
| 다른 판 직접 지정 | 경로를 받아 파일이 있는지 보고, 위 "이번만" 과 같이 처리한다 |

`projects\trace\` 는 git 에서 빠져 있어서 임시 복사본이 저장소에 안 남는다.
DB 경로는 늘 **절대 경로**로 쓴다. 상대 경로는 설정 파일이 있는 폴더 기준이라
임시 복사본에서 틀어진다.

**새 차종 만들기**를 골랐으면 아래 "새 차종 설정 만들기" 를 먼저 하고 돌아온다.

### ④ DB 점검 — 장비 없이

```
& $py CanDbc.py <dbc> <dut.node>
```

버스마다 한 번. 종료 코드 0 결함 없음 / 1 결함 있음 / 2 오류.
결함이 있어도 벤치는 진행한다 — DB 담당에게 넘길 목록이다. 넘길 파일이
필요하면 `--all --out ..\..\projects\trace\DB_<버스>_<노드>.txt`.

### ⑤ 계획 — 연결하지 않는다

```
& $py can_bench.py <설정>
```

버스별 채널·보율·DB·판정 대상 메시지 수·레스트버스가 흉내 낼 ECU 와 메시지
수·초기값 대신 보낼 신호가 나온다. 요약만 보여 주고 이어서 ⑥으로 간다.
②에서 "계획까지" 를 골랐으면 여기서 ⑦로 간다.

### ⑥ 실행 — ②에서 고른 만큼

```
받기만                  & $py can_bench.py <설정> --listen --trace ..\..\projects\trace
받기 + 깨워서 판정      & $py can_bench.py <설정> --run    --trace ..\..\projects\trace
```

`--run` 은 받기만을 먼저 하지 않고 바로 간다. 레스트버스가 제어기를 깨운 뒤
첫 프레임부터 판정 시간을 잰다.

### 새 차종 설정 만들기

②에서 "프로젝트 정보로 새 설정 만들기" 를 골랐을 때만 한다.
`assets\bench_template.toml` 에 ①의 프로젝트 정보를 채워 초안을 만든다.

| 항목 | 채우는 곳 | 모르면 |
|---|---|---|
| `name` | `<차종>_<제어기>` 에 시험 대상 노드의 위치(DRV/AST…)를 붙임. 예 `HE1i_PSU_DRV` | — |
| `dut.node` | ①의 시험 대상 노드 | 여럿이면 선택지로 묻는다 |
| `[[bus]] name` | 망 종류 — B2 → `B-CAN`, Local → `Local` | — |
| `bus.dbc` | ①의 빌드 DB **절대 경로** | 빌드 DB 가 `References\DB` 에 없으면 최신을 쓰고 알린다 |
| `fd` `bitrate` `data_bitrate` `sample_point` `data_sample_point` | ①의 컨트롤러 값 | — |
| `bus.channel` | 실제 결선 | **반드시 묻는다** (①의 장비 채널을 선택지로) |
| `bus.signals` (IGN 등) | 같은 프로젝트 기존 설정, 기존 CANoe 패널·CAPL | 비워 두고 묻는다 |
| `exclude` | 실험대에 실물로 붙어 있는 ECU | ②의 질문 4 |
| `dut.e2e` | 같은 프로젝트 기존 설정 | `""` 로 두고 알린다 |

- 모르는 것(채널·IGN 신호)은 **한 번에 모아서** 묻는다 (AskUserQuestion, 최대 4개).
- 초안의 각 값 옆 주석에 **근거(파일·날짜)** 를 적는다.
- 같은 프로젝트(같은 제어기)의 기존 `.toml` 은 틀로 써도 된다. 다른 프로젝트
  것은 쓰지 않는다.
- 저장 전 초안을 표로 보여 주고 확인받는다. 이것이 새 차종의 유일한 두 번째 확인이다.

설정 항목은 `can_bench.py` 의 `SETTINGS_KEYS` 에 있는 것만 쓴다. 모르는 이름은
오타로 보고 `can_bench` 가 멈춘다 (조용히 기본값으로 돌면 실물 ECU 와 같은 ID 를
보낼 수 있어서 일부러 그렇게 만들어졌다).

### ⑦ 보고

종료 코드 `0` 통과 / `1` 실패 / `2` 설정·연결 오류 또는 중단.

```
## CAN 벤치 결과

| 항목 | 값 |
| 설정 | projects\psu_drv.toml |
| 대상 | GW_PSU_DRV_FD |
| 장비 | VN1640A serial 78463 |
| 방식 | --run, 10초 (앞 2초 제외) |
| 프로젝트 | HE1i / PSU, 브랜치, 앱 폴더 |
| DB | 빌드 DB / 최신 / 설정 — ②의 답, 설정과 달랐으면 그 사실 |
| B-CAN | 실패 7 / 주의 0 / 정보 5 / 통과 3 |
| Local | … |
| 기록 | projects\trace\PSU_DRV_<시각>.txt, *.blf |
```

그 아래에 **실패·주의 줄만** 메시지 이름과 이유 그대로 옮기고, 이유별로 무엇을
볼지 한 줄씩 붙인다.

| 이유 | 뜻 / 볼 것 |
|---|---|
| 수신 없음 (주기 메시지) | DUT 가 안 보낸다. 깨우기 조건(IGN 신호·NM·PN), 해당 기능 활성 조건 |
| 수신 없음 (이벤트·NM) — 정보 | 조건이 없으면 안 오는 게 정상일 수 있다 |
| 평균 주기 벗어남 | DUT 송신 주기 설정 또는 DB 주기 |
| 간격 1.5배 초과 — 주의 | 프레임이 빠졌다. DUT 가 안 보냈는지 이쪽이 놓쳤는지는 구분 못 한다 |
| 길이 / 형식(FD·Classic) | DB 와 DUT 설정 불일치 |
| 카운터 멈춤·건너뜀 | DUT E2E 카운터 |
| CRC 틀림 | E2E 방식이 HkmcE2E 와 같은지부터 의심 (미확인 사항) |
| CRC 확인 안 함 — 정보 | 그 메시지는 CRC 를 보지 않았다. 통과가 CRC 까지 맞았다는 뜻이 아니다 |

판정 줄의 시각(첫 프레임부터 잰 초)으로 `.blf` 에서 그 자리를 찾을 수 있다.

## 하지 않는 것

- 판정 로직·허용오차 기본값 변경 — 원본 스크립트 쪽 일이다. 설정의 `cycle_tol`
  은 사용자가 정하면 바꾼다.
- ②에서 송신을 고르지 않았는데 `--run` 하는 것.
- `projects\trace\` 를 git 에 넣는 것.
