# Tech Research to Confluence

기술 자료 Confluence 가이드의 **"무엇을 담을까"** 를 담당하는 파이프라인 상위 스킬.

```
[본 스킬 담당]                              [confluence-writing 위임]
① 소스 판별 → ② 깊이 확인 → ③ 조사 → ④ 목차+범위 승인 → ⑤ 작성 → ⑥ 발행
```

**⑤⑥은 본 스킬이 다루지 않는다.** 승인 완료 후 작성 단계에 진입하면 반드시 `/mnt/skills/user/confluence-writing/SKILL.md`를 읽고 그 규약(인스턴스 선택, 톤, 구조, 서식, MCP 발행/수정, 세션 관리)을 정본으로 따른다. 규칙이 겹쳐 보이면 항상 confluence-writing이 우선.

---

## 1. 요청 유형 판별

| 유형 | 예시 | 본 스킬 적용 |
| --- | --- | --- |
| 조사형 신규 가이드 | "ISO 26262 조사해서 정리해 등록해줘" | ⭕ 전체 파이프라인 |
| 정리형 신규 가이드 | "이 파일/대화 내용 정리해서 올려줘" | ⭕ 조사만 생략 (②③ 스킵, ④부터) |
| 혼합형 | "이 자료 기반 + 최신 동향 보강" | ⭕ 보강 범위만 부분 조사 |
| 기존 가이드 확장/보강 | "기존 ○○ 가이드에 보강해줘" | ⭕ 기존 트리 조회 후 신규/수정 분류를 승인안으로 제시 |
| 단일 페이지 작성, 단순 수정 | "페이지 하나 만들어줘", "표 고쳐줘" | ❌ confluence-writing 단독 |

## 2. 🚫 기획 단계 절대 규칙

1. **목차+범위 승인 없이 본문 페이지를 생성하지 않는다.** 목차 초안 + 각 하위 페이지가 다룰 범위(1~2줄)를 제시하고 명시적 승인 후 작성 시작 (`references/content-planning.md` §4 형식).
2. **조사형은 깊이 프로파일을 먼저 확인한다** (개념/실무/심층 — 매번 확인이 기본, 같은 시리즈 내에서는 재사용).
3. **조사 자료는 문단 단위로 옮겨 적지 않는다.** 재구성·재서술, 출처는 주요한 것만.
4. **기존 가이드 확장 시 기존 트리를 먼저 조회한다** — 조회 없이 작성하면 중복 페이지 생성 위험.
5. **발행·수정의 안전 규칙(허락, fetch, html 왕복 등)은 confluence-writing의 절대 규칙을 따른다** — 본 스킬은 이를 재정의하지 않는다.

## 3. 참조 로드맵

| 파일 | 언제 읽나 |
| --- | --- |
| `references/content-planning.md` | 요청 접수 직후 — 소스 판별 상세, 깊이 프로파일(ISO 26262 예시), 조사 규약, 승인 게이트 형식, 목차 설계 원칙 |
| `/mnt/skills/user/confluence-writing/SKILL.md` | ④ 승인 완료 직후, 작성 시작 전 — 작성·발행 규약 전체 (필수) |

## 4. 핵심 메시지 (한 문장)

> **깊이를 먼저 묻고, 목차와 각 페이지의 범위를 승인받은 뒤에야 쓴다 — 어떻게 쓰고 올릴지는 confluence-writing이 정본이다.**
