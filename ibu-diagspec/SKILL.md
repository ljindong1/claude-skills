# IBU 진단사양서 (BCM·SMK) — 뷰어 생성·새 차종 추가·통합 뷰어

진단 담당자가 **정본 워크북 하나**를 고치거나 새 차종을 넣고, 그 결과를 뷰어(HTML)·엑셀 양식으로 받아 보는 일을 돕는다.
계산은 모두 이 스킬의 `scripts/` 안 specforge 코드가 한다 — 표를 직접 읽어 O/X를 추측하거나 엑셀을 손으로 고치지 말 것.
정본은 담당자가 계속 쓰는 원본이라, 손으로 고친 흔적이나 형식 깨짐이 생기면 다음 빌드·저장소 반영이 틀어진다.

## 무엇이 들어 있나

- `scripts/specforge/` — 정본 읽기, 규칙 계산, 뷰어·엑셀 생성 코드 (SW플랫폼LAB specforge 저장소와 같은 코드)
- `scripts/refdata.json` — 블록도(IBU R52)·기능사양표(CN7)에서 미리 뽑은 참조 데이터. 블록도 PDF가 없어도 규칙 계산이 된다.
  어느 차종이 들어 있는지는 `info`의 `blockdiag_vehicles`(차종 → SMK/IMMO 형별 쪽)·`funcspec_vehicles`로 확인한다.
  블록도는 18개 차종, 기능사양표는 CN7 PE 3종뿐이라 그 밖의 차종은 첨부 문서가 없으면 해당 근거 항목을 규칙으로 판단하지 못한다
- `scripts/data/projects.yaml` — 문서마다 다른 차종 표기를 묶는 별칭표
- `scripts/viewer/template.html` — 뷰어 템플릿
- 모듈: **BCM(R391)·SMK(R188) 정본이 있다.** 모듈 폴더에 정본이 없으면 SW플랫폼LAB에서 받아 두라고 안내한다.
  SMK는 판단 기준이 '검토 방법' 열(기본 적용·미적용·블록도·기능사양표)이고, '블록도'만 적힌 항목은 항목 이름(Description·Actuator Name)의 신호로 판단한다.
  SMK의 'Diag Tool Display'는 표출 여부라 BCM H열 같은 품번 조건으로 쓰지 않는다.

## 저장 폴더 — 모듈 폴더(BCM·SMK) 아래 날짜 폴더

담당자가 고른 **저장 루트** 아래에 모듈마다 폴더를 둔다. 정본은 모듈 폴더 바로 아래, 결과는 그 아래 날짜 폴더에 남긴다.
BCM 작업은 BCM 폴더만, SMK 작업은 SMK 폴더만 건드린다. 날짜 폴더에 정본 사본을 함께 두는 것은 "이 뷰어·엑셀이 어느 정본으로
만든 것인지"를 날짜 폴더만 보고 알 수 있게 하려는 것이다.

```
<저장 루트>/                                     (예: E:\모베이스\DiagSpec_manage)
├── BCM/
│   ├── diagspec_IBU_BCM_Master.xlsx              ← BCM 정본 (담당자가 고치는 파일)
│   └── 20261104/                                 ← 실행한 날 (같은 날 다시 돌리면 덮어씀)
│       ├── diagspec_IBU_BCM_Master_20261104.xlsx ← 이번에 쓴 정본 사본
│       ├── ibu_bcm_diagspec_viewer_20261104.html ← 뷰어 (배포용)
│       └── 진단사양서_BCM_원본양식_20261104.xlsx  ← 기존 통합 진단사양서와 같은 배치의 엑셀
│           (새 차종을 추가한 날은 + 신규차종_BCM_<코드>_추가보고_…html, 신규차종_BCM_<코드>_확인목록_…xlsx)
├── SMK/  (같은 구조 — diagspec_IBU_SMK_Master.xlsx)
└── 통합/
    └── 20261104/
        ├── ibu_diagspec_통합뷰어_20261104.html   ← "합쳐 줘" 때만 (작업 4)
        └── 통합뷰어_구성_20261104.txt
```
불일치 목록·요약은 파일로 남기지 않는다 — 실행 결과 JSON에 나오니 대화로 알려 준다.

### 모듈 고르기 (모든 작업의 첫 단계)

담당자의 말에 BCM/SMK가 드러나 있지 않으면 먼저 하나만 묻는다: **"BCM / SMK 중 어느 모듈 작업인가요?"**
(선택 질문 도구가 있으면 그것으로). 고른 모듈의 폴더(`<저장 루트>/<모듈>/`)와 그 안의 정본만 쓴다.
"합쳐 줘"는 모듈을 묻지 않는다 (작업 4).

### 폴더 정하기

1. 담당자가 저장 루트를 말하지 않았으면 물어본다. 앱에 그 폴더가 연결돼 있어야 저장할 수 있으니, 연결이 안 돼 있으면
   앱의 '+' 메뉴 → '폴더 추가'로 연결해 달라고 한다. 한 번 정한 루트는 다음에도 같은 곳을 쓰는지만 확인한다.
2. `<저장 루트>/<모듈>/` 바로 아래에서 정본(`diagspec_*_<모듈>_Master.xlsx`, 시트 `차종별값`·`진단항목` 등이 있는 xlsx)을 찾는다.
   - 모듈 폴더가 없으면 만들어도 되는지 묻고 만든다. 정본이 없고 대화에 첨부돼 있으면 그 파일을 정본으로 둘지 물어본 뒤 복사한다.
   - 예전 통합 진단사양서 `.xls`만 있으면 이 스킬은 정본만 다룬다고 알리고 SW플랫폼LAB에 문의하도록 안내한다.
3. 실행 위치에 따라 경로를 쓴다.
   - 셸에서 폴더가 보이면(예: `~/mnt/<폴더 이름>`) `--master <루트>/<모듈>/<정본>.xlsx --out <루트>/<모듈>` 로 바로 실행한다.
   - 셸이 클라우드 작업공간이라 폴더가 안 보이면, 정본을 작업공간으로 가져와 `--out` 을 작업공간 폴더로 실행한 뒤,
     만들어진 날짜 폴더의 파일을 `<루트>/<모듈>/<YYYYMMDD>/`로 써 넣는다 (같은 이름은 덮어쓴다).
   - Excel에서 열려 있는 파일은 쓰거나 옮길 수 없다. 실패하면 그 파일을 닫아 달라고 하고 다시 한다.
   - 폴더를 끝내 쓸 수 없으면 결과 파일을 대화로 보내고, 어디에 두면 되는지(위 구조) 알려 준다.
4. 결과는 저장 폴더(또는 파일)로만 전달한다. 사내 진단사양 데이터라 공유 링크가 생기는 아티팩트로 발행하지 않는다.

### 실행 준비

- 의존 패키지: `openpyxl`, `pyyaml`. 블록도 PDF를 받았을 때만 `pymupdf`가 더 필요하다.
  ```bash
  python -c "import openpyxl, yaml" || pip install openpyxl pyyaml --break-system-packages
  pip install "pymupdf>=1.26,<2" --break-system-packages   # 블록도 PDF가 있을 때만
  ```
- 실행 위치는 이 스킬의 `scripts/` 폴더이고, 스킬 폴더에 캐시 파일이 생기지 않도록 `PYTHONDONTWRITEBYTECODE=1`을 붙인다.
- 실행 결과 JSON의 `files`에 저장된 파일 경로가 나온다. 담당자에게는 날짜 폴더 경로와 파일 세 개를 알려 준다.

## 작업 1 — 정본을 고쳤으니 뷰어·엑셀 만들기

```bash
cd <스킬>/scripts
PYTHONDONTWRITEBYTECODE=1 python -m specforge.desk build --master "<루트>/<모듈>/<정본>.xlsx" --out "<루트>/<모듈>"
```
새 블록도·기능사양표를 함께 받았으면 `--blockdiag <pdf>` / `--funcspec <xlsx>`를 붙인다 (같은 차종이면 첨부본이 우선).

실행 결과 숫자로 짧게 알려 준다:
- **불일치**(mismatch): 정본 O/X와 블록도·기능사양표 규칙 결과가 다른 칸 — 담당자가 확인할 후보. `mismatch_list`를 표로 보여 준다
- **조건부**: 지역·품번처럼 문서로 판단할 수 없는 조건이 남아 O/X 어느 쪽도 틀렸다고 할 수 없는 칸
- **예외 확인**: 규칙과 다르지만 적용예외에 사유가 적힌 칸 (담당자가 이미 확인함)
- 평가 불가(not_evaluable)는 판단 기준이 없거나 그 차종의 블록도·기능사양표가 없는 칸이라 대부분이다 — 숫자만 짧게 언급하면 된다.
  기록값 비표준(recorded_other)은 O/X 자리에 다른 글자(예: "0.0")가 든 칸이라, 있으면 `recorded_other_list`의 항목·차종을 짚어 고치도록 알린다.
- 불일치 목록 끝의 근거 코드 읽는 법: `signals:1` 블록도에 신호 있음(0 없음, 여러 신호면 신호마다 1/0),
  `signals[SMK]`·`signals[IMMO]` 그 형의 블록도 쪽에서 찾음, `features:True/False` 기능사양표 적용/미적용,
  `no_funcspec`·`no_IMMO` 그 자료가 없음. 담당자에게는 "블록도에 ○○ 신호 있음"처럼 풀어서 말한다.
- 같은 날 다시 만들었으면 날짜 폴더의 파일을 새로 덮어썼다고 말하고, 결과가 앞과 같으면 표를 반복하지 말고 "앞과 같음"으로 줄인다.

담당자가 고친 곳을 말했다면(예: "B079 SU2id를 O로 바꿈") 그 칸이 불일치 목록에 있는지 확인해 알려 준다 —
규칙과 다르게 고친 것이 의도라면 `적용예외` 시트에 (항목ID, 차종, 값, 사유, 확인자, 확인일) 한 행을 적어 두면
다음부터 '예외 확인'으로 분류된다고 안내한다. 담당자가 원하면 그 행은 직접 써 넣어 준다 (작업 3).

## 작업 2 — 새 차종 추가 (Claude가 묻고, 담당자는 답만 한다)

담당자가 "새 차종 넣어 줘" 정도만 말해도 된다. 필요한 정보는 Claude가 아래 순서로 **먼저 요청**하고, 담당자는 답하거나 파일을 첨부하기만 한다.
알아낼 수 있는 것(차종 코드, 기준 차종 후보, 다음 Rev, 참조 데이터 유무)은 도구로 미리 채워서 고르게 한다 — 담당자에게 코드나 경로를 타이핑시키지 않는다.

### 1단계 — 차종 이름 받기
저장 폴더에 정본이 하나뿐이면 폴더는 다시 묻지 않고 "○○ 폴더의 정본(Rev)에 추가합니다"라고 알리기만 한다.
담당자가 새 차종 이름을 말하지 않았으면 이것 하나만 묻는다:
> 추가할 새 차종 이름을 알려 주세요. 진단사양서 열 머리글에 쓸 표기 그대로면 됩니다. (예: `SU2i F/L 26MY`)

### 2단계 — 준비 정보 조회 (담당자에게 묻기 전에 실행)
```bash
PYTHONDONTWRITEBYTECODE=1 python -m specforge.desk info --master "<루트>/<모듈>/<정본>.xlsx" --new-name "<새 차종 이름>"
```
결과의 `new_vehicle`에 새 차종 코드(`code`), 이미 정본에 있는지(`already_in_master` — true면 추가하지 말고 알린다),
내장 블록도 유무(`blockdiag`), 기능사양표 유무(`funcspec`), 기준 차종 후보 5개(`like_candidates`), 그리고 `next_rev`가 나온다.

### 3단계 — 한 번에 요청하기
아래 틀로 **한 메시지**에 모아 요청한다. 고를 수 있는 것은 번호로 고르게 하고, 선택 질문 도구(AskUserQuestion 등)가 있으면 그것을 쓴다.
이미 알고 있는 항목(담당자가 먼저 말한 것)은 빼고 묻는다.

> **[새 차종 추가 · BCM] ○○○ — 아래 내용을 알려 주세요.**  (모듈 이름을 제목에 넣는다)
>
> **① 기준 차종** — 시트 구성과 사양이 가장 가까운 기존 차종입니다. 규칙으로 정할 수 없는 값은 이 차종 값을 그대로 가져옵니다.
>   1) SU2i F/L 25MY (담당 이지영, 29개 시트) 2) SU2i F/L (담당 이지영, 30개 시트) 3) … (`like_candidates` 순서대로 라벨·담당자·시트 수) / 그 밖이면 차종 이름을 적어 주세요
>   (후보끼리 시트 수가 다르면 새 차종도 고른 차종의 시트에만 들어간다는 점을 한 줄 덧붙인다)
> **② 담당자** — 이 차종 열을 맡을 분 (기본: ①의 담당자 — 같으면 "같음")
> **③ 개정 번호** — `next_rev`로 할까요? (예: R392 / 다른 번호 / 비워 둠)
> **④ 블록도 PDF** — 이 차종 쪽이 들어 있는 블록도를 첨부해 주세요. 없으면 "없음".
>   (내장 블록도에 이미 있으면: "내장 블록도(R52)에 이 차종이 있어 첨부하지 않으셔도 됩니다. 더 새 판이 있으면 첨부해 주세요."
>    없으면: "내장 블록도(R52)에는 이 차종 쪽이 없습니다. 이 차종 쪽이 들어 있는 블록도가 있으면 첨부해 주세요.")
> **⑤ 기능사양표 xlsx** — 이 차종 품번사양표가 있으면 첨부해 주세요. 없으면 "없음".
>
> 블록도·기능사양표가 없으면 그 근거로 판단하는 항목은 모두 기준 차종 값으로 채우고 확인 목록에 표시합니다.
>
> 한 줄로 답하셔도 됩니다. 예: `1, 같음, 예, 없음, 없음`

### 4단계 — 답을 받은 뒤 확인 (필요할 때만 한 번 더 묻는다)
- 첨부가 있으면 `info --new-name … --blockdiag <pdf> --funcspec <xlsx>`로 다시 조회해, 첨부 문서에서 새 차종이 같은 코드로 읽히는지 본다
  (`new_vehicle.blockdiag`/`funcspec`). 안 읽히면 `refs_not_in_master`에 나온 첨부 문서 쪽 표기를 보여 주고
  "첨부하신 블록도에는 이 차종이 '○○'로 되어 있습니다. 같은 차종인가요? (예/아니오)"만 묻는다 → 예면 `--alias "○○=<코드>"`.
- 블록도에 SMK형 쪽만 있으면 "-SMK 사양 항목은 기준 차종 값을 씁니다"라고 알려 둔다 (질문 아님).
- 실행 직전에 한 줄로 요약해 확인받는다: "SU2i F/L 26MY 를 SU2i F/L 25MY 기준으로, 담당 이지영, R392 로 추가합니다. 진행할까요?"

### 5단계 — 실행
```bash
PYTHONDONTWRITEBYTECODE=1 python -m specforge.desk add-vehicle --master "<루트>/<모듈>/<정본>.xlsx" --name "<새 차종 이름>" \
    --like <기준 차종 코드> --owner <담당자> [--rev R392] [--blockdiag <pdf>] [--funcspec <xlsx>] [--alias "표기=코드"] --out "<루트>/<모듈>"
```
날짜 폴더에 새 차종이 들어간 정본 사본(`<정본 이름>_<날짜>.xlsx`), 뷰어, 원본양식에 더해
**`신규차종_<코드>_추가보고_<날짜>.html`**(추가 결과 보고서 — 무엇을·무엇 기준으로 추가했고, 근거 자료, 요약 숫자, 기준 차종과 다르게 정한 값,
확인이 필요한 칸(시트별, 이유 풀이), 새 차종 불일치, 다음 할 일)과 `신규차종_<코드>_확인목록_<날짜>.xlsx`(전 항목 상세)가 생긴다.
담당자에게는 보고서를 먼저 열어 보라고 안내한다.
확인 목록의 노란 행 = 기준 차종 값을 넣어 **확인 필요**, 파란 행 = 규칙 결과가 기준 차종과 다른 값.

### 6단계 — 결과 알리고, 마지막 두 가지를 묻는다
알릴 것: 규칙으로 정한 칸 수(`by_rule`), 그중 기준 차종과 다른 칸(`differs_from_like` 목록 그대로), 확인 필요 칸 수(`needs_check`),
새 차종의 불일치(`new_vehicle_mismatch`, 있으면 `new_vehicle_mismatch_list`). `summary_whole_workbook`은 정본 전체 숫자라 새 차종 결과로 말하지 않는다.
블록도·기능사양표가 없어 규칙을 못 쓴 경우(`has_blockdiag`/`has_funcspec` false)는 꼭 따로 말한다.

그리고 묻는다:
> ⑥ 저장 폴더의 Master를 새 차종이 들어간 정본으로 바꿀까요? (예 / 확인 목록 먼저 볼게요)
> ⑦ 확인 목록 노란 칸 중 고칠 값이 있으면 "항목 코드 · 값"으로 알려 주세요. (예: `B079 O`, `DID #B00C 0x03 X`) 없으면 "없음".

⑥이 '예'면 날짜 폴더의 정본 사본을 저장 폴더의 정본 이름으로 덮어 복사한다. Excel에서 열려 있으면 닫아 달라고 하고,
파일이 읽기 전용이라 쓸 수 없으면 날짜 폴더의 사본을 직접 복사해 바꿔 달라고 안내한다 (파일 위치를 알려 준다).
⑦에 값을 주면 작업 3대로 Master의 `차종별값`을 고치고 작업 1로 다시 만든다.

## 작업 3 — 정본 값 고치기 (담당자가 부탁할 때)

정본 구조 — 고칠 곳은 두 시트뿐이다:
- **`차종별값`**: 행 = 진단항목(항목ID·시트·코드·이름), 열 = 차종코드. 칸에 O / X / - (값형 항목은 글자). 회색 칸은 그 차종이 그 시트에 없는 칸이라 비워 둔다.
  차종별 O/X는 모두 여기 있다. 담당자는 엑셀에서 이 시트를 직접 고쳐도 된다 (원래 진단사양서처럼 항목 × 차종 격자다).
- **`적용예외`**: 규칙(블록도·기능사양표)과 다르지만 맞다고 확인한 칸만 — 항목ID, 차종, 값, 사유, 근거(Rev·CR), 확인자, 확인일.
  O/X 값을 바꾸는 곳이 아니다 (값은 차종별값에서 읽는다).
- 변경 이력은 `개정이력` 시트에 한 행 (Rev, 날짜, 작성자, 종류 'O/X 변경', 시트, 내용 예: "DID #B079 SU2id X → O", 차종).

담당자가 "B079 SU2id O로 바꿔 줘"처럼 부탁하면, openpyxl로 저장 폴더 정본을 열어 `차종별값`에서 항목ID 행(코드·시트로 찾는다)과
차종코드 열이 만나는 칸을 고치고, 개정이력 행을 더한 뒤 저장하고 작업 1로 다시 만든다. 고치기 전에 바꿀 칸(항목·차종·지금 값 → 새 값)을
담당자에게 보여 주고 확인받는다. 셀 값은 문자열로, 공백 없이 쓴다. 다른 시트·서식은 건드리지 않는다.

## 작업 4 — "합쳐 줘": 모듈별 뷰어를 골라 통합 뷰어 만들기

평소에는 모듈별 뷰어만 만든다. 담당자가 "합쳐 줘", "통합 뷰어", "BCM이랑 SMK 한 파일로" 등을 말할 때만 한다.
정본을 다시 읽거나 고치지 않는다 — 이미 만들어진 날짜 폴더의 뷰어 HTML을 골라 그대로 묶는다.

1. 판 목록 조회:
   ```bash
   PYTHONDONTWRITEBYTECODE=1 python -m specforge.desk versions --root "<저장 루트>"
   ```
   모듈마다 날짜 폴더 목록(새것부터, 날짜·Rev·뷰어 경로)이 나온다.
2. 한 메시지로 묻는다 (기본은 각 모듈의 최신판):
   > **[통합 뷰어] 묶을 판을 골라 주세요.**
   > **BCM**: 1) 20261104 (R392) 2) 20261103 (R391) …  **SMK**: 1) 20261104 (R188) …
   > 저장 위치: `<저장 루트>/통합/` 에 오늘 날짜로 둘까요? (예 / 다른 폴더)
   > 한 줄로 답하셔도 됩니다. 예: `1, 1, 예`
3. 실행:
   ```bash
   PYTHONDONTWRITEBYTECODE=1 python -m specforge.desk combine --part "BCM=<BCM 뷰어 HTML>" --part "SMK=<SMK 뷰어 HTML>" --out "<저장 루트>/통합"
   ```
   `<out>/<YYYYMMDD>/ibu_diagspec_통합뷰어_<날짜>.html` 과 묶은 판을 적은 `통합뷰어_구성_<날짜>.txt` 가 생긴다.
   통합 뷰어는 맨 위에서 모듈을 전환하고, 머리글에 "BCM R392 (20261104) · SMK R188 (20261104)"처럼 묶은 판이 찍힌다.
   안의 화면은 고른 모듈 뷰어와 똑같다.
4. 담당자에게 파일 위치와 묶은 판(모듈·날짜·Rev)을 알려 준다. 배포는 통합 뷰어 HTML 하나만 돌리면 된다.

## 마무리

- **배포는 날짜 폴더의 뷰어 HTML 파일만** 한다. 정본·원본양식은 담당자(정본 관리자)만 갖는다. HTML 머리글과 브라우저 탭 제목에
  Rev·정본 사본 이름·생성 일시가 찍혀 있어, 받은 사람이 어느 판인지 알 수 있다. HTML 안에 진단사양 전체 데이터가 들어 있으니 사내 경로로만 전달하라고 한 줄 덧붙인다.

- 고친 정본(Master)은 **SW플랫폼LAB에 보내 저장소에 반영**하도록 안내한다 (사용자가 SW플랫폼LAB 사람이면 이 안내는 생략). 저장소에 반영되면 Jenkins가 같은 결과를 다시 만든다.
- 여러 담당자가 같은 정본을 동시에 고치면 서로 덮어쓸 수 있으니, 최신 정본을 받아서 작업하라고 한 줄 덧붙인다.

## 규칙 계산 요약 (설명이 필요할 때)

- 규칙 = 진단항목의 '적용 판단 기준'(원본 I열) AND 'Tool 표시'(원본 H열 — 실제 내용은 품번·사양 조건)
- 블록도 신호: 해당 차종 블록도에 신호가 있으면 참. `-SMK 사양`이면 IMMO형 쪽, `SMK 사양`이면 SMK형 쪽에서만 찾는다
- 기능사양표: 그 차종의 어느 지역이든 STD/OPT이면 적용. `5DR`/`4DR`은 차체 형식
- 지역(브라질·북미…), `차종별 상이`, `& 직구동 타입`, `또는 TIOS …` 같은 조건은 문서로 판단할 수 없어 '조건부'
