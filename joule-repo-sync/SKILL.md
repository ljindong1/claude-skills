# joule 저장소 동기화 (회사 Gitea -> 개인 GitHub)

## 왜 이런 구조인가

joule 은 원래 개인 저장소(`D:\Ljindong\joule` -> GitHub `ljindong1/Joule`)에서 개발했는데,
회사 업무에 필요해져 사본을 회사 Gitea 로 옮겼다. 개인 계정으로는 회사 Gitea 에 접근할 수 없어
저장소가 둘로 갈렸고, 지금은 **회사 저장소에서만 개발한다**.

| | 역할 |
|---|---|
| `D:\Mobase\asec_autotest_tool` | 본 저장소. 여기서 개발하고 커밋한다 (origin = 사내 Gitea) |
| `D:\Ljindong\joule` | 동기화 작업장 겸 개인 백업. 여기서 개발하지 않는다 |
| GitHub `ljindong1/Joule` (private) | 개인 백업 사본. 작업장의 `public` 브랜치가 올라간다 |

작업장의 브랜치 두 개가 역할이 다르다. 헷갈리면 사고가 난다.

- `main` = 회사 저장소를 그대로 받아 둔 사본이다. **DBC 가 들어 있어 GitHub 로 나가면 안 된다.**
- `public` = `*.dbc` 를 떨어낸 사본이다. 이것만 GitHub 로 간다.

## 사용자가 정한 규칙 (2026-11-07)

1. **제외는 `*.dbc` 만.** 차종 표준 DB 는 고객사 자료라 사내 저장소에만 둔다.
   `src/joule/flash/assets/`(CVD·HAE 벤더 스크립트와 플래시 알고리즘 ELF)와
   `tests/golden/flash/` 는 **올린다** - 확인해 보니 그 안에 암호 열쇠가 없고
   (HSM 열쇠는 `.bin` 안에 있고 저장소에 없다) 사본이 private 이라,
   백업으로서 코드가 돌아가는 쪽을 택했다. 2026-10-27 에는 이것들도 뺐는데 그 규칙을 바꾼 것이다.
2. **덧붙이기 전용.** 이미 올라간 커밋은 고치지 않는다. force push 를 쓰지 않는다.
   (예외는 `rebuild` 하나인데, 그것도 사용자가 이력을 다시 쓰자고 한 때만 쓴다.)
3. **회사 -> 개인 단방향.** 개인 쪽에서 작업하지 않으므로 역방향은 다루지 않는다.
4. **푸시는 반드시 사용자 확인 뒤에.** 아래 "푸시 규약" 을 그대로 지킨다.
5. **사본 커밋의 작성자·커밋터는 `ljindong <ljindong1@gmail.com>`** 으로 적는다
   (날짜·메시지·순서는 회사 것 그대로). 회사 저장소는 `jdlee@mobaseasec.com` 으로 커밋되는데,
   GitHub 는 author 메일이 계정에 등록된 것일 때만 작성자로 연결하고, 개인 저장소에 회사 메일을
   남기지 않으려는 뜻도 있다. 원본을 그대로 쓰려면 `--keep-identity`.

2026-11-07 에 이 규칙으로 **사본 이력 187 개를 루트부터 다시 만들고 한 번 force push 했다**
(그 전 사본은 `*.dbc` 와 `assets/` 를 함께 뺀 132 개였고 작성자가 섞여 있었다).
그 뒤로는 덧붙이기만 한다.

## 어떻게 동기화하나

`git filter-repo` 는 이 PC 에 없고, 매번 전체를 다시 쓰면 공개 커밋 해시가 계속 바뀐다.
그래서 **회사 커밋 하나하나의 트리를 가져와 `*.dbc` 만 빼고 `public` 에 `commit-tree` 로 쌓는다.**

- 트리를 통째로 가져오므로 충돌이 없고, 작성자·커밋터·날짜·본문이 그대로 남는다.
- 각 사본 커밋 끝에 `Mirror-Of: <회사 커밋 sha>` 를 붙인다. 이것이 **다음 동기화의 기준점**이라,
  로컬 파일이나 ref 가 사라져도 사본 자체에서 "어디까지 반영했나" 를 알 수 있다.
- 제외 파일만 바꾼 커밋은 내용이 비지만 그대로 쌓는다 - 커밋이 1:1 로 대응해야 추적이 끊기지 않는다.

## 절차

스크립트 하나로 다 한다. 저장소 경로는 기본값이 박혀 있어 보통 인자가 필요 없다.

```powershell
cd D:\Ljindong\skills-repo\joule-repo-sync
python scripts\sync_mirror.py <명령>
```

Bash 로 돌릴 때는 한글이 깨지지 않게 `PYTHONIOENCODING=utf-8` 을 붙인다.

| 명령 | 하는 일 |
|---|---|
| `setup` | 한 번만. 원격·refspec·pre-push 훅을 깐다 |
| `status` | 몇 커밋 밀렸는지, 사본이 private 인지 한눈에 |
| `preview` | 올라갈 커밋 목록, 빠지는 파일, **사본에 새로 들어가는 것 점검** |
| `sync` | 사본 브랜치에 쌓는다 (로컬만, 푸시 안 함). 끝에 `verify` 가 자동으로 돈다 |
| `rebuild` | 사본 이력을 루트부터 다시 만든다. 제외 규칙이나 작성자를 바꿀 때만. 푸시에 `--force` 가 필요하다 |
| `push` | 확인을 받아 GitHub 로 보낸다 |
| `verify` | 사본 내용이 회사 저장소와 같은지 (차이가 DBC·안내 파일뿐인지) |

평소 흐름은 **`status` -> `preview` -> `sync` -> (사용자 승인) -> `push`** 다.
`sync` 까지는 로컬이라 되돌리기 쉽다. 밖으로 나가는 것은 `push` 하나뿐이다.

### 사내망 밖(집)에서도 돈다

사내 Gitea 는 사내에서만 닿지만 동기화는 집에서도 된다. 이 스킬이 **회사 저장소를 로컬 폴더로
읽기** 때문이다 - 작업장의 `company` 원격은 네트워크 URL 이 아니라 경로
`D:/Mobase/asec_autotest_tool` 이고, 회사 폴더에 보내는 git 명령은 `status` 와
`remote get-url`(설정 읽기)뿐이다. **Gitea 에는 접속하지 않는다.** 네트워크가 필요한 곳은
GitHub 하나다 (사본 fetch·push, private 판정).

그래서 동기화 기준은 **회사 폴더의 로컬 `main` 브랜치**다. 사내에서 한 커밋이 그 폴더에
들어 있어야 사본에 올라간다. 집에서는 Gitea 에서 새로 가져올 수 없으니, "사내에서 커밋했는데
사본에 없다" 면 그 폴더가 아직 그 커밋을 받지 못한 것이다 (사내망에서 `git pull` 한 뒤 다시 돌린다).

### preview 에서 사용자에게 보고할 것

`preview` 가 "사본에 새로 올라가는 것 점검" 을 찍는다. 기준은 회사 트리가 아니라 **지금 사본**이라,
회사 저장소에 오래 있었지만 사본에 처음 들어가는 파일도 여기서 드러난다.
이 세 줄은 그냥 흘리지 말고 사용자에게 옮긴다.

- **사본에 처음 들어가는 확장자** - 새 종류의 자료가 섞여 들어오는 신호다.
  `.xls` `.pdf` `.dbc` `.arxml` `.bin` 같은 것이 뜨면 올려도 되는지 먼저 묻는다.
- **사본에 처음 들어가는 최상위 폴더** - 새 자료 묶음이 생겼다는 뜻이다.
- **1MB 넘는 파일** - 백업에 큰 바이너리가 들어오는지 본다.

이 점검이 있는 까닭: 2026-10-27 에 정한 제외 규칙만 믿고 돌렸다면, 그 뒤 `tests/golden/flash/` 로
새로 들어온 벤더 스크립트 본문이 점검 없이 올라갔을 것이다. **제외 규칙은 시간이 지나면 낡는다.**

## 푸시 규약 (사용자 요구)

푸시는 되돌리기 어렵고 밖으로 나가는 일이라, **사용자가 그 자리에서 승인한 뒤에만** 한다.

- Claude 가 대신 돌릴 때는 `push` 를 **먼저 묻지 않고 실행하지 않는다.**
  `preview`·`sync`·`verify` 결과를 보여 주고 "보낼까요?" 를 물은 뒤, 승인을 받고서야 보낸다.
- 승인은 **그 턴에 받은 것만** 유효하다. 지난번 승인이 이번 푸시를 덮지 않는다.
- 스크립트도 스스로 막는다: 확인 입력(`push` 라고 타이핑)이 없거나 비대화형이면 멈춘다.
  사용자 승인을 받은 뒤에만 `--confirmed` 를 붙여 돌린다.
- `push` 는 보내기 전에 **무엇이 나가는지** 찍는다 (대상 저장소, 커밋 수, fast-forward 여부,
  빠지는 패턴, 사본 작성자). 그리고 private 이 아니면, 검증이 통과하지 못하면,
  fast-forward 가 아닌데 `--force` 가 없으면 멈춘다.
- `--force` 는 `rebuild` 로 이력을 다시 쓴 뒤에만 쓴다. `--force-with-lease` 로 보내므로
  GitHub 쪽이 그 사이에 바뀌었으면 거부된다. 쓰기 전에 **force 라는 것과 무엇을 버리는지**
  사용자에게 분명히 말하고 승인을 받는다.

## rebuild 를 쓰는 때

제외 규칙이나 작성자처럼 **과거 이력까지 걸리는 것**을 바꿀 때만 쓴다. 평소에는 `sync` 다.

`rebuild` 는 돌면서 스스로 세 가지를 확인한다. 하나라도 어긋나면 종료 코드가 0 이 아니다.

- **1:1 대조**: 사본 커밋 수가 회사와 같고, 커밋마다 날짜·제목이 같고,
  `Mirror-Of` 가 짝이 맞는 회사 커밋을 가리키는지.
- **최신 트리 비교**: 다시 만든 사본의 최신 내용이 전 사본과 같은지.
  제외 규칙을 바꾸지 않았다면 같아야 하고, 다르면 왜 다른지 설명이 있어야 한다.
- **verify**: 회사 트리와의 차이가 빠진 DBC + 안내 두 파일뿐인지.

전 사본은 `refs/sync/public-before-rebuild` 에 남는다. 푸시 전이라면 그것으로 되돌릴 수 있다.
merge 커밋이 있는 이력은 선형 재생성으로 다룰 수 없어 스스로 멈춘다 (부모 매핑을 넣어야 한다).

## 안전망 (실기 확인됨)

- `pre-push` 훅: GitHub 로 가는 ref 안에 `.dbc` 가 있으면 거부한다.
  `main` 을 실수로 밀면 막힌다 - 2026-11-07 에 실제로 막히는 것을 확인했다.
- `remote.origin.push = refs/heads/public:refs/heads/main`: `git push origin` 만 쳐도 사본만 나간다.
- `branch.main.remote = company`: 작업장 `main` 의 기본 상대가 회사 저장소다 (전에는 GitHub 였다).
- `verify`: 사본과 회사 트리의 차이가 **빠진 DBC + 안내를 덧붙인 두 파일**뿐인지 본다.
  설명되지 않는 차이가 하나라도 있으면 푸시하지 않는다.
- private 확인: 토큰 없이 `api.github.com` 을 두 번 읽는다. 확실히 public 인 저장소를 대조군으로 먼저
  읽어, 404 가 "private" 때문인지 "네트워크 차단" 때문인지 가린다. 판정이 안 되면 푸시하지 않는다.

## 되돌리기

`sync` 가 쌓은 것이 잘못됐으면 (아직 푸시 전이라면) 사본 브랜치를 전으로 돌린다.

```powershell
cd D:\Ljindong\joule
git reflog public            # 전 위치를 찾는다
git update-ref refs/heads/public <전 sha>
git update-ref -d refs/sync/company-main
```

푸시한 뒤에 잘못을 발견했다면 되돌리지 말고 **회사 저장소에서 고쳐 커밋하고 다시 동기화한다**
(덧붙이기 전용이라 그게 자연스럽다). 사본 이력을 force push 로 고치는 것은 사용자가 따로 요청할 때만 한다.

## 흔한 문제

| 증상 | 까닭과 조치 |
|---|---|
| `[중단] 작업장에 커밋 안 된 변경이 있다` | 작업장은 동기화 전용이다. 거기서 파일을 고치지 않는다. `git -C D:\Ljindong\joule checkout .` 로 되돌린다 |
| `[중단] 기준점을 찾지 못했다` | 사본 tip 에 `Mirror-Of` 가 없고 ref 도 없다. `--from <회사 커밋>` 으로 한 번 준다 |
| `기준점 ... 추정 - 맞는지 확인할 것` | trailer 가 없어 작업장 `main` 으로 추정했다. `preview` 의 커밋 목록이 맞는지 사용자와 확인한다 |
| `[중단] 기준점이 회사 tip 의 조상이 아니다` | 회사 저장소 이력이 갈렸다(rebase·force push). 사용자에게 알리고 어떻게 맞출지 정한다 |
| `[중단] private 임을 확인하지 못했다` | 네트워크가 막혔거나 저장소가 public 이 됐다. 공개 상태를 확인한 뒤에만 `--allow-public` |
| `[경고] 설명되지 않는 차이` | 사본과 회사 트리가 제외·안내 밖에서 다르다. 푸시하지 말고 원인을 찾는다 |
| 회사 저장소에 커밋 안 된 변경이 있다는 알림 | 동기화는 커밋된 것만 다룬다. 먼저 커밋할지 사용자에게 묻는다 |

## 하지 않는 일

- 개인 -> 회사 방향은 다루지 않는다. 개인 쪽에서 작업할 일이 생기면 설계부터 사용자와 다시 정한다.
