# eCoDY-IMS 패치 추적

SWP Delivery_Patch 티켓 하나를 출발점으로 **연결된 자료 전부**를 따라가 사내 Confluence 페이지로 정리한다. 매일 아침 예약 작업이 부르는 무인 실행이 기본이므로 **실행 중 사용자에게 되묻지 않는다** — 막히면 막힌 사실을 페이지에 남기고 끝낸다.

> **이 스킬이 존재하는 이유.** 패치 티켓 본문에는 `Dcm_R44 2.1.1.0_HF2 → 2.1.1.0_HF4` 같은 한 줄만 있다. 실제로 무엇이 바뀌는지, 적용하면 어떤 에러가 새로 뜨는지, 어떤 결함이 고쳐지는지는 **티켓에 링크조차 없는 자료들**에 흩어져 있다. 2026-11-05 실측: 티켓 하나를 끝까지 따라가니 IMS 18건 + ECM 4건이 나왔고, 그 안에 **티켓에 전혀 등장하지 않는 중간 버전의 변경 6건**과 **패치 후 새로 뜨는 Validation 에러 — 신규 16개 + 변경 1개**가 있었다. 사람이 매번 이걸 다 뒤지지 않게 하는 것이 목적이다.

## 입력과 산출물 — 이 셋 밖은 내 일이 아니다

| | |
| --- | --- |
| **입력** | ① 사람이 집어 준 **Delivery_Patch 티켓 키** · 또는 ② 직전 실행이 남긴 구간 마커 `IMS-WINDOW-END-UTC`(무인 실행) |
| **하는 일** | 그 티켓에서 출발해 **참조가 더 안 나올 때까지** eCoDY-IMS·ECM 을 따라가 수확한다 (→ 추적 지도) |
| **산출물** | 사내 Confluence **패치 페이지**(티켓 1개 = 페이지 1장) + **일별 기록** 1장 + 부모의 **색인 영역** |

산출물이 제 규격을 지키면 그 뒤를 누가 어떻게 쓰든 상관없다. 그래서 이 문서는
**다른 스킬이 무엇을 어떻게 하는지 적지 않는다** — 적어 두면 그 스킬이 바뀔 때 같이 썩고,
읽는 내가 남의 절차를 내 절차로 착각한다.

## 권한 원칙

**eCoDY-IMS · eCoDY-ECM — 읽기 전용**
- **조회(GET)만** 한다. `ims_api.py`·`ecm_api.py`·`_ecody_common.py` 는 GET 이외 요청을 스스로 차단한다. 스크립트 밖에서 임의의 `fetch`·폼 제출·편집/삭제/댓글/좋아요/감시/상태 변경을 하지 않는다.
- **IMS 댓글은 HAE 로 나가는 외부 메시지다.** 이 스킬은 쓰지 않는다. 문의가 필요하면 **초안만 보고에 담고 등록하지 않는다.**
- 로그인·OTP·비밀번호는 입력하지 않는다. **토큰 값은 페이지·보고·로그에 절대 쓰지 않는다.** 접속 계정이 공용 계정이면 그 사실을 알고 권한 범위를 그 계정 기준으로 본다.

**사내 Confluence(mobaseasec) — 생성·수정 가능, 삭제 금지**
- 생성: 부모 `334594056` 아래 **① 구간 내 신규 티켓의 패치 페이지**(P8N — 무인 실행도 만든다), **② 일별 기록 페이지**(`380698635` 하위). 기준선 이전의 과거 티켓은 만들지 않고 일지의 목록에만 올린다. 🔴 **그 목록을 근거로 작업을 제안하지 않는다** (사용자 방침 2026-11-07 — "기존 것은 작업 완료한 것이라 안 해도 된다. 앞으로 일어나는 것 중심으로 간다").
- 수정 허용 범위는 둘뿐이다: ① 이 스킬이 관리하는 패치 페이지 본문, ② 부모 페이지의 `PATCH-INDEX` 관리 영역.
- 모든 수정은 **직전 `getConfluencePage(contentFormat="html")` → 필요한 부분만 바꿈 → 나머지는 받은 html 그대로 → `updateConfluencePage`** 순서를 지킨다. MCP 는 본문 전체를 교체하므로, 받은 html 을 건너뛰고 새로 쓰면 사람이 붙여 둔 내용·첨부가 사라진다.
- 삭제·이동(`parentId` 변경)은 하지 않는다.

**사내 Redmine — 건드리지 않는다**
- 읽지도 쓰지도 않는다. 패치 페이지는 **eCoDY 자료만으로** 구성한다 (사용자 방침 2026-11-05).

## 설계 원칙 — 왜 이렇게 하는가

- **티켓 본문은 출발점일 뿐이다.** 모듈명과 시작·끝 버전, 그리고 "설정 변경은 배포 시 댓글로 안내"라는 문구가 거의 전부다. 본문만 읽고 끝내면 아무것도 모른 것과 같다.
- **버전 경로를 끊지 않는다.** `HF2 → HF4` 면 **HF3 도 들어온다.** 중간 버전은 티켓·설정 변경 안내 어디에도 등장하지 않지만 반드시 함께 적용된다. 시작·끝만 보면 그 변경을 통째로 놓친다.
- **없는 것과 못 찾은 것을 구별해 적는다.** 하위작업 본문이 비어 있으면 "자료 없음"이라고 쓴다. 안 쓰면 다음 사람이 똑같이 한 시간을 헤맨다. §2.5 "자료가 없는 것" 절은 선택이 아니라 필수다.
- **수집은 스크립트가 결정적으로, 판단만 Claude 가 한다.** 어떤 티켓을 읽을지는 아래 추적 지도가 기계적으로 정한다. "중요해 보이는 것만" 고르면 빠진다.
- **댓글이 티켓의 본체다.** 2026-11-05 실측: 댓글 23건 중 19건이 패치가 아니라 **별개로 안내된 통합필수점검 논쟁**이었고, 2주를 끌다 "검증 불필요"로 끝났다. 이 결론을 페이지에 **끝난 일이라고 명시**해야 다음 사람이 다시 꺼내지 않는다.
- **적용자가 쓸 수 있게 쓴다.** 페이지의 목적은 요약이 아니라 **누락 없는 적용**이다. 그래서 ERR 코드·의존 모듈 버전·재현 시나리오처럼 **그대로 복사해 쓸 값**을 반드시 담는다.
- **MCU 가 다르면 함정이 다르다.** 같은 모듈의 같은 패치라도 S32K 계열과 CYT 계열은 설정 근거 문서의 절이 다르고 MCAL 제약이 다르다. 형제 과제 페이지를 참조로 걸되 **"MCU 가 달라 함정은 다르다"를 명시**한다.
- **짝 패치가 같을 거라고 가정하지 않는다.** 2026-11-05 실측: 같은 모듈·같은 버전의 FBL·APP 패치인데 **설정 변경이 거의 겹치지 않았다** — DefineOption 이름도(`DCM_FOTA_USED_FBL` vs `__GHS__`), harmonize 대상도(EcuM·BswM vs Rte·EcuM), Rte ShortName 목록도 달랐다. **FBL·APP 은 각자 끝까지 조사한다.** 같은 부분(버전 경로·결함 상세·ERR 목록)은 "양쪽이 같다"고 명시해 주면 읽는 사람이 헷갈리지 않는다.
- **패치 설정과 "함께 온 점검 안내"를 구별한다.** HAE 가 배포 때 끼워 보내는 통합필수점검·HwObject 권장 사항은 **패치와 무관한 잠재 이슈 공유**다(HAE 가 직접 그렇게 설명했다 — 2026-11-05 실측). 설정 변경 표에 섞여 와도 페이지에서는 **별도 항목으로 떼어** 적는다. 섞어 적으면 "패치 때문에 해야 하는 일"로 오해한다.
- **예측할 수 있는 것은 예측해 준다.** IM 의 표준 설정값과 새 Validation 의 조건을 나란히 놓으면 **무엇이 걸릴지 미리 알 수 있다**(§P5). 적용자가 Generate 하고 당황하기 전에 알려 주는 것이 이 페이지의 값이다.
- **구간이 범위를 정한다.** "미종결 티켓 전부"가 아니라 **직전 실행 이후**가 기준이다. 기준 없이 긁으면 백로그 수십 건에 페이지를 만들어 버린다. 구간 사슬(`IMS-WINDOW-END-UTC`)이 있으면 주말·휴일·실패가 끼어도 빈틈이 없고, 과거를 소급하지도 않는다.
- **발행 규약은 `confluence-writing` 이 정본이다.** 이 스킬은 "무엇을 담을까"만 정하고, "어떻게 쓰고 올릴까"는 그 스킬을 따른다. 발행·수정 단계(P7·P8·P8N·P9)에 들어가기 전에 **반드시 읽는다** — 안 읽고 쓰면 표 폭이 통째로 날아간다(2026-11-06 실측, 아래 함정 표).
- **고객사 전용 자료다.** 요약·링크 중심으로 쓰고 본문을 통째로 옮기지 않는다. 설정값·버전·ERR 코드·파라미터명 같은 사실은 짧게 그대로 인용해도 된다.

## P2. 대상 결정

### P2-1. 구간 확정 — 어디서부터 "새것"인가

**구간은 직전 실행이 정한다.** 주말·휴일·실패가 끼어도 빈틈이 생기지 않는다 (`ecody-ecm-monitor` 와 같은 사슬 방식).

1. `getConfluencePageDescendants(pageId="380698635", depth=1)` 로 일지 목록을 받아 **날짜가 가장 늦은 1건**을 읽고 `IMS-WINDOW-END-UTC:\s*(\S+)` 를 뽑는다. 이 값이 `WINDOW_START`.
2. 그 기록이 없으면(일지가 전부 지워진 경우) `WINDOW_START` = **오늘 00:00 KST** (= 전날 15:00 UTC). 정상 상태에서는 기준점 페이지 `380764172` 가 최소 1건을 보장한다 — 없으면 보고에 **"일지가 사라졌다"**를 적는다.
   > 🔴 **과거를 소급하지 않는 이유.** 기준 날짜 없이 미종결 티켓을 전부 긁으면 백로그 수십 건에 페이지를 만들어 버린다. 그래서 **첫 실행은 오늘부터**다. 과거 티켓은 사용자가 지시할 때만 만든다 (사용자 방침 2026-11-06).
3. `WINDOW_END` = 현재 UTC (P0 에서 구한 값).
4. 구간이 7일을 넘으면 그대로 진행하되 보고와 일별 기록에 **"장기 공백 N일"** 을 명시한다.

### P2-2. 페이지가 있는 티켓 — 갱신 대상

1. `getConfluencePageDescendants(cloudId="mobaseasec.atlassian.net", pageId="334594056", depth=1)` 로 하위 페이지 목록(id·제목)을 받는다.
2. 각 페이지를 `getConfluencePage(contentFormat="markdown")` 로 읽어 푸터 마커를 뽑는다.

| 마커 | 뜻 | 정규식 |
| --- | --- | --- |
| `IMS-PATCH-TICKET` | 이 페이지가 담당하는 티켓 키 | `IMS-PATCH-TICKET:\s*(\S+)` |
| `IMS-UPDATED` | 마지막 반영 시점의 티켓 갱신 시각 | `IMS-UPDATED:\s*(\S+)` |
| `IMS-COMMENTS` | 마지막 반영 시점의 댓글 수 | `IMS-COMMENTS:\s*(\d+)` |
| ⭐ `IMS-GUIDE-REV` | **이 페이지가 어느 판의 안내로 쓰였나** — 설정 변경 안내 댓글의 번호와 그 댓글의 `수정` 시각(`[2]@2026-11-09T11:25`). 수정된 적이 없으면 작성 시각을 쓴다 | `IMS-GUIDE-REV:\s*\[(\d+)\]@(\S+)` |

3. 마커가 있는 티켓 키 전체가 **갱신 판정 대상**이다(→ P6). 마커가 없는 페이지는 사람이 손으로 쓴 것이므로 **건드리지 않는다**.

> 📌 **손으로 쓴 과거 5장의 현재 상태** (2026-11-07)
>
> `MCP0806-255` · `270` · `272` · `279` · `280` 은 사람이 쓴 페이지인데 **§1 일감 개요 속성 표는
> 11개 규격으로 맞춰 두었다**(사용자 지시). 그래서 부모 목록 표에 올라올 수 있는 상태다.
>
> 🔴 **그래도 마커(`IMS-PATCH-TICKET`)가 없으므로 무인 실행은 여전히 건드리지 않는다.**
> 본문은 옛 축(수집 순서)이고 부록으로 쪼개지도 않았다 — 전면 재생산은 티켓마다
> IMS·ECM 전수 추적이 붙으므로 **사용자가 지목할 때만** 한다.
>
> ⚠️ **속성 표를 두 번 줄이지 않는다.** 표에 `티켓`·`제목`·`일정` 같은 옛 항목이 보이면 아직
> 안 고친 페이지이고, 안 보이면 이미 11개다. **행 이름으로 판별한다.**

### P2-5. 옛 페이지의 속성 표만 11개로 줄일 때 ⭐ (2026-11-07 신설)

사용자가 **"일감개요 표만 고쳐라, 다른 내용은 그대로 둬라"** 고 할 때의 절차다. 본문을 다시 쓰지 않는다.

| 지키는 것 | 왜 |
| --- | --- |
| 🔴 **뺄 값이 본문에 있는지 먼저 센다** | 표에서 빼면 **그 값이 페이지에서 사라진다.** 본문 html 을 받아 그 문자열을 세고 **1회면 표에만 있는 것**이다(= 사라진다). 2회 이상이면 본문에도 있다 |
| 🔴 **본문에 없는 값은 버리지 말고 옆 표로 옮긴다** | 속성 표 바로 뒤의 **"속성에 넣지 않은 티켓 정보"** 표가 그 자리다. ADF 라면 **행 노드를 그대로 `push`** 하고 첫 칸만 `tableHeader → tableCell` 로 바꾼다 — 글자를 다시 쓰지 않으니 깨질 데가 없다 |
| 실측(5장) | 본문에 **없던** 것은 `연관 수평전개` · `SWP Generator` · `배포 구분` · `일정` · `담당 / HAE 응대` **다섯**이었다 → 전부 옆 표로 옮겼다. `티켓`·`제목` 은 서두 링크와 페이지 제목에 있어 버렸고, `MCU`·`제어기 단계` 는 `적용 대상` 첫 줄로 합쳤다 |
| 👤 **칸은 노드를 재사용해 보존한다** | `사내 일감` · `사내 진행 상태` 는 **받은 ADF 행 노드를 그대로 다시 넣는다.** 270·255 의 Redmine 번호와 진척이 한 글자도 바뀌지 않았다 |
| ⭐ **값이 틀린 칸은 고친다** | 실측: 279·280 의 `새 Validation` 이 **"19개"** 였는데 같은 Dcm HF4·같은 IM `4.1.1.28` 은 **신규 16 + 변경 1** 이다(198 조사). 270 의 `티켓`·`SWP 버전` 에는 **255 의 값**이 섞여 있었다. 줄이는 김에 **근거를 적어 바로잡는다** |
| 캡션도 같이 고친다 | 표 뒤의 *"위 속성은 목록 표의 열로 그대로 쓰인다"* 는 20개 시절 문구다. **11개 중 ⭕ 여섯만 열이 된다**로 바꾸고 **뺀 값이 어디로 갔는지** 한 줄 적는다 |
4. ⭐ **대표의 하위(깊이 2)를 구별한다.** `depth=1` 목록에는 섞이지 않으므로 평소에는 신경 쓸 일이 없다. 열어 보게 되면 푸터 마커로 가른다 — `IMS-PATCH-SUB` 가 있으면 **이 스킬이 만든 부록 4장**이고(P8 이 고친다), 마커가 아무것도 없으면 **사람이 손으로 쓴 심화 분석 페이지**이므로 읽지도 수정하지도 않는다.
5. 일별 기록은 부모의 직접 자식이 아니라 묶음 페이지 `380698635` 하위이므로 이 목록에 섞이지 않는다. 묶음 페이지 자신도 제목에 `Delivery_Patch` 가 없어 제외된다.

### P2-3. 신규 티켓 — 구간 내에 생긴 것은 페이지를 만든다 ⭐

고정 설정의 **과제 프로젝트 목록**을 대상으로 구간 내 생성분을 찾는다.

```bash
python <스킬폴더>/../ecody-search/scripts/ims_api.py search   --queries '[{"tag":"신규","jql":"project in (MCP0806,MCP1001,MCP1105) AND issuetype = SWP_Module_Release AND created >= \"<WINDOW_START KST yyyy/MM/dd HH:mm>\" ORDER BY created ASC"}]'   --per-query 50 --out <스크래치패드>/new.txt
```

> ⚠️ **JQL `created` 는 KST 로 쓴다** (Jira DC 는 서버 시간대 해석). `WINDOW_START` 가 UTC 이므로 **+9h 해서** 넣는다. 상태로 거르지 않는다 — 한글 상태명은 `HTTP 400` 을 낸다(실측).

결과를 셋으로 나눈다.

| 구분 | 처리 |
| --- | --- |
| 구간 내 생성 + **페이지 없음** | ⭐ **P8N 으로 페이지를 만든다** |
| 구간 내 생성 + 페이지 있음 | 이미 P2-2 에 있다. 중복 생성하지 않는다 |
| 구간 **밖**(과거) + 페이지 없음 | **만들지 않는다.** 일별 기록의 "페이지 없는 과거 티켓" 목록에 키·제목·상태·댓글 수만 적는다 |

마지막 줄이 방침의 핵심이다 — **구간 안에 생긴 것만 만든다.**

> 🔴 **과거 백로그는 알림판이 아니라 기록이다** (사용자 방침 2026-11-07).
>
> 이전 방침은 "사용자 판단을 기다린다"였고, 그래서 나는 회차마다 *"가장 묵은 `MCP1105-96`·`97` 을
> 짝으로 묶어 하시겠습니까"* 같은 **제안을 붙였다.** 그러지 않는다 — 사용자의 말로는
> **"기존 것은 작업 완료한 것이라 안 해도 된다. 앞으로 일어나는 것 중심으로 간다."**
>
> | 한다 | 하지 않는다 |
> | --- | --- |
> | 목록에 **키·제목·상태·댓글 수**를 남긴다 | 🔴 **"이걸 하시겠습니까" 를 묻지 않는다** |
> | 사용자가 **티켓 키를 집어 주면** 그때 만든다(P2-4) | 🔴 묵은 순서·짝 묶음을 **추천하지 않는다** |
> | 목록은 **그대로 유지**한다 — 나중에 필요해지면 바로 쓴다 | 🔴 보고·일지 꼬리에 **권유 문장을 쓰지 않는다** |
>
> 📌 **목록을 지우지는 않는다.** 키와 상태가 적혀 있어야 나중에 지목할 때 바로 쓸 수 있고,
> 지워 두면 그 사실을 다시 수집해야 한다. **남기되 조용히 남긴다.**

### P2-4. 재작성 요청 — 사람이 티켓 키를 집어 주었을 때 ⭐ (2026-11-06 신설)

사용자가 티켓 키를 주며 **"다시 만들어줘", "재작성", "새 규격으로 다시", "페이지 다시 정리"**
라고 하면 이 모드다. **P6 변화 판정을 건너뛰고** P3~P7 을 처음부터 돌려 본문을 전면 교체한다.

왜 필요한가 — 페이지 **규격이 바뀌었을 때**다. 티켓은 그대로인데 수확 규칙이 늘어난 경우
(`page-format.md` §3.1 의 "근거 문서 설정 변경 절 전수 수확" 처럼), P6 은 "변화 없음 →
건너뜀" 으로 판정해 **아무것도 하지 않는다.** 그러면 새 규격이 영원히 반영되지 않는다.

| 지키는 것 | 왜 |
| --- | --- |
| **페이지를 지우지 않는다. 같은 id 에 본문만 교체한다** | ⭐ 페이지 URL 은 **바깥에서 참조된다** — 다른 위키 문서, 메일, 사내 기록. 지우고 새로 만들면 id 가 바뀌어 **그 참조가 전부 깨진다.** 어디서 가리키는지 이 스킬은 알 수 없으므로, 안전한 쪽을 택한다. 댓글·버전 이력도 사라진다 |
| **교체 전에 현재 본문을 스크래치패드에 내려 둔다** | 되돌릴 수 있어야 한다. 그리고 비교 재료가 된다 |
| **교체 후 이전 버전과 대조해 "새로 들어온 절"을 보고한다** | 규격 보완이 실제로 먹었는지 확인하는 유일한 방법이다. 지웠으면 이 비교가 불가능하다 |
| **짝 패치 페이지도 함께** | FBL·APP 은 한 쌍이다. 한쪽만 새 규격이면 다음에 또 헷갈린다 |
| 무인 실행에서는 **돌지 않는다** | 사람이 명시적으로 요청할 때만. 전면 교체는 무인으로 할 일이 아니다 (P8-A 참조) |

반영은 P8-B(사람이 있을 때 ADF 왕복)로 한다. 본문이 길면 `updateConfluencePage` 응답이
잘릴 수 있다 — "발행 시 유의" 를 먼저 읽어라.

## P3. 티켓 정독

```powershell
python <저장소>\ecody-search\scripts\ims_api.py read <티켓키들> --max 60000 --out <스크래치패드>\ticket.txt
```

Delivery_Patch 티켓은 댓글이 수십 건이라 `--max` 를 크게 준다(2026-11-05 실측: 댓글 23건 티켓이 17,073자). 출력에 본문·댓글·첨부·연결·하위작업·변경 이력이 모두 들어온다.

본문에서 반드시 뽑는 것:

| 항목 | 쓰임 |
| --- | --- |
| 모듈 목록과 **시작→끝 버전** | P4 릴리즈 노트 체인의 입력. 가장 중요하다 |
| SWP 이름·버전 | 페이지 §1 |
| 유형·상태·**IMS 티켓 라벨** | 진행 상태 판정 (`VC_Checked`, `배포완료`, `HAEQ확인_적용` 등). ⭐ **사용자 방침이 금지한 것은 사내 Confluence 라벨**(`patch`)이고, **IMS 티켓 라벨은 상태 근거이므로 읽는다** — 품질 검증 통과 여부가 여기에만 남는 경우가 있다 |

댓글에서 반드시 뽑는 것:

| 항목 | 주의 |
| --- | --- |
| **설정 변경 안내 표** | 보통 배포 댓글에 있다. 나중에 **수정될 수 있다** — 변경 이력에서 댓글 수정 시각을 확인한다 |
| `Generator` · `harmonize` 항목 | "해당 없음"도 사실이므로 적는다 |
| 기술 문답 | 결론을 뽑아 §4 에 쓰고 **"끝난 논의"임을 명시**한다 |
| 가리킨 ECM 문서 제목·링크 | P5 의 입력 |

변경 이력·첨부에서 반드시 뽑는 것:

- **첨부 `삭제 + 추가` 가 같은 파일명으로 일어났으면 재배포다.** 날짜를 §7 에 적고 "이전 파일로 작업했다면 대조하라"를 경고한다.
- **올린 쪽을 구별한다.** HAE 배포본과 **당사가 올린 자료**(빌드 로그·arxml·Validation 결과·캡처)를 §7 표에서 나눈다. 당사 첨부는 질문의 근거이고, 특히 **빌드 로그에는 실제 실패 원인이 들어 있다** — 거기서 치명 오류와 경고를 꺼내 §4 에 적는다(2026-11-05 실측: `cannot open source file "Com.h"` 로 Jenkins FAILURE).
- 담당자 왕복 횟수 — 문답이 길었다는 신호다.
- **IMS 티켓 라벨 변화** — 품질팀 검토 완료 등 상태 근거다. `HAE → HAE 배포완료 → HAE VC_Checked 배포완료` 처럼 흐름이 남는다. 누가 언제 올렸는지까지 적는다(실측: 199 는 배지환/협력사가 2026-09-10 에 `VC_Checked` 를 달았고, **그 사실이 댓글에는 없다**).
- **HAE 답변의 어조를 그대로 옮긴다.** "이미 되어 있을 것으로 **기대**됩니다" 는 확인이 아니다. 이런 답은 §확인 필요 에 "직접 확인해야 한다"로 올린다.

## P4. IMS 추적

**`references/collect-guide.md` §1~§3 을 읽고 그대로 수행한다.** 요지:

1. **수평전개**: 연결(`Relates`)의 `Information` 티켓 → 그 본문의 `수평전개 티켓 : CPINFO-xxxx` → **원본을 읽는다**. 결함 상세 12항목이 여기 있다. `--max` 를 20000 이상 준다(실측 8,713자).
2. **짝 패치**: APP↔FBL 티켓은 **서로를 직접 링크하지 않는다**(2026-11-05 실측). 위 **수평전개 사본의 연결 목록**에 양쪽이 걸려 있으니 거기서 찾는다. 키·상태만 확인하고 본문은 그 페이지가 따로 담당한다 — 단 **설정 변경이 같을 거라고 가정하지 않는다**.
2-1. **댓글이 가리키는 다른 과제 티켓**: "`<다른과제>-NNN` 과 같은 방법으로 조치" 같은 문구가 나오면 그 키를 읽어 본다. 우리 과제가 아니면 **`HTTP 403 "명시된 이슈를 볼 권한이 없습니다"`** 가 뜬다 — 그때는 §2.5 에 "조치 내용이 우리 기록에 없다 · 작업자나 커밋 이력으로 확인 필요"를 적는다. 이것을 안 적으면 같은 문제가 재발했을 때 처음부터 다시 헤맨다.
3. **릴리즈 노트 체인** — 가장 중요하고 가장 잘 빠진다. 시작·중간·끝 버전을 **전부** 찾는다. JQL 형식과 토큰화 함정은 `collect-guide.md` §2 가 정본이다.
4. **하위작업**: 릴리즈 노트의 `sub-task_SWCR` 전부를 읽는다. **본문이 비어 있는 것이 정상이다**(실측 12건 전부 비어 있었다). 비어 있으면 §2.5 "자료 없음"에 기록하고 수평전개로 넘어간다.
5. **사전 공지**: `CPD_ModulesPreNotice`. 보통 본문이 없다. 존재 사실만 적는다.

## P5. ECM 추적

```powershell
python <저장소>\ecody-search\scripts\ecm_api.py search --queries <쿼리json> --per-query 12 --out <...>
python <저장소>\ecody-search\scripts\ecm_api.py read <pageId들> --max 60000 --out <...>
```

| 찾을 것 | 왜 | 어떻게 |
| --- | --- | --- |
| **`[IM] <모듈> - R44`** | ★★ 버전별 **의존 모듈 버전** · **Validation 신규 ERR 코드 전체 목록** · 설정 신규 항목. 페이지 가치의 큰 몫이 여기서 나온다 | `title ~ "<모듈>" and title ~ "IM"` → 한 페이지를 `--max 60000` 으로 받아 버전 절(`4.1.1.x`)을 뽑는다 |
| 통합필수점검 `[IA-0xx]`·`[VC-0xx]` | 댓글이 "FAIL #5 해당" 처럼 번호만 말한다. 문서를 봐야 **등급(Error/Advisory/Exception)** 과 조건을 안다 | `title ~ "IA-0xx"` |
| 설정 변경의 근거 `SAG` | 안내가 가리킨 절이 **우리 MCU 에 해당하는지** 확인해야 한다 | 제목 키워드로 검색 |
| `[ToU 7-2]` 수평전개 프로세스 | Close 전 댓글 양식 | `title ~ "수평전개" and title ~ "프로세스"` |

> ⚠️ **HAE 가 적어 준 IM 절 번호를 그대로 믿지 않는다.** IM 은 장 번호 체계를 재편한 적이 있어 안내의 절 번호가 옛것일 수 있다 (2026-11-05 실측: 안내의 `5.1.1.29`·`3.1.1.5` 가 현재 IM 에서 `4.1.1.28`·`2.1.1.5` 였다). **제목과 내용으로 찾고, 번호가 어긋났으면 페이지에 그 사실을 적는다** — 적용자가 못 찾아 헤매는 주된 원인이다.

> ⚠️ **ECM 링크가 `HTTP 404 {"authorized": false}` 로 막힐 수 있다.** 계정 권한 문제다. 추측으로 메우지 말고 §2.5·§5 에 "페이지 id · 404 · 권한 요청 필요"를 기록한다. 권한이 막혔을 때의 우회로 두 가지를 페이지에 적어 주면 좋다 — ① **배포 zip 안의 `Doc` 폴더에 설정 변경 문서가 들어 있다**(2026-11-05 HAE 안내), ② 같은 내용의 다른 ECM 페이지를 제목으로 검색한다.

> ⭐ **여기서 한 걸음 더 — 무엇이 걸릴지 예측한다.** IM 에는 그 모듈의 **표준 설정값**(예: `2.4.1 DcmGeneral`)과 **새 Validation 의 조건**(예: `4.1.1.28`)이 같이 있다. 둘을 나란히 놓고 대조하면 **적용자가 만날 에러를 미리 지목할 수 있다.**
>
> 2026-11-05 실측 예: `ERR053310`·`ERR053311` 의 조건은 "서비스가 `Used=true` + `DcmDemIntegrated=false` + 사용자 함수 없음" 인데, IM 이 정한 **FBL 표준 설정이 `DcmDemIntegrated: False`** 였다. 즉 FBL 은 조건의 절반을 기본으로 만족한다 → 페이지에 "**이 FBL 에서 걸릴 가능성이 높다, 근거는 이것**" 이라고 적었다. 이런 한 줄이 페이지의 가치를 가장 크게 올린다. **단 "가능성이 높다"로 쓰고 "걸린다"로 쓰지 않는다** — 실제 설정은 확인하지 않았기 때문이다. 그리고 같은 자리에 조건 · 참고(HAE 표준값) · **확인 지점**(당사 파일 + 컨테이너 경로 + 파라미터명) · 판정(`확인 필요`)을 붙인다 — **규칙 8 의 네 줄**이다(`page-format.md`). 🔴 **반대 방향도 같다** — "안 쓰면 무관" 을 🟢 로 칠하지 않는다. 위험 쪽은 Generate 가 잡아 주지만 안전 쪽은 아무도 잡지 않는다.

6. 두 장을 넘게 고쳐야 하거나 합이 4만 자를 넘으면 **P8-A2 로 넘긴다**(한 회차에 다 하려다 깨뜨리지 않는다).

### P8-A2. 무인 실행 — 갱신 대기로 남긴다

**대표를 고쳐야 할 때**, 또는 **쪼개지지 않은 옛 통짜 페이지**일 때. 본문을 수정하지 않고 일지(P9-1)의 `갱신 대기` 절에 한 줄씩 적는다. 다음을 반드시 담는다.

| 담을 것 | 왜 |
| --- | --- |
| 티켓 키 · 페이지 링크 | 나중에 바로 열 수 있게 |
| **무엇이 바뀌었나** (새 댓글 요지 / 첨부 재배포 / **어느 속성 칸이 어떻게** 달라졌는지) | 이것이 있으면 ADF 반영이 몇 분이면 끝난다. **칸 이름을 적어 두면** 사람이 그 칸만 열어 고친다 |
| 티켓의 새 `갱신` 시각 · 댓글 수 | 다음 회차가 같은 변화를 두 번 올리지 않도록 |
| 며칠째 대기인지 | 묵은 것이 눈에 띄게 |

**대기로 남길 때는 `IMS-UPDATED`·`IMS-COMMENTS`·`IMS-GUIDE-REV` 마커를 고치지 않는다.** 마커를 올리면 다음 회차가 "이미 반영됐다"고 보고 변화를 잃는다 — **본문을 실제로 반영한 뒤에만** 마커를 올린다(P8-A1 은 반영하므로 올린다).

### P8-B. 사람이 있을 때 — ADF 왕복으로 반영

일지의 `갱신 대기` 를 보고 처리한다. 절차는 함정 표의 **"큰 페이지 보존 수정 = 크롬 ADF 왕복"** 이 정본이다. 바꿀 ADF 노드만 `splice` 하고 나머지는 건드리지 않는다. 끝나면 그 페이지의 마커를 올리고 일지의 대기 줄을 **완료로 표시**한다.

🔴 **사람이 적은 칸은 절대 덮지 않는다** — 표를 새로 만들지 말고 제자리에서 바꿀 칸만 바꾼다
(2026-11-06 실측: 270·255 의 `사내 진행 상태`·`사내 일감` 에 실제 값이 있었다).

| 보존할 것 | 어떻게 |
| --- | --- |
| 👤 `사내 일감` · 👤 `사내 진행 상태` | **행 노드를 그대로 다시 넣는다.** 글자를 옮기지 않으니 깨질 데가 없다 |
| ⚠️ `적용 대상` 의 **👤 둘째 줄**(저장소·브랜치·차종) | 이 칸은 **주인이 둘**이다. 첫 줄(MCU·제어기 단계)은 스킬이 갱신해도 되지만 **둘째 줄은 떼어내 그대로 다시 붙인다.** 칸을 통째로 새로 쓰면 사람이 적은 브랜치가 사라진다 |

**칸을 고칠 때는 칸 노드를 두고 `content` 만 바꾼다** — 노드를 새로 만들면 `attrs.colwidth` 가 날아가 표 폭이 무너진다(2026-11-07 실측, 5장).

📌 **마커 있는 옛 통짜 페이지는 지금 0장이다.** 손으로 쓴 5장은 마커가 없어 P6 대상이 아니고(P2-2),
그 다섯은 **§1 표만 11개로 맞춰 둔 상태**다 — 본문 분할은 지시가 있을 때만 하고, 🔴 **먼저 하자고 제안하지 않는다**(사용자 방침 2026-11-07).

### P8-F. 실패 처리

- 토큰 실패·스크립트 예외로 수집을 못 했으면 **페이지를 수정하지 않는다**(틀린 내용으로 덮는 것보다 낫다).
- 부모 `PATCH-INDEX` 영역의 마지막 실행만 실패로 바꾸고, 보고에 실패 단계와 오류 메시지를 적는다.
- Confluence 발행까지 실패하면 결과 보고에 그 사실을 분명히 적는다.

## P8N. 신규 페이지 생성 (구간 내 새 티켓)

P2-3 에서 나온 **구간 내 신규 + 페이지 없음** 티켓마다 수행한다.

1. 그 티켓에 **P3~P7 을 그대로 적용**한다 — 갱신과 조사 깊이가 같다. "새것이라 대충"은 없다.
2. ⭐ **대표를 먼저 만들고, 그 id 를 부모로 부록 4장을 만든다** (2026-11-07 개정). 순서가 거꾸로면 부록이 부모 `334594056` 바로 아래에 생겨 목록 트리에 섞인다.

| 순 | 호출 | 비고 |
| --- | --- | --- |
| ① | `createConfluencePage(spaceId="43843599", parentId="334594056", contentFormat="html", title="<대표 제목>")` | 이 시점의 본문은 **서두 + §1 속성·경과 + §2 + §3 + §4 + §5 + §6** 까지. 부록 링크는 아직 비어 있다 |
| ② | 부록 A~D 를 각각 `parentId=<대표 id>` 로 생성 | 제목은 고정 넷. 첫 문단에 **대표로 돌아가는 링크**, 푸터에 `IMS-PATCH-SUB` |
| ③ | ⭐ 대표의 **다섯 군데만** 채운다 — 📑 부록 표 네 칸 + 푸터 `IMS-SUBPAGES` 한 줄 | **크롬 ADF 왕복으로 그 다섯 노드만 갈아끼운다.** 본문을 다시 보내지 않는다(2026-11-07 실측: 대표가 약 20k 여서 통째 교체는 생길 이유가 없다). 크롬이 없는 세션이면 `getConfluencePage(contentFormat="html")` → 교체 → `updateConfluencePage` 로 돌리고, 그럴 때는 받은 html 을 그대로 돌려주고 다섯 군데만 끼워넣는다 |

> ⭐ **부록 링크는 📑 표 한 곳에만 둔다** (2026-11-07 실측, 199).
>
> 본문은 부록을 *"부록 B.2-1"* 처럼 **이름으로만** 가리키고 하이퍼링크를 걸지 않는다.
> 그래서 ② 가 끝나고 나서 대표에서 고칠 곳이 **네 칸 + 한 줄**로 고정된다.
>
> 🔴 **역으로 하면 본문을 다시 써야 한다.** 예전 이 칸은 §3·§4 에도 부록 링크를
> 뿌리라고 적었는데, 그러면 고칠 노드가 여럿이라 **통째 교체로 밀리고** 그러는 사이
> 글자가 깨진다(11-06 실측). 링크를 한 곳에 모으는 것은 보기 미비 보단 **고칠 면을
> 줄이는 설계**다.
>
> 📝 `IMS-SUBPAGES` 는 ① 에서 **`(부록 생성 후 채움)`** 이라고 쓰고 ③ 에서 그 문자열을
> 한 번에 치환한다. 표시자를 두면 **어디를 못 채웠는지 기계가 알아본다** — 부록을
> 만들다 중단된 회차도 다음 회차가 이어서 채울 수 있다(4-1).

3. 제목은 고정 설정의 규칙을 따른다 — 대표는 `<티켓키> <티켓 제목 그대로> — <핵심 모듈> <시작>→<끝>`, 부록은 고정 넷. 🔴 **부록 제목에 `Delivery_Patch` 를 넣지 않는다.**
4. **중복 방지**: 만들기 전에 P2-2 의 하위 페이지 목록에서 같은 티켓 키의 `IMS-PATCH-TICKET` 마커가 없음을 다시 확인한다. 응답이 잘려 생성 여부가 불확실하면 **다시 만들지 말고** 목록을 조회해 확인한다(아래 "발행 시 유의"). 부록도 같다 — 대표의 `depth=1` 자식을 조회해 이미 있는 문자를 건너뛴다.
4-1. 🔴 **부록을 만들다 중간에 실패하면 대표를 지우지 않는다.** 만들어진 것까지 두고, 일지에 "부록 N/4 까지 생성 — 나머지 미생성"을 적는다. 다음 회차가 빠진 문자만 채운다.
5. 티켓 하나가 실패하면 그 건만 건너뛰고 나머지를 계속한다. 실패는 일별 기록과 보고에 남긴다.
6. 신규 생성이 3건을 넘으면 **생성은 하되** 일별 기록 머리에 "신규 N건 — 조사 깊이를 확인해 주세요"를 적는다. 한 회차에 많이 쏟아지면 사람이 훑어볼 필요가 있다.

### P8N-1. 본문 크기 — 쪼갠 뒤의 선 ⭐ (2026-11-07 개정)

**기본이 바뀌었다 — 이제 쪼개는 것이 기본이다.** 2026-11-07 까지는 "한 패치의 모든 것이 한 장에"였고 7만에서 꼬리를 뺐다. 실측 결과 **MCP1001-198 한 장이 76,803자 · 표 20개**로 금지선에 닿았고, 매번 보는 15k가 안 보는 60k에 묻혔다. 그래서 **처음부터 대표 1장 + 부록 4장**으로 만든다(page-format.md "페이지 구성").

선은 **페이지 한 장마다** 적용된다.

| 선 | 자 | 성격 | 할 일 |
| --- | --- | --- | --- |
| 정상 | **~2.5만** | 🟢 | 쪼갠 하위의 정상 범위다(실측 13k~22k). 아무것도 하지 않는다 |
| 경고 | **4만** | 🟡 다시 보라 | 하위 한 장이 4만을 넘으면 그 절 안에 **중복이나 원문 복사**가 있을 가능성이 높다. 아래 ①로 대조한다. 걷어내도 4만이면 **그대로 쓴다** — 일지에 "하위 N 이 M자" 한 줄만 적는다 |
| 분할 | **6만** | 🟠 더 쪼갠다 | 그 하위를 **절 단위로 한 번 더** 가른다(예: `§3` → `§3.1 설정 변경` / `§3.2 Validation`). 제목에 절 번호가 박혀 있으므로 **교차 참조는 깨지지 않는다** |
| 금지 | **8만** | 🔴 넘기지 않는다 | 실측 최대가 **85,139자**(198 구판)다. 그 위는 **생성이 잘려 깨진 페이지가 올라간다** — 아무도 못 보고 지나간다. 쪼개도 8만이면 **생성 전에 멈추고 사람에게 알린다** |

**대표는 2만을 넘기지 않는다.** 넘으면 쪼갠 뜻이 없다 — 대표에 상세를 적고 있다는 신호이므로 그 상세를 해당 하위로 내린다.

**① 먼저 중복을 걷어낸다 (잃는 내용 0)**

🔴 **"짝 패치와 내용이 같다"를 믿지 않는다 — 행 단위로 대조한다.** 198 이 스스로 "§2 전체와 §3.3 은 APP 페이지와 내용이 동일하다"고 적어 놓았지만, **대조해 보니 60행 중 20행이 FBL 고유였다**(2026-11-06 실측).

| 절 | 행 | 같음 | 고유 |
| --- | --- | --- | --- |
| 2.1 버전 경로 | 5 | 4 | 1 |
| 2.2 중간 버전 | 7 | 5 | **2** (CPINFO-3954·3953 에 FBL 판단) |
| 2.3 결함·개선 | 16 | 13 | 3 |
| 2.4 결함 상세 | 11 | 6 | **5** |
| 2.5 자료 공백 | 7 | 2 | **5** |
| 3.3 Validation | 14 | 10 | **4** (ERR053310·311 근거) |

| 규칙 | 근거 |
| --- | --- |
| 🔴 **대조 없이 링크로 돌리지 않는다** | 198 을 통째로 링크로 바꿨다면 FBL 고유 분석 20행이 사라졌다. 표는 더 심하다 — 2.4 에서 6행만 빼면 `원인`은 남고 `현상`은 없어져 **읽을 수 없는 표**가 된다 |
| 대조 방법 | 양쪽 ADF 를 받아 행 텍스트를 정규화(공백·구두점 제거)해 상대 페이지 전문에 있는지 본다. **같은 행이 8할을 넘는 표만** 링크 후보다 |
| 🟢 **이 규칙은 새로 쓸 때 쓰는 것이다** | 이미 쓴 페이지를 사후에 줄이는 데는 거의 못 쓴다. **처음 쓸 때** 뒤쪽 페이지에 `§2 는 짝 패치 <키> 와 동일` + 링크로 시작하고, 다르다고 판단한 행만 적는다 |
| 겹치지 않는 절은 각자 끝까지 | 설정 변경·논의·빌드 이슈는 FBL·APP 이 다르다(설계 원칙) — 여기서는 줄이지 않는다 |

> 📌 **이미 있는 큰 페이지는 줄이지 않아도 된다.** 8만 금지선은 **한 번에 써서 만들 때**의 한계다. 이미 올라간 페이지의 갱신은 ADF 왕복이라 크기 제한이 없다 — 198 이 83,517자인 것은 **위험이 아니다.**

**② 그래도 넘치면 한 번 더 쪼갠다**

꼬리 절을 빼던 옛 방식은 **이미 근거 문서·첨부·링크가 부록 D 로 나가 있으므로 쓸 일이 없다.** 대신 **넘치는 부록을 소절 단위로 가른다.**

| 규칙 | 왜 |
| --- | --- |
| 부모는 **대표 페이지**, 깊이 2 를 유지한다 | 부모 `334594056` 바로 아래에 두면 목록 트리에 섞인다. 깊이 3 은 만들지 않는다 |
| 제목은 **부록 문자 + 소절 이름** (`· 부록 B-2 Validation`) | 절 번호를 제목에 박으면 축을 바꿀 때 또 어긋난다. 문자는 살아남는다 |
| 🔴 **`patch` 라벨·`IMS-PATCH-TICKET`·속성 매크로를 붙이지 않는다** | 붙으면 부모 목록 표에 줄이 늘고 갱신이 여러 번 돈다. 푸터는 `IMS-PATCH-SUB` 하나뿐이다 |
| 대표의 **📑 부록 표에 줄을 더하고 `IMS-SUBPAGES` 를 함께 고친다** | 가리키지 않는 부록은 아무도 못 찾는다. 본문 여러 자리가 아니라 **📑 표 한 곳**이다(P8N ③) — 그래서 여기도 고칠 곳이 한 칸이다 |
| 일지에 적는다 | "부록 B 가 N자라 B.4 를 따로 분리" — 왜 쪼갰는지가 남아야 다음에 기준이 된다 |

## P9. 부모 색인과 일별 기록

### P9-1. 일별 기록 페이지 ⭐

**이 페이지가 구간 사슬을 잇는다 — 빠뜨리면 다음 회차의 기준이 사라진다.**

제목 `eCoDY IMS 패치 모니터링 YYYY-MM-DD (요일)`, **부모 `380698635`**(일별 기록 묶음) 하위. 같은 날 이미 있으면 **새로 만들지 않고** 그 페이지에 `🔁 추가 실행 HH:MM` 블록을 끼워 넣는다.

담는 것:

| 절 | 내용 |
| --- | --- |
| 구간 | `WINDOW_START ~ WINDOW_END` (KST). 7일 초과면 "장기 공백 N일" |
| ⭐ **신규** | 이번에 **페이지를 만든** 티켓 — 키·제목·모듈·버전·**대표 링크 + 부록 A~D 링크**. 부록이 4장 다 만들어졌는지 명시한다(중간에 실패하면 "부록 N/4"). 0건이면 "없음" |
| ⭐ **갱신 대기** | **무인 실행의 본론이다**(P8-A). 변화가 생긴 페이지별로 — 티켓 키 · 페이지 링크 · **무엇이 바뀌었나**(새 댓글 요지, 첨부 재배포, **어느 속성 칸이 어떻게** 달라졌는지) · 새 `갱신` 시각 · 댓글 수 · **며칠째 대기**. 본문은 고치지 않았음을 전제로 쓴다 |
| ⭐ **갱신 완료** | **실제 반영한** 페이지 — 무인이 하위만 고친 것(P8-A1)과 사람이 ADF 왕복으로 한 것(P8-B) 둘 다. **어느 하위 몇 번을 왜 고쳤는지** + 판 번호. 이때만 대표의 마커를 올렸다 |
| 건너뜀 | 변화 없어 손대지 않은 티켓 — 키만 나열 |
| **페이지 없는 과거 티켓** | 구간 밖 백로그. 키·제목·상태·댓글 수. 🔴 **조용한 기록이다 — 권유 문장을 붙이지 않는다**(사용자 방침 2026-11-07). "다음 회차가 할 일" 에도 넣지 않는다 |
| 공백·실패 | 403/404 로 못 본 자료, 실패한 단계와 오류 |

페이지 끝에 마커를 **글자 그대로** 남긴다 — 틀리면 다음 회차 구간이 어긋난다.

```
IMS-WINDOW-END-UTC: <WINDOW_END ISO>
IMS-RUN: 신규 N(하위 N장) · 갱신대기 N · 갱신완료 N(하위 N장) · 건너뜀 N · 실패 N
```

변화가 0건이어도 **마커를 위해 페이지는 만든다**(내용은 "변화 없음" 한 줄).

### P9-2. 부모 색인 — 영역 한 곳만

부모 `334594056` 의 **`PATCH-INDEX-BEGIN` ~ `PATCH-INDEX-END` 사이만** 다시 쓴다. 영역 밖은 받은 html 그대로 보존한다.

> ⭐ **패치 목록 표는 건드리지 않는다.** 부모의 **페이지 속성 보고서 매크로**가 각 패치 페이지의 속성을 모아 자동으로 그린다. 페이지가 생기거나 속성이 바뀌면 표가 알아서 따라온다 — 스킬이 매일 고칠 표가 없다. 매크로 `<div>` 를 실수로 지우지 않도록, 받은 html 에서 `data-extension-key="detailssummary"` 블록이 살아 있는지 확인한 뒤 send 한다.

영역에 담는 **최소**는 네 줄이다: 마지막 실행 시각 · 결과(신규/갱신/건너뜀/실패) · 추적 기준선 · 탐지 프로젝트 목록.

⚠️ **실제로는 더 많다** — 2026-11-07 기준 **열 줄**(위 넷 + 구간 · 페이지 구성 · 속성 항목 · 복구 이력 · 백로그 · 손으로 쓴 장 상황). 그래서 **매 회차 전부를 다시 짓지 않고 돌아진 칸만 고친다.**

🔴 **상황을 설명하는 칸은 일이 진행되면 거짓이 된다 — 같은 회차에 같이 고친다.**

| 새 페이지를 만들었으면 | 함께 고칠 칸 |
| --- | --- |
| ⭐ 그 티켓이 **백로그 목록에 있었다면** | **백로그 칸의 건수를 줄이고** "✅ `<키>` 는 언제 만들었다" 를 적는다(2026-11-07 실측: 199 를 만들어 **12건 → 11건**). 줄이지 않으면 부모가 **이미 만든 티켓을 아직 없다고 말한다** |
| 그 티켓에 **짝이 있었다면** | 백로그 칸에 짝을 가리키는 문장이 있으니 그것도 같이 고친다 |
| 새 규격이 **처음으로 적용된 페이지**면 | 페이지 구성 · 속성 항목 칸의 *"아직 안 쓰는 페이지"* 문장이 거짓이 되었는지 본다 |

> 📝 **이것을 두 번 놓칠 뻔했다** (2026-11-07). 속성 20개 → 11개 개정 후엔 부모의
> *"속성 11개를 아직 안 쓰는 페이지"* 줄이 그 날 고친 다섯 장 덕분에 거짓이 됐고,
> 199 를 만들자 백로그 12건이 거짓이 됐다. 둘 다 **그랩 가서 다시 읽어봐서야** 찾았다.
> ⇒ **생산물을 만들기 전에 부모에서 그 티켓 키와 숫자를 `grep` 한다.**

⭐ **부모 수정은 ADF 왕복이 기본이다.** 돌아진 칸만 `content` 를 갈아끼우면
보고서 매크로를 **직렬화조차 하지 않는다** — 이 자리가 하루에 두 번 깨진 뒤
얻은 결론이고, v21·v22 는 그 방식으로 한 번도 깨지지 않았다.

실패한 회차에도 **이 영역만은 갱신한다**(P8-F) — 일지조차 못 만든 날 "오늘 안 돌았다"가 남는 유일한 자리다.
