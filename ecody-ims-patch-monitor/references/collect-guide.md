# 수집 요령 — 티켓에서 연결된 전부를 찾아내는 방법

`SKILL.md` P4·P5 의 정본. 순서대로 수행한다. **§2 가 가장 중요하고 가장 잘 빠진다.**

스크립트는 모두 `<저장소>\ecody-search\scripts\` 에 있다. 토큰이 세션에 없으면 명령 앞에 붙인다:

```powershell
$env:ECODY_IMS_TOKEN=[Environment]::GetEnvironmentVariable('ECODY_IMS_TOKEN','User')
$env:ECODY_ECM_TOKEN=[Environment]::GetEnvironmentVariable('ECODY_ECM_TOKEN','User')
```

`python -I` 는 쓰지 않는다 — 스크립트 폴더가 `sys.path` 에서 빠져 `_ecody_common` import 가 깨진다.

## §1. 티켓에 링크로 걸린 것

`ims_api.py read` 출력의 `--- 연결` 절을 본다.

| 연결 종류 | 무엇인가 | 어떻게 처리 |
| --- | --- | --- |
| `Relates` + 유형 `Information` + 제목이 `[수평전개]` 로 시작 | **과제 사본**. 내용은 원본 복사본이고 본문 맨 위에 `수평전개 티켓 : CPINFO-xxxx` 가 있다 | 사본에서 **원본 키를 뽑아 원본을 읽는다**. 사본은 상태·라벨·담당자 이력만 쓴다 |
| `Inspection` (릴리즈 노트 ↔ 수평전개) | 릴리즈 노트와 수평전개를 잇는 링크 | 양방향으로 따라간다 |
| `상위` / `하위` | 릴리즈 노트와 `sub-task_SWCR` | §3 |

> ⚠️ **짝 패치(APP↔FBL)는 연결에 없다** (2026-11-05 실측). 두 딜리버리 티켓은 서로를 링크하지 않는다. **수평전개 사본의 연결 목록**에 APP·FBL 양쪽이 걸려 있고, 그것이 짝을 찾는 유일한 경로다. 짝을 찾으면 키·제목·상태만 적고 본문은 그 티켓의 페이지가 담당하되, **설정 변경이 같을 거라고 가정하지 않는다** — 실측에서 FBL 9건 / APP 5건이고 거의 겹치지 않았다.

> ⚠️ **댓글이 가리키는 다른 과제 티켓도 따라간다.** "`<다른과제>-NNN` 과 같은 방법으로 조치" 같은 문구가 나오면 그 키를 읽어 본다. 우리 과제가 아니면 **`HTTP 403 "명시된 이슈를 볼 권한이 없습니다"`** 다. 그때는 §2.5 에 "조치 내용이 우리 기록에 없음 · 작업자나 커밋 이력으로 확인 필요" 를 적는다 — 안 적으면 같은 문제가 재발했을 때 처음부터 다시 헤맨다.

수평전개 원본은 길다. **`--max 20000` 이상** 준다(실측 8,713자).

```powershell
python ims_api.py read CPINFO-4110 --max 20000 --out <스크래치패드>\hd.txt
```

### 수평전개 원본에서 뽑을 12항목

결함마다 `[이슈N]` 블록으로 반복된다. **이 12 항목이 페이지 §2.4 표의 행이 된다.**

| # | 항목 | 페이지에 왜 필요한가 |
| --- | --- | --- |
| 1 | 현상 (Defect Description) | 무엇이 잘못되나 |
| 2 | 발견방법 (How to find) | `내부 테스트` 와 `협력사 테스트` 는 무게가 다르다 |
| 3 | 원인 (Defect Causes) | 우리 설정이 해당되는지 판단하는 근거 |
| 4 | 재현조건 및 시나리오 | **실기 검증 TC 로 그대로 쓸 수 있다** |
| 5 | 재현 빈도 | `항상` 인지 `간헐적` 인지 |
| 6 | 복구 방법 | `없음` 이면 심각도가 올라간다 |
| 7 | **수평전개 검토 대상** | ★ 우리 제어기가 대상인지 가리는 조건. 보통 `<모듈> <버전> 이하` + 기능 조건 |
| 8 | 관련 ES 사양 | 사양 추적 |
| 9 | 플랫폼 개선 내용 | 패치가 실제로 무엇을 바꿨나 |
| 10 | **FBL impact** | ★ FBL 2.0/3.0 별 영향. 짝 패치가 필요한 이유의 근거 |
| 11 | **R40/R44 impact** | ★ 우리 R 버전 해당 여부 |
| 12 | Comment | HAE 가 "이 점을 고려해 판단하라"고 단 조건 |

## §2. 릴리즈 노트 체인 — 시작·중간·끝 버전 전부 ★★

티켓에는 **링크가 없다.** 직접 찾아야 한다. 티켓 본문의 `<모듈> <시작버전> → <끝버전>` 이 입력이다.

### 2-1. 검색 형식 (실측으로 검증된 것만)

```powershell
# 모듈 기준 버전의 HF 전부 — 이것이 주력이다
python ims_api.py search --queries <q.json> --per-query 40 --out <...>
```

`q.json` 예 (모듈 `Dcm_R44`, 기준 버전 `2.1.1.0`):

```json
[{"tag":"HF전부", "jql":"summary ~ \"Dcm_R44-2.1.1.0_HF*\" ORDER BY created ASC"},
 {"tag":"베이스",  "jql":"summary ~ \"Dcm_R44-2.1.1.0\" ORDER BY created ASC"}]
```

| 쿼리 형태 | 실측 결과 | 쓸 수 있나 |
| --- | --- | --- |
| `summary ~ "Dcm_R44-2.1.1.0_HF*"` | **27건** (노트 + 하위작업 + 수평전개가 한 번에) | ✅ **주력** |
| `summary ~ "Dcm_R44-2.1.1.0_HF4"` | 9건 (그 버전만) | ✅ 특정 버전 확인용 |
| `summary ~ "Dcm_R44-2.1.1.0"` | 13건 | ✅ 베이스 버전 확인용 |
| `summary ~ "Dcm_R44"` | 🔴 **0건** | ❌ |
| `issuetype = CP_ModuleRelease AND summary ~ "Dcm_R44"` | 🔴 **0건** | ❌ |

> ⚠️ **왜 모듈명만으로는 0건인가** — Jira 의 텍스트 검색은 토큰 단위로 색인한다. `Dcm_R44-2.1.1.0_HF4` 가 하나의 토큰으로 들어가 있어 앞부분 `Dcm_R44` 만으로는 매칭되지 않는다. **전체 버전 문자열을 쓰거나 와일드카드 `*` 를 붙여야 한다.** `issuetype` 조건을 같이 걸어도 0건은 0건이다 — 조건 문제가 아니라 검색어 문제다.

> ⚠️ **상태 조건에 한글을 쓰지 않는다.** `status not in (닫힘, 완료, Reject)` → `HTTP 400 '닫힘' 값이 'status' 필드에 존재하지 않습니다`. 상태로 거르지 말고 전부 받아 결과에서 가린다.

### 2-2. 버전 경로 만들기

검색 결과에서 **유형이 `CP_ModuleRelease` 인 것만** 골라 생성일 순으로 늘어놓는다. 그중 **시작 버전보다 뒤, 끝 버전까지**를 전부 체인에 넣는다.

```
티켓:  Dcm_R44  2.1.1.0_HF2 → 2.1.1.0_HF4

검색 결과의 CP_ModuleRelease (생성일 순)
  CPINFO-3674  Dcm_R44-2.1.1.0        2026-xx   ← 시작보다 앞 → 제외
  CPINFO-3739  Dcm_R44-2.1.1.0_HF1    2026-xx   ← 시작보다 앞 → 제외
  CPINFO-3846  Dcm_R44-2.1.1.0_HF2    2026-05-12  ← 시작점 (현재 형상)
  CPINFO-3952  Dcm_R44-2.1.1.0_HF3    2026-06-26  ★ 중간 — 티켓에 없다
  CPINFO-4051  Dcm_R44-2.1.1.0_HF4    2026-07-14  ← 목표
  CPINFO-4xxx  Dcm_R44-2.1.1.0_HF5    (이후)      ← 범위 밖 → 참고로만
```

- **시작점도 읽는다.** 현재 형상이 무엇인지 알아야 차이를 말할 수 있다.
- **범위 밖의 다음 버전(HF5)도 제목만 확인한다.** "이번 범위 아님"을 페이지에 적어 두면 다음 패치 때 바로 안다.
- 모듈이 여러 개면 **모듈마다 체인을 따로** 만든다.
- 버전 체계가 `_HF` 가 아닌 경우(`2.1.1.0` → `2.1.2.0` 처럼 마이너가 오르는 경우)는 `summary ~ "<모듈>-2.1.*"` 로 넓혀 받고 같은 방식으로 정렬한다.

### 2-3. 릴리즈 노트 본문에서 뽑을 것

본문은 `ISSUE TYPE | DESCRIPTION` 표가 반복되는 구조다. `ISSUE TYPE` 은 `improvement` · `activity` · `bug` 세 가지다.

| ISSUE TYPE | 어떻게 다루나 |
| --- | --- |
| `improvement` | 본문에 상세가 있다. **`Configuration URL` 이 채워진 것은 설정에 닿는다** — 페이지에 경로를 그대로 적는다 |
| `activity` | 주석·테스트·컴파일 대응. 한 줄로 묶어도 된다 |
| `bug` | 보통 `BUG 내용은 LinkedIssue 와 SubTask 로 연결되어 있는 내용을 확인하시기 바랍니다` **한 줄뿐이다** → §3 으로 간다. 단 **노트마다 다르다** — 부모 본문에 결함 상세를 다 적어 둔 노트도 있다(실측: 같은 모듈의 HF2 노트). **반드시 본문을 끝까지 확인한다** |

각 항목에서 뽑는 필드: `Target MCU` · `Related Functionality / Configuration URL / Related API` · `Impact on ASW (Configuration / APP Logic)` · `Detailed Changes [KR]` · `Dependent module version`.

본문이 길어 잘릴 수 있다. `(이하 N자 생략)` 이 보이면 **`--max` 를 늘려 다시 읽는다**(실측: 결함 상세가 있는 노트는 10,000자를 넘는다).

## §3. 하위작업과 사전 공지

```powershell
python ims_api.py read CPINFO-4052 CPINFO-4053 ... --max 2600 --out <...>
```

- 유형은 `sub-task_SWCR`. **본문이 비어 있는 것이 정상이다** (실측: 12건 전부 비어 있었다).
- 비어 있으면 **제목을 결함 목록으로 쓰고**, 상세는 §1 수평전개에서 찾는다.
- **수평전개에도 없는 결함은 "자료 없음"으로 페이지에 명시한다.** 실측: HF4 결함 6건 중 수평전개에 있는 것은 2건뿐이었다. 나머지 4건은 오토에버가 적어 두지 않았다 — 더 찾아도 없다.
- 첨부(스크린샷)만 붙어 있고 설명 글이 없는 경우도 있다. 첨부 존재를 적되 내용을 추측하지 않는다.
- 사전 공지(`CPD_ModulesPreNotice`)도 보통 본문이 없다. 존재 사실과 날짜만 적는다.

### 4-1. IM (Integration Manual) — 가장 가치가 높다 ★★

```json
[{"tag":"IM","cql":"title ~ \"Dcm\" and title ~ \"IM\" and space = mclassicfaq"}]
```

제목이 `[IM] <모듈> - R44` 인 페이지가 목표다 (`[IM] Dcm - R44` 처럼). **한 페이지에 모든 버전이 절로 들어 있다** — 3만 자가 넘으므로 `--max 60000` 으로 받아 파일에 쓰고, 절 번호로 필요한 부분만 꺼낸다.

```bash
grep -n "2\.1\.1\.0_HF[234]" im_dcm.txt      # 버전 절의 줄 번호 찾기
sed -n '<시작>,<끝>p' im_dcm.txt              # 그 절만 꺼내기
```

IM 구조와 뽑을 것:

| IM 절 | 내용 | 페이지 어디에 쓰나 |
| --- | --- | --- |
| `2.1.1.x` 모듈 추가 | `SCons.arxml` · `EcucValueCollection` · `Ecud_EcuM.arxml` · `Ecud_Rte.arxml` 등의 **표준 설정** | §3.1 — HAE 안내와 **대조**한다. IM 에만 있는 항목(예: `EcuMShutdownCause` 의 `ECUM_CAUSE_DCM`)을 찾아낸다 |
| **`2.4.x` 모듈 일반 설정** | ★★ `<모듈>General` 의 **표준 설정값 전체** (예: `DcmDemIntegrated: False`) | §1 표 + **ERR 예측의 재료** (아래 ⭐) |
| `2.4.x` Configuration For Resolving Error | 에러 해소용 수동 설정 | §3.1 참고 |
| **`4.1.1.x` 모듈 버전별 변경사항** | ★★ 버전마다 `Dependency`(의존 모듈 버전) · **`Validation 신규`(ERR 코드 전체)** · `Validation 변경` · `설정 신규` · `NOTE` | §3.2 의존성 표, **§3.3 ERR 코드 표** |

> ⭐ **IM 은 FBL·APP 용이 따로 있을 수 있다.** 실측: `[IM] Dcm - R44`(모듈 공통, 버전별 변경사항) 와 `[Dcm][R44] IM - 1. FBL3.0 SWP의 Dcm 설정`(FBL 전용, 표준 설정값) 이 별개 페이지였다. **FBL 패치면 FBL 전용 IM 을 반드시 함께 찾는다** — DefineOption 이름이 거기에만 있다.

> ⭐ **표준 설정값 × ERR 조건 = 예측.** `2.4.x` 의 표준 설정값과 `4.1.1.x` 의 새 Validation 조건을 나란히 놓으면 **적용자가 만날 에러를 미리 지목할 수 있다.** 실측: `ERR053310`·`ERR053311` 의 조건이 "`Used=true` + `DcmDemIntegrated=false` + 사용자 함수 없음" 인데 **FBL 표준이 `DcmDemIntegrated: False`** 였다 → 페이지에 "이 FBL 에서 걸릴 가능성이 높다, 근거는 이것" 을 적었다. **"가능성이 높다"로 쓰고 "걸린다"로 쓰지 않는다** — 실제 프로젝트 설정은 확인하지 않았기 때문이다.

> **ERR 코드 목록이 이 스킬의 가장 큰 산출물이다.** 티켓·릴리즈 노트에는 "Validation 추가" 라고만 적혀 있고 **코드 번호가 없다.** IM 에만 있다. 적용자는 Generate 후 처음 보는 `ERR0532xx` 를 만나는데, 이 표가 있으면 "패치가 깨뜨린 것이 아니라 원래 틀렸던 것이 드러난 것"임을 바로 안다. 🔴 단 페이지에는 "뜨는 것이 정상"으로 쓰지 않고 ERR 마다 원인 → 대응 → 완료 기준을 붙인다 (`page-format.md` 문장 규칙 2).

> ⚠️ **HAE 안내의 IM 절 번호를 그대로 믿지 않는다.** IM 은 장 번호 체계를 재편한 적이 있다(실측: 안내의 `5.1.1.29`·`3.1.1.5` → 현재 `4.1.1.28`·`2.1.1.5`). 번호가 아니라 **내용으로 찾고**, 어긋났으면 페이지 §5 에 "안내 번호 → 현재 번호" 를 적는다. 적용자가 문서를 못 찾아 헤매는 주된 원인이다.

### 4-2. 통합필수점검 IA / VC

```json
[{"tag":"IA","cql":"title ~ \"IA-079\""}]
```

댓글은 "FAIL 목록 #5·#7 해당" 처럼 번호만 말한다. 문서를 읽어 **등급과 조건**을 확인한다.

| 등급 | 뜻 | 페이지에 어떻게 쓰나 |
| --- | --- | --- |
| 🔴 Error | 설정값 오류, 즉시 수정 | "수정 필요" |
| 🟡 Advisory | 권고 (예: MCAL 버전 업데이트 권장) | **"권고"임을 명시한다.** Error 와 섞어 적으면 과도한 대응을 부른다 |
| 🟣 Exception | Pre-Condition 미충족으로 검증 불가 | 설정 오류와 구별해 적는다 |

문서의 `배경 및 목적` · `적용 범위`(MCU·플랫폼·뱅크·필수 모듈) · `해결 방법` · 연결된 조치 가이드 목록도 뽑는다. **적용 범위에서 우리 MCU 가 제외 대상인지 먼저 본다.**

### 4-3. SAG — 설정 변경의 실제 근거

설정 변경 안내가 가리킨 SAG 를 제목으로 찾아 **해당 절이 우리 MCU 를 대상으로 하는지** 확인한다. SAG 는 MCU 별로 하위 절이 갈린다(예: `3.3.1.1 CYTXXX` / `3.3.1.2 S32K31X` / `3.3.1.3 TC3XX`). TC3XX 처럼 "변경 없음" 이거나 반대로 "추가하면 컴파일 에러" 인 경우가 있다.

또한 그 SAG 가 **이 패치 전용 문서가 아닐 수 있다.** 실측: `__GHS__` 근거로 가리킨 SAG 는 Attempt Counter 기능 통합 가이드였고, 그 문서에는 이 패치와 무관한 별도 요구(integration_Pfls 최소 버전, PFEE 영역 제약 등)가 잔뜩 있었다. **공유하는 절만 근거로 쓰고, 문서 전체가 패치 범위인 것처럼 적지 않는다.**

### 4-4. 404·403 처리와 우회로

ECM 페이지가 `ERROR HTTP 404 {"authorized": false, ...}` 로, IMS 티켓이 `HTTP 403` 으로 올 수 있다 — 계정 권한 문제다.

- 추측으로 메우지 않는다.
- 페이지 §2.5·§5 에 **식별자 · 상태코드 · "권한 요청 필요"** 를 적는다.
- 푸터 마커 `ECM-MISSING`·`IMS-MISSING` 에 그 id 를 남긴다.

**우회로 두 가지** (2026-11-05 실제로 통했다):

1. **배포 zip 안의 `Doc` 폴더.** HAE 안내: "문서 산출물은 압축 파일 내 `<차종>_<버전>_<구분>\Doc` 에 있습니다 — 짝 패치 티켓에서도 동일 경로". ECM 권한이 막혔을 때 가장 빠르다.
2. **같은 내용의 다른 ECM 페이지를 제목으로 검색.** 당사가 실제로 쓴 예: `[C Studio][R44] 하모나이즈 Remove Invalid Configurations 옵션 > 3.11 EcuM`, FBL 전용 Dcm IM, `[IM] Crypto_76_HaeModule - 2.X`, `[IM] OsImp_S32K3xx - R44`, `[IA-014]`.

페이지에는 이 우회로를 **적어 둔다** — 다음 사람이 권한을 기다리며 멈추지 않게 한다.

### 4-5. 설정 변경 표에 섞여 오는 점검 항목

HAE 설정 변경 표의 마지막 행에 `ValidationChecker 검증항목` 이 끼어 있을 수 있다(실측: `[IA-086] ComMSynchronousWakeUp`). **이것은 패치 설정이 아니다.**

- HAE 가 직접 설명한 성격: "**HwObject 관련 설정 변경 권장 사항은 모듈 업데이트와는 무관하다.** HAE 에서 모듈 배포될 때마다 잠재적 이슈가 될 만한 항목들을 함께 공유해 드리고 있다."
- 따라서 페이지에서는 **설정 변경 표와 분리된 별도 블록**으로 적는다.
- 그 점검 문서를 읽어 **등급**을 확인한다. 실측: IA-086 은 🟡 Advisory 이고 지침도 "false 로 바꿔라" 가 아니라 "**프로젝트에 맞추어 값을 정한다**" 였다 — HAE 안내만 보면 "false 로 고쳐야 하는 일" 로 오해한다.

## §5. 수집 후 자기 점검

페이지를 쓰기 전에 아래를 센다. 하나라도 비어 있으면 추적이 덜 끝난 것이다.

| 확인 | 기준 |
| --- | --- |
| 버전 경로 | 시작·중간·끝이 **전부** 체인에 있나. 중간이 0 개라면 정말 연속 버전인지 검색 결과로 확인했나 |
| 결함 | 하위작업 전체를 열었나. 상세가 있는 것과 없는 것을 **나눠** 적었나 |
| 수평전개 | 원본(CPINFO)을 읽었나 (사본만 읽고 끝내지 않았나). 12항목을 다 뽑았나 |
| **짝 패치** | 수평전개 **사본의 연결**에서 짝을 찾았나 (딜리버리 티켓끼리는 안 걸려 있다) |
| **다른 과제 티켓** | 댓글이 가리키는 키를 읽어 봤나. 403 이면 §2.5 에 적었나 |
| ECM | IM 버전 절을 열었나. **ERR 코드 목록을 가져왔나.** FBL 패치면 **FBL 전용 IM** 도 찾았나 |
| **ERR 예측** | IM 표준 설정값과 ERR 조건을 대조해 **걸릴 만한 것을 지목**했나 |
| 점검 | IA/VC 문서의 **등급**을 확인했나. 설정 변경 표에 섞인 점검 항목을 **떼어** 적었나 |
| 댓글 | 긴 문답의 **결론**을 뽑았나. "끝난 일"임을 적었나. HAE 가 "기대됩니다" 로 답한 것을 확인 필요로 올렸나 |
| 변경 이력·첨부 | 첨부 재배포가 있었나. **당사 첨부와 HAE 배포본을 구별**했나. **빌드 로그에서 실패 원인을 꺼냈나** |
| 자료 없음 | §2.5 에 **"없다"를 명시**했나 |
| 우회로 | 권한이 막힌 문서가 있으면 **zip 내 `Doc` 폴더·대체 ECM 페이지**를 적었나 |
