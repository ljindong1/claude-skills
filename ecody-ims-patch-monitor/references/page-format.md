# 패치 페이지 형식

`SKILL.md` P7 의 정본. 부모 `334594056` "[Autoever] Patch 티켓" 아래 패치 티켓 하나당 **대표 1장 + 부록 4장**이다 (2026-11-07 2차 개정 — 한 장 → 길이 분할 → **축 교체**).

**이 페이지를 읽는 사람은 패치를 적용할 사람이다.** 목적은 요약이 아니라 **누락 없는 적용**이다. 그래서 ERR 코드·의존 모듈 버전·설정 경로·재현 시나리오처럼 **그대로 복사해 쓸 값**을 담는다. 반대로 결함 설명을 길게 늘여 쓰지 않는다.

> 🔴 **마크업은 `confluence-writing` 스킬이 정본이다 — 먼저 읽는다.**
>
> 이 문서는 **어느 절에 무엇을 담고 표를 몇 열로 할까**를 정한다. **어떤 html 로 쓸까**는 `confluence-writing`(+ 그 `references/formatting-cheatsheet.md`)이 정한다. 아래 각 절의 `2열 표(250/510)` 같은 표기는 **폭 숫자**이고, 그 숫자를 적용하는 방법은 이것이다:
>
> ```html
> <table data-layout="default" data-display-mode="fixed">
>   <thead><tr><th data-colwidth="250"><p><strong>…</strong></p></th>
>              <th data-colwidth="510"><p><strong>…</strong></p></th></tr></thead>
>   <tbody><tr><td data-colwidth="250"><p>…</p></td>
>              <td data-colwidth="510"><p>…</p></td></tr></tbody>
> </table>
> ```
>
> **모든 행의 모든 셀**에 `data-colwidth` 를 넣는다. **`<colgroup>`·`<col>` 은 쓰지 않는다** — create/update 모두 저장 시 서버가 지워서 표가 균등 폭으로 렌더링된다. 2026-11-06 실측: `<colgroup>` 으로 쓴 페이지의 표 19개가 전부 폭을 잃었다. 폭 합계 기준은 **760px** 이다.
>
> 그 밖의 규약도 그대로 따른다 — 본문은 **H3** 부터(H1·H2 금지), 수정은 **직전 fetch 후 전체 교체**, 첨부가 있으면 **html 왕복**.

## 제목

```
<티켓키> <티켓 제목 그대로> — <핵심 모듈> <시작버전> → <끝버전>
```

예: `MCP1001-199 [R44][BJ/TPMS][APP][V.2.1.11] Delivery_Patch — Dcm_R44 2.1.1.0_HF4`

모듈이 여러 개면 가장 영향이 큰 것만 쓰고 `외 N건` 을 붙인다. **제목은 한 번 정하면 바꾸지 않는다** — 바꾸면 링크가 깨지고 색인이 어긋난다.

**부록 페이지 제목은 넷으로 고정이다** (2026-11-07 2차 개정). 자유 제목을 쓰지 않는다 — 고정이어야 P8 이 "바뀐 것 → 고칠 페이지"를 찾을 수 있다.

```
<티켓키> · 부록 A 변경의 뿌리
<티켓키> · 부록 B 우리 형상 변경 지도
<티켓키> · 부록 C 막힌 것과 끝난 논의
<티켓키> · 부록 D 근거 문서와 첨부
```

🔴 **부록 제목에 `Delivery_Patch` 가 들어가면 안 된다** — 부모 목록 표가 제목으로 수집하므로 한 티켓이 5줄로 뜬다.

📌 **절 번호(`§2`·`§3`)를 제목에 박지 않는다.** 1차 개정은 그렇게 했는데 축을 바꾸자 네 제목이 전부 어긋났다. **문자(A~D)는 담는 내용이 바뀌어도 살아남는다.**

## 페이지 구성 — 대표 1장 + 부록 4장 ⭐ (2026-11-07 2차 개정)

**축을 바꿨다.** 1차 개정(같은 날)은 76,803자 한 장을 길이로 쪼갠 것이었고, 그때 절 구성은
`§2 변경내역 / §3 설정 / §5 문서 / §7 첨부` — **자료를 어디서 읽었나** 순서였다. 사용자 지적이
정확했다: *"객관성은 있는데 의미 없는 나열이고, 무엇을 말하려는지 모르겠다."*

원인은 셋이었다.

| 증상 | 원인 |
| --- | --- |
| 읽어도 할 일이 안 보인다 | 구조가 **수집 창고의 목차**였다. 독자의 질문은 *왜 → 어디 → 어떻게 → 확인* 인데 그 축으로 한 번도 걷지 않았다 |
| 인과가 끊겨 있다 | `현상 → 모듈 수정 → 우리 arxml 의 어느 컨테이너 → Generate → 실기 확인` 이 네 장에 흩어져 **독자가 재조립**해야 했다 |
| 우리 일이 아니라 HAE 의 물건으로 읽힌다 | 전부 `HAE 안내 ①~⑨` 로 적었다. 엔지니어가 실제로 여는 것은 **파일**이다 — `Ecud_EcuM.arxml`, `Bswmd_BswM.arxml`, `SCons.arxml` |

그래서 **대표는 하나의 논증**으로, **부록은 그 논증의 근거**로 다시 나눈다.

```
[Autoever] Patch 티켓 (334594056)              ← 부모. 보고서 매크로가 label=patch 수집
└ <티켓키> <티켓 제목> — <모듈> <시작>→<끝>      ← 대표 (속성 11개 · 마커)
   │  서두 6문장 · §1 개요(속성·경과) · §2 왜 받나 · §3 우리 형상에 닿는 범위
   │  · §4 작업 순서 · §5 끝났다고 말하는 기준 · §6 아직 모르는 것
   ├ <티켓키> · 부록 A 변경의 뿌리                ← 왜 바뀌었나
   ├ <티켓키> · 부록 B 우리 형상 변경 지도        ← ★ 실제 작업이 일어나는 장
   ├ <티켓키> · 부록 C 막힌 것과 끝난 논의        ← 갱신이 거의 여기만 생긴다
   └ <티켓키> · 부록 D 근거 문서와 첨부           ← 참조
```

| 페이지 | 답하는 질문 | 담는 절 | 언제 보나 |
| --- | --- | --- | --- |
| **대표** | **무엇을 왜 어떤 순서로 하나** | 서두 · §1 개요 · §2 왜 · §3 범위 · §4 순서 · §5 완료 기준 · §6 모르는 것 | **매번** |
| 부록 A `변경의 뿌리` | **왜 바뀌었나** | A.1 결함·재현 · A.2 버전 경로 · **A.3 중간 버전** · A.4 나머지 변경 · A.5 의존 · **A.6 자료 공백** | 적용 전 1회 |
| 부록 B `우리 형상 변경 지도` | **우리 파일의 어디를 고치나** | B.1 파일 목록 · B.2 파일별 변경 · B.3 harmonize·Generate · **B.4 새 Validation** · B.5 닿지 않는 것 | 적용 중 계속 |
| 부록 C `막힌 것과 끝난 논의` | **막히면 어떻게 하나** | C.1 끝난 논의 · C.2 막힌 것 · C.3 문서 권한 | 막혔을 때 |
| 부록 D `근거 문서와 첨부` | **원본은 어디 있나** | D.1 HAE 문서 · D.2 첨부 · D.3 링크 · D.4 용어 | 참조 |

### 축이 바뀌면 같은 사실이 이렇게 달라진다

**버리는 쓰기 (출처 축)** — 아홉 줄을 읽고 "어느 파일을 여나"를 독자가 재조립해야 한다.

```
§3.1 설정 변경 항목
 ① DefineOption 에 DCM_FOTA_USED_FBL 추가     ← FBL IM 2.3.1
 ② Ecud_EcuM.arxml ListOne 에 Dcm_Init        ← Dcm IM 2.1.1.5
 ⑥ SCons.arxml ShortName Swcd_Bsw_NvM         ← NvM IM 2.1.1.3
 ⑨ OsImp_init → OsImp_Init                    ← IA-014 #2
```

**쓰는 쓰기 (형상 축)** — 파일을 열고 그대로 따라갈 수 있다.

```
Ecud_EcuM.arxml — 네 군데를 고친다
 1. ListOne 에 Dcm_Init 추가 · Index 는 프로젝트 순서(IM 예시 42 를 쓰지 않는다)
      왜   : Dcm 초기화 주체가 바뀌었다          ← Dcm IM 2.1.1.5
      함정 : R4.4.0 이라 harmonize 가 지우지 않는다 ← C Studio RIC 3.11
 2. OsImp_init → OsImp_Init (대소문자)          ← IA-014 #2 🔴 Error
 ...
 ⚠️ 이 파일을 건드렸으면 harmonize 를 EcuM → BswM 순서로 돌린다 (B.3)
 🔴 안 하면 : OsImp 초기화 누락 — 빌드는 되고 런타임에 터진다
```

**차이는 정보량이 아니라 조립 상태다.** 같은 사실을 담되 **독자가 조립하지 않게** 쓴다.

### 지키는 규칙 여섯

| 규칙 | 왜 |
| --- | --- |
| 🔴 **§1 속성 매크로 11개는 대표에만 둔다** | ① 부모의 보고서 매크로가 그 값을 모아 목록 표를 그린다 — 대표에서 빠지면 **그 줄의 열이 통째로 빈칸**이 된다. ② `사내 진행 상태`·`적용 대상`·`사내 일감` 은 👤 사람 칸이라 한 곳에만 있어야 한다 (사용자 확인 2026-11-07) |
| 🔴 **부록 제목에 `Delivery_Patch` 를 넣지 않는다** | 부모 목록 표의 수집 조건이 제목이다 — 넣으면 **한 티켓이 표에 5줄**로 뜬다 |
| ⭐ **부록은 문자(A~D)로 부른다** | 절 번호(`§2`·`§3`)를 부록 제목에 박으면 **축을 다시 바꿀 때 또 어긋난다**. 문자는 담는 내용이 바뀌어도 살아남는다. 교차 참조는 `A.3`·`B.2 Ecud_EcuM.arxml` 처럼 **부록 문자 + 소절**로 쓴다 |
| ⭐ **부록마다 되돌아가는 링크 한 줄** | 첫 문단을 `← <대표 링크> 로 돌아가기. 이 페이지는 부록 X … 다.` 로 시작한다. 🔴 **형제 링크는 걸지 않는다** — 생성 순서 때문에 id 를 모르고, 페이지 트리가 이미 보여 주며, **MCP 가 제목 기반 `ac:link` 로 바꾸므로 제목을 고치면 한꺼번에 깨진다**(함정 표 참조). 실측: 198 재생산본이 이 규칙을 어겨 부록끼리 **39개**를 걸었고 제목 링크가 **61개**였다 — 이름으로 전환해 **11개**로 줄였다(2026-11-07). 형제는 `부록 B.2-1` 처럼 **글자로만** 가리킨다 |
| 🔴 **대표에 표를 세 개 넘게 두지 않는다** | 표는 조회에 좋고 **추론에 나쁘다.** 대표는 논증이므로 **문장이 주고 표가 보조**다. 격자만 쌓이면 1차 개정의 실패가 되돌아온다. 📝 **📑 부록 표와 §1 속성 매크로는 규격이라 세지 않는다** — 세는 것은 §1.1 이후의 내용 표다 |

| 부록 | `IMS-PATCH-SUB: <티켓키> / <부록 문자> (<부록 이름>) · 대표 <대표 id>` | **P2-2 가 패치 페이지로 오인하지 않게** 하고, P8 이 "바뀐 것 → 고칠 부록"을 계산으로 정하게 한다 |

🔴 **부록에 `IMS-PATCH-TICKET` 을 쓰지 않는다.** 쓰면 한 티켓에 페이지가 5장 있는 것으로 판정되어 갱신이 5번 돈다.

### 이 구조가 버는 것

패치 티켓에서 실제로 바뀌는 건 거의 항상 **댓글 문답**이다 — 198 도 36건 중 10건이 IA-079 논쟁이었다. 그 변화는 **부록 C** 한 장에만 떨어진다. 통짜 8만 자 페이지는 갱신에 5만 토큰이 들어 무인 실행이 포기했지만(P8), 쪼개면 **부록 C 한 장**만 교체하면 된다.

그리고 축을 바꾼 덕에 **대표가 짧아진다.** 수집물을 요약하지 않고 **결론만** 적으면 되기 때문이다 — 근거는 부록이 들고 있다.

**대표·부록 다섯 장의 모든 문장에 적용한다.** 사용자가 198 대표를 처음 보는 사람의 눈으로 읽고 헷갈린다고 지적한 곳이다.

| 198 의 문장 | 이렇게 읽혔다 | 빠진 것 |

| # | 규칙 | 쓰는 법 |
| --- | --- | --- |
| 1 | **사람이 하는 일과 툴이 하는 일을 나눈다** | Generate·harmonize 같은 툴 작업은 **무엇을 검사하고 무엇을 생성하는지**만 쓴다. "고친다"의 주어는 **언제나 사람**이다. 툴 내부의 순서(예: 검사와 코드 생성 중 무엇이 먼저인지)는 **자료로 확인한 것만** 쓴다 — 확인하지 못했으면 지어 쓰지 않는다. 사람과 툴 사이의 순서는 분명히 쓴다 — **사람이 값을 맞춘다 → 툴이 Generate 한다.** ❌ `Generate 하면 해결된다` ⭕ `Generate 는 설정을 검사해 결과를 보고한다. 보고된 오류는 사람이 고친다` |
| 2 | **오류·경고·위험은 "원인 → 대응 → 완료 기준"을 한 묶음으로 쓴다** | 현상만 적지 않는다. **원인은 "어떤 값이 어떤 상태일 때 뜨는지"로 쓴다** — 오류가 당연히 뜨는 것처럼 쓰지 않는다. ❌ `ERR0532xx 가 뜨는 것이 정상이다` ❌ `Generate 하면 오류가 뜬다` ⭕ `<ERR> 이 뜰 수 있다 · 원인: <규칙의 조건>(출처) · 대응: 사람이 <할 일>(출처) · 완료 기준: <확인할 상태>`. Validation 오류의 완료 기준은 §5 의 "전부 설명되는 상태(해결했거나, 해당 없음 근거가 있다)"다. 그 밖의 오류·위험에서 자료에 대응이나 완료 기준이 없으면 그 칸에 **`자료 없음`** 이라고 쓰고 §6 에 올린다 — 칸을 비우거나 지어 채우지 않는다 |
| 3 | **💡 다섯 줄은 줄마다 본문 없이 읽어도 오해가 없어야 한다** | 툴 용어나 축약어만으로 줄을 끝내지 않는다. 줄마다 **누가 무엇을 하는지**가 들어 있어야 한다 |

## 서두 — 여섯 문장 서술 ⭐ (2026-11-07 2차 개정 · 글머리 금지)

**대표의 첫 블록은 글머리가 아니라 문장이다.** 글머리로 쓰면 요약이 되고, 요약은 논증하지 않는다.
1차 개정에서 💡 글머리 아홉 줄을 쓴 결과가 "의미 없는 나열"이라는 지적이었다.

여섯 문장에 이것만 담는다. 순서를 지킨다 — 이 순서가 독자의 질문 순서다.

```
1. 이 패치는 무엇을 고치러 왔나      (현상 한 줄 — 버전 숫자가 아니라 증상)
2. 왜 우리가 받기로 했나             (우리 회신·사유. 받지 않아도 되는 패치가 아니라는 근거)
3. 우리 형상에서 닿는 범위           ("파일 N 개 · 군데 N 곳 · 빌드 설정 N 개" 처럼 세어 준다)
4. 가장 위험한 지점 하나             (둘 이상 쓰지 않는다. 하나로 못 고르면 아직 이해가 덜 된 것이다)
5. 지금 어디까지 왔나                (적용 전 / 빌드 실패 상태 / 검증 대기 — 사람 칸과 모순되지 않게)
6. 기준 시각                         (조회 기준 YYYY-MM-DD KST)
```

🔴 **조사 범위를 서두에 늘어놓지 않는다.** "티켓 N건·릴리즈 노트 N개·ECM N건을 따라갔다" 는
**푸터로 보낸다.** 그건 작업자에게 필요한 정보가 아니라 **우리가 성실했다는 증거**다 — 자리가 다르다.

## 💡 요약 블록 — 다섯 줄 (대표에만)

서두 바로 뒤. **다섯 줄을 넘기지 않는다.** 글머리는 논증의 뼈대만 짚고, 살은 §2~§6 과 부록이 든다.

```

| `macroId` | **넣지 않는다.** Confluence 가 새로 만들어 준다. 공식 형식 안내에도 "Omit `macroId`" 라고 적혀 있다 |
| `_parentId` | `macroParams` 안에 **원본 페이지 번호**가 박혀 있을 수 있다. 지워서 `macroParams` 를 `{}` 로 둔다 |

#### 그래도 알고 있어야 하는 규칙

| 규칙 | 이유 |
| --- | --- |
| **행마다 `<th>`(이름) + `<td>`(값)** = 헤더**열** | 보고서 매크로는 `<th>` 를 속성 이름으로 읽는다. 둘 다 `<td>` 거나 `<th>` 만 있는 헤더**행**이면 속성으로 인식되지 않아 목록 표가 빈다. 일반 표(§1.1·§2.1 등)는 반대로 헤더행이다 |
| **`<thead>` 는 있어도 없어도 된다** | Confluence 가 저장할 때 모든 행을 `<tbody>` 로 합친다(실측). 예전 판에 "첫 행은 `<thead>` 안에" 라고 적었던 것은 **틀린 지침이었다** |
| **`schemaVersion` 은 `"1"`** (보고서 쪽은 `"3"`) | 두 매크로의 스키마 버전이 다르다. 틀리면 마이그레이터가 돌다가 깨진다 — SKILL.md 실측 함정의 `NullPointerException` 건이 그것이다 |
| **속성 11개, 이름·순서 그대로** | 표본 = 전역 템플릿 = 부모 페이지 안내, 셋이 같아야 한다. 한 글자만 달라도 그 열이 조용히 빈다. ⭕ 여섯 이름은 매크로가 글자 그대로 쓰므로 **얼어 있다** |

> 🔴 **`data-parameters` 의 따옴표.**
>
> JSON 이스케이프를 한 군데라도 빠뜨리면 파라미터가 **통째로 버려지고** 매크로가 "Corrupted content" 로 깨진다(실측).
> 가장 안전한 꼴은 **홑따옴표 속성 + 민낯 JSON** 이다 — `data-parameters='{"macroParams":{},"macroMetadata":{...}}'`.
> 발행 뒤 `getConfluencePage` 로 한 번 읽어 `__confluenceADFMigrationUnsupportedContentInternalExtension__` 가 **없는지** 확인한다.

> 📌 **라벨은 다루지 않는다** (사용자 방침 2026-11-07).
>
> 부모의 목록 보고서는 `label = "patch"` 로 모으고, 라벨은 본문이 아니라 별도 메타데이터라
> **본문을 복제해도 따라오지 않고, MCP 로는 달 수도 없다**(2026-11-06 실험 확인).
> 그래도 **스킬은 라벨을 조회하지도 안내하지도 않는다** — 목록 표에서 빠진 줄은
> 사용자가 보고 바로 처리한다. 라벨 이야기를 페이지·일지·보고에 쓰지 않는다.

### §1.1 경과

3열 표(`90`/`520`/`150`: 일자 · 내용 · **출처**). **출처 칸을 반드시 채운다** — 나중에 어디서 온 사실인지 추적할 수 있어야 한다.

릴리즈 노트 배포일부터 시작해 수평전개 발행 → 과제 사본 → 딜리버리 일감 생성 → 배포 → 문답 → 첨부 교체 순으로. **티켓 생성 전의 일(모듈 배포, 수평전개)도 넣는다** — 패치가 왜 왔는지가 거기서 나온다.

## §2. 왜 이 패치를 받나 — **대표**

*이 패치를 받지 않으면 무슨 일이 생기나* 에 답하는 절이다. **버전 숫자로 답하지 않는다.**

| 담을 것 | 쓰는 법 |
| --- | --- |
| **현상** | 증상을 먼저 쓴다 — `OTA 중 TransferData Repeat Block 에 NRC 0x71`. 그 다음에 조건을 붙인다 |
| **심각도** | **복구 방법이 있나 · 문제 상황에서 항상 발생하나 · 어디서 발견됐나**(협력사 / 실차 / 내부). 이 셋이 적용 우선순위를 정한다 |
| **우리가 받기로 한 근거** | 수평전개 회신의 날짜와 사유를 그대로. **이 한 줄이 "왜 하필 지금"에 답한다** |
| **해당되지 않는 결함** | 함께 고쳐진 결함 중 우리에게 해당 없는 것은 **해당 없음으로 명시**한다. 안 쓰면 검증 범위가 부풀어 오른다 |

2~4 문장 + 필요하면 표 한 개. 재현 시나리오·결함 상세는 **부록 A.1** 로 보내고 여기서 링크한다.

세어 준다. 문장 두세 개 + 표 한 개로 끝낸다 — 상세는 **부록 B** 가 든다.

## §4. 작업 순서 — **대표**

실제 손이 움직이는 순서. **각 단계가 부록 B 의 파일을 가리킨다** — 단계와 파일이 1:1 로 붙어야
독자가 다시 조립하지 않는다.

| 열 | 쓰는 법 |
| --- | --- |
| 순서 | 1, 2, 3 … **작업 순서대로.** 중요도 순이 아니다 |
| 할 일 | 한 문장 + 그대로 복사해 쓸 값(버전·파라미터명). 설명은 부록으로 |
| 어디 | `부록 B.2 Ecud_EcuM.arxml` 처럼 **파일을 가리킨다.** 문서 이름이 아니라 **우리 파일** |
| 막히면 | 알려진 실패가 있는 단계만 `부록 C.2` 를 붙인다 |

표준 흐름 — 프로젝트마다 바뀌지만 뼈대는 같다.

```
1 배포본 확보·대조 (재배포 여부)        5 harmonize (순서 지킴)
2 의존 모듈 버전 맞춤                   6 Generated 삭제 → Generate All(툴) → 뜬 Validation 오류 처리(사람)
3 arxml 설정 변경 (파일별)              7 빌드
4 IM 에만 있는 항목 확인                8 중간 버전 영향 확인
                                        9 SWP 버전업 (짝 패치와 함께)
                                       10 실기 검증 (부록 A.1 시나리오를 TC 로)
```

🔴 **"IM 에만 있는 항목"을 별도 단계로 둔다.** HAE 안내에 없고 IM 에만 있는 설정이 매번 2~4 건
나온다 — 가장 많이 빠뜨리는 자리이므로 설정 단계에 섞지 않고 독립 단계로 세운다.

🔴 **툴 단계와 사람 단계를 나눠 쓴다** (문장 규칙 1). 툴 단계의 "할 일"에는 툴이 검사·생성하는 것만 쓰고, 결과를 보고 고치는 일은 사람 단계로 따로 쓴다.

🔴 **오류가 예상되는 단계에는 그 자리에 "원인 → 대응 → 완료 기준"을 쓴다** (문장 규칙 2). `§5 참조` 만 남기지 않는다 — 처리 방침이 단계와 떨어져 있으면 작업자가 무엇을 해야 하는지 안 보인다(198, 사용자 지적 2026-11-08).

**Validation 규칙이 새로 들어온 패치는 이 흐름으로 쓴다.** 정상 흐름은 *사람이 필요한 값을 맞춘 뒤 Generate 하면 오류 없이 코드가 나온다* 이다. 오류는 **새 규칙이 요구하는 값을 아직 맞추지 않았을 때만** 뜬다.

```
👤 1. 안내·IM 의 설정 변경 N 군데를 고친다
👤 2. 부록 B.4 의 새 규칙과 우리 값을 미리 점검한다 — 걸릴 값은 Generate 전에 고칠 수 있다
⚙ 3. Generate All — 우리 값이 새 규칙에 맞지 않으면 그 규칙의 ERR 을 보고한다
👤 4. 뜬 ERR 을 하나씩 처리한다 — 값을 고쳐 해결하거나, 해당 없음 근거를 남긴다
👤 5. 전부 설명되면 완료로 본다 (§5)
```

🔴 **어느 쪽을 권하는지(2 를 꼭 하라 / 3·4 로 처리하라)는 자료에 근거가 있을 때만 쓴다.** 근거가 없으면 위 흐름을 그대로 두고 권고를 붙이지 않는다.

## §5. 끝났다고 말하는 기준 — **대표** ⭐ (신설)

**무엇을 확인하면 이 패치가 끝난 것인가.** 1차 개정에서는 이것이 §6 의 10번 항목에 묻혀 있었다.

| 담을 것 | 쓰는 법 |
| --- | --- |
| **필수 TC** | 부록 A.1 의 재현 시나리오를 **기대 결과까지** 옮긴다 — `잔여 180 byte 에서 Repeat 송신 → 긍정 응답`(패치 전엔 NRC 0x71) |
| **해당 없는 TC** | 조건이 안 맞아 **안 하는 시험**을 명시한다. 안 쓰면 검증자가 못 돌리는 시험을 붙들고 있는다 |
| **정적 확인** | Validation 결과 — 새 ERR 이 **전부 설명되는 상태**(해결했거나, 해당 없음 근거가 있다)인지 · 빌드 성공 · 생성물 diff. 괄호 풀이를 생략하지 않는다 |
| **기록 종결** | IMS 티켓 Close 조건과 주체. 수평전개 사본과 딜리버리 티켓의 Status 규칙이 **다르다** |

| 올리는 것 | 왜 |
| --- | --- |
| HAE 가 **"기대됩니다"** 로 답한 항목 | 확인이 아니다 |
| HAE 안내에 **없지만** IM 이 요구하는 항목 | 안내만 따르면 빠진다 |
| 권한이 막혀(403·404) **근거를 못 본** 항목 | 권한 요청이 필요한지까지 판정해 준다 |
| **가능성이 높다**고만 말할 수 있는 Validation | 실제 설정을 확인하지 않았다. 조건 · 확인된 것 · 확인 안 된 것 · 확인 방법을 함께 쓴다 (문장 규칙 4) |
| 우리 기록과 HAE 기록이 **어긋난** 항목 | 추측으로 맞추지 않는다 |
| `~없는 것으로 보인다` 수준의 전제 | 실제로 없는지 확인해야 한다 |

🔴 **여기에 적은 것은 §4 작업 순서의 해당 단계에서도 가리킨다.** 대표 끝에만 있으면 작업 중에 안 읽는다.

# 부록 A. 변경의 뿌리 — **부록 A 페이지**

*왜 바뀌었나* 에 답한다. 적용 전에 한 번 읽는 장이므로 **무엇이 들어오는지**만 담고, 어떻게
설정하는지는 부록 B 로 보낸다.

## A.1 왜 고쳤나 — 결함과 재현 시나리오 ⭐

수평전개 원본(`CPINFO-xxxx`)의 결함 상세. **재현 시나리오가 그대로 실기 TC 가 된다** — 바이트
수·횟수·응답 코드까지 옮긴다. 결함마다 **복구 가능 여부**와 **발견 경로**를 붙인다.

🔴 **우리에게 해당 없는 결함은 해당 없음으로 쓴다.** 조건(두 개 이상 프로토콜 동시 진단 등)을
함께 적어 **왜 해당 없는지**를 남긴다 — 다음 프로젝트는 해당될 수 있다.

## A.2 어느 버전에서 고쳤나 — 버전 경로

모듈별 `시작 → 끝` 과 **그 사이 중간 노트 수**. 노트를 몇 개 읽었는지 밝힌다.

## A.3 중간 버전에 무엇이 딸려 오나 ⭐ — **빼면 안 되는 절**

`HF2 → HF4` 티켓이면 **HF3 도 들어온다.** 티켓·설정 안내 어디에도 나오지 않는다 — **이 스킬의
존재 이유다.** 변경마다 **설정 영향이 있나**를 판정해 적고, 없으면 "없음"이라고 쓴다.

없으면 **"중간 버전 없음"** 이라고 쓴다 — 빈칸은 조사를 안 한 것과 구별되지 않는다.

## A.4 목표 버전의 나머지 변경

`improvement`·`activity`·`bug` 를 구분. **`Impact on ASW` 가 `Configuration` 인 항목은 부록 B 에
대응 항목이 있어야 한다** — 없으면 둘 중 하나가 빠진 것이다. `Related API` 는 그대로 옮긴다.

## A.5 함께 맞춰야 하는 모듈 (의존)

버전을 맞춰야 하는 모듈과 **조건부 의존**(특정 기능을 쓸 때만). 조건을 안 적으면 안 쓰는데 올려서
다른 것을 깨뜨린다.

## A.6 자료가 없는 것 ⚠️ — **빼면 안 되는 절**

**없는 것**(하위작업 본문이 비어 있다)과 **못 본 것**(403·404)을 구별한다. 안 쓰면 다음 사람이
똑같이 한 시간을 헤맨다. **추측으로 메우지 않는다** — 빈 하위작업의 제목으로 내용을 지어내는 것이
가장 위험한 기록이다.

# 부록 B. 우리 형상 변경 지도 — **부록 B 페이지** ★ 핵심

**이 장이 이번 개정의 중심이다.** 1차 개정의 `§3.1 설정 변경 항목`(HAE 안내 번호 순)을 버리고
**우리가 여는 파일 순서**로 재조립한다.

## B.1 한눈에 — 고치는 파일과 군데 수

표 하나. `파일 / 종류 / 군데 수 / 무엇을 / 조건부인가`. `무엇을` 칸은 §3 의 "`하는 일 (쉽게)` 쓰는 법"을 따른다. **합계를 적는다** — §3 과 💡 셋째 줄이 이 숫자를 인용한다.

`종류` 는 `설정값 (Ecud)` · `정의 (Bswmd)` · `빌드 설정` · `생성물` 중 하나다 (문장 규칙 6). 합계도 종류별로 나눠 적는다.

## B.2 파일별 변경

**파일 하나 = 소절 하나** (`#### Ecud_EcuM.arxml — N 군데`). 소절 안은 번호 목록이고, 항목마다
넷을 붙인다.

| 붙이는 것 | 왜 |
| --- | --- |
| **무엇을** | 컨테이너·파라미터명·값. 그대로 복사해 쓸 수 있게 |
| **왜** | 근거 문서와 절 (`← Dcm IM 2.1.1.5`). 근거 없는 변경은 적지 않는다 |
| **함정** | 숫자 예시를 베끼면 안 되는 것 · harmonize 가 지우는지 여부 · 대소문자 |
| 🔴 **안 하면 생기는 일** | 빌드 실패 / Validation ERR / **빌드는 되고 런타임에 터짐**. 이것이 우선순위를 정한다 |

🔴 **`삭제` 와 `컴파일·Generate 제외` 를 구별한다.** 섞으면 빌드가 깨진다(실측).
🔴 **IM 의 `Index`·`Id` 숫자는 전부 예시다.** 프로젝트의 실제 순서로 정한다.
💡 **HAE 답변의 어조를 보존한다.** "되어 있을 것으로 **기대**됩니다" 는 확인이 아니다 → §6 으로.

## B.3 harmonize 와 Generate 순서

파일이 아니라 **절차**다. 대상 모듈과 **순서**를 쓰고, 순서를 어겨 에러가 난 실측이 있으면 그것도
쓴다. "해당 없음"도 사실이므로 쓴다.

## B.4 Generate 후 새로 뜨는 Validation ⭐ — **빼면 안 되는 절**

패치가 설정은 안 바꾸는 대신 **검증을 추가**하는 경우가 있다. 처음 보는 에러는 "패치가 깨뜨린 것"이
아니라 **"원래 틀렸던 것이 드러난 것"** 일 수 있다. 🔴 **그래도 "뜨는 것이 정상"으로 끝내지 않는다** — ERR 마다 원인 → 대응 → 완료 기준을 붙인다 (문장 규칙 2).

⭐ **한 걸음 더 간다** — IM 의 **표준 설정값**과 새 Validation 의 **조건**을 나란히 놓으면 **무엇이
걸릴지 미리 지목할 수 있다.** 이 한 줄이 페이지의 가치를 가장 크게 올린다.
⚠️ **"걸릴 가능성이 높다"로 쓰고 "걸린다"로 쓰지 않는다** — 실제 설정은 확인하지 않았다. 그 옆에 조건 · 확인된 것 · 확인 안 된 것 · 확인 방법을 쓴다 (문장 규칙 4).
📌 **신규와 변경을 구별해 센다.** 합쳐 세면 대표의 속성 칸 숫자가 틀어진다.

## B.5 우리 형상에 닿지 않는 것

HAE 가 배포 때 함께 보내는 **패치와 무관한 점검**(IA·VC). 설정 변경 표에 섞여 와도 여기로 떼어
적고 **등급(🔴 Error / 🟡 Advisory / 🟣 Exception)** 과 **적용 범위에 드는지**를 밝힌다.
섞어 적으면 "패치 때문에 해야 하는 일"로 오해한다.

# 부록 C. 막힌 것과 끝난 논의 — **부록 C 페이지**

**갱신이 거의 항상 이 장에 떨어진다**(P8-A1). 새 댓글·새 빌드 실패가 들어오는 자리다.

## C.1 끝난 논의 — 다시 꺼내지 않는다

길게 오간 문답은 표로 눌러 적고 **결론을 못 박는다** — 누가, 언제, 무엇으로 닫았는지. 판정 등급이
걸린 논의면 등급 표를 함께 둔다. **재검토 조건이 있으면 그것만** 남긴다(`단, 조건 X 가 생기면`).

## C.2 적용 중 막힌 것

**빌드 로그는 티켓 본문이 아니라 첨부에 있다** — 꺼내서 치명 오류와 경고를 적는다. 오류 문구는
**원문 그대로** 한 줄 인용한다(적용자가 그 문자열로 검색한다). 조치 근거가 다른 과제 티켓이라
`403` 이면 **"우리 기록에 없다 · 작업자·커밋 이력으로 확인 필요"** 라고 쓴다.

## C.3 문서 접근 권한

막힌 문서의 **id · 상태 코드 · 어디서 온 링크인지** + **권한 요청이 필요한지 판정**. 발신 측이 이미
링크를 교체했으면 요청은 불필요하다. 우회로(배포 zip 의 `Doc` 폴더 · 제목 검색)를 적어 준다.

# 부록 D. 근거 문서와 첨부 — **부록 D 페이지**

## D.1 함께 확인할 HAE 문서

문서마다 **어느 절을 보나**와 **확인 결과**. 제목만 나열하면 쓸모가 없다 — 적용자는 절 번호와 값이
필요하다. 못 본 문서(403·404)도 이 표에 남긴다.

📌 **안내에 적힌 IM 절 번호를 믿지 않는다.** IM 이 장 번호를 재편해 왔고 **어긋남이 패턴**이다
(실측 3건 모두). **안내 번호 → 실제 번호**를 적어 둔다.

## D.2 첨부 파일

**올린 쪽을 구별한다** — HAE 배포본과 당사 자료(빌드 로그·arxml). 🔴 **스킬은 첨부를 받지도 올리지도
않는다** — 목록만 적는다. 같은 파일명의 삭제 → 추가는 **재배포**이므로 날짜와 함께 "이전 판으로
작업했다면 대조하라"를 경고한다.

## D.3 참고 링크

키만 나열하지 않고 **그것이 무엇인지** 한 조각을 붙인다 — `(HF2, 시작점)`, `(본문 없음)`,
`(범위 밖)`. 나중에 다시 열 사람에게는 그 한 조각이 전부다.

## D.4 용어 (2026-11-08 신설)

다섯 장에 처음 나온 툴·AUTOSAR 용어와 한 줄 풀이 (문장 규칙 7). 풀이에도 문장 규칙 5 가 적용된다 — 자료에 정의가 있으면 출처를 달고, 없으면 (추정) 을 붙인다.

## 푸터 (글자 그대로)

### 대표 페이지 푸터

`<hr />` 뒤에 `style="font-size: 12px"` 문단 둘.

```
수집 범위 (eCoDY 읽기 전용 API): IMS — <티켓> 본문·댓글 N건·첨부·변경 이력 N건 / <연결 티켓 전부> / 하위작업 N건(<키 나열>) · ECM — <pageId>(<제목>)…, <pageId>는 404 · 기준 시각 YYYY-MM-DD HH:MM KST
```

```
IMS-PATCH-TICKET: <키> · IMS-UPDATED: <ISO> · IMS-COMMENTS: <수> · IMS-PAIR: <짝 키> · IMS-SUBPAGES: A=<id>,B=<id>,C=<id>,D=<id> · IMS-LINKED: <쉼표 구분> · ECM-LINKED: <쉼표 구분> · ECM-MISSING: <쉼표 구분>
```

| 마커 | 쓰임 |
| --- | --- |
| `IMS-PATCH-TICKET` | **P2 가 이 마커로 대상을 찾는다. 없으면 이 페이지는 갱신되지 않는다** |
| `IMS-UPDATED` · `IMS-COMMENTS` | P6 변화 판정의 기준 |
| `IMS-PAIR` | 짝 패치 |
| `IMS-LINKED` · `ECM-LINKED` | 다음 회차가 추적 범위를 재확인하는 근거 |
| `IMS-SUBPAGES` | **P8-A1 이 "바뀐 것 → 고칠 부록"을 계산으로 정하는 근거.** 부록을 다시 조회하지 않아도 id 를 안다 |
| `ECM-MISSING` | 권한이 풀리면 다시 시도할 목록 |

**마커를 틀리면 다음 회차가 이 페이지를 못 찾거나 변화를 놓친다.** 형식을 그대로 지킨다.

### 부록 페이지 푸터

`<hr />` 뒤에 `style="font-size: 12px"` 문단 **하나**. 대표의 마커를 부록에 복사하지 않는다.

```
IMS-PATCH-SUB: <티켓키> / <부록 문자> (<부록 이름>) · 대표 <대표 pageId> · 기준 YYYY-MM-DD KST
```

예: `IMS-PATCH-SUB: MCP1001-198 / B (우리 형상 변경 지도) · 대표 381747206 · 기준 2026-11-07 KST`

| 마커 | 쓰임 |
| --- | --- |
| `IMS-PATCH-SUB` | ① P2-2 가 **패치 페이지로 오인하지 않게** 한다 ② P8 이 고칠 부록을 문자로 찾는다 ③ 사람이 손으로 만든 심화 분석 페이지와 구별한다 |

🔴 **부록에 `IMS-PATCH-TICKET`·`IMS-UPDATED`·`IMS-COMMENTS` 를 쓰지 않는다.** 쓰면 한 티켓이 5장으로 판정되어 갱신이 5번 돈다.

| ⭐ **대표를 표로 채우기** | 표는 조회용이고 추론하지 않는다. 대표는 **문장이 주**고 표는 셋 이하 |
