# 패치 페이지 형식

`SKILL.md` P7 의 정본. 부모 `334594056` "[Autoever] Patch 티켓" 아래 패치 티켓 하나당 한 페이지다.

**이 페이지를 읽는 사람은 패치를 적용할 사람이다.** 목적은 요약이 아니라 **누락 없는 적용**이다. 그래서 ERR 코드·의존 모듈 버전·설정 경로·재현 시나리오처럼 **그대로 복사해 쓸 값**을 담는다. 반대로 결함 설명을 길게 늘여 쓰지 않는다.

> 🔴 **마크업은 `confluence-writing` 스킬이 정본이다 — 먼저 읽는다.**
>
> 이 문서는 **어느 절에 무엇을 담고 표를 몇 열로 할까**를 정한다. **어떤 html 로 쓸까**는 `confluence-writing`(+ 그 `references/formatting-cheatsheet.md`)이 정한다. 아래 각 절의 `2열 표(250/510)` 같은 표기는 **폭 숫자**이고, 그 숫자를 적용하는 방법은 이것이다:
>
> ```html
> <table data-layout="default" data-display-mode="fixed">
>   <thead><tr><th data-colwidth="250"><p><strong>…</strong></p></th>
>              <th data-colwidth="510"><p><strong>…</strong></p></th></tr></thead>
>   <tbody><tr><td data-colwidth="250"><p>…</p></td>
>              <td data-colwidth="510"><p>…</p></td></tr></tbody>
> </table>
> ```
>
> **모든 행의 모든 셀**에 `data-colwidth` 를 넣는다. **`<colgroup>`·`<col>` 은 쓰지 않는다** — create/update 모두 저장 시 서버가 지워서 표가 균등 폭으로 렌더링된다. 2026-11-06 실측: `<colgroup>` 으로 쓴 페이지의 표 19개가 전부 폭을 잃었다. 폭 합계 기준은 **760px** 이다.
>
> 그 밖의 규약도 그대로 따른다 — 본문은 **H3** 부터(H1·H2 금지), 수정은 **직전 fetch 후 전체 교체**, 첨부가 있으면 **html 왕복**.

### 1.0-A 매크로 마크업 — **짓지 말고 복제한다** (2026-11-06 개정)

마크업을 손으로 쓰지 않는다. **표본 페이지 `380665864` "패치 표본 페이지 양식"** 을
`getConfluencePage(cloudId="mobaseasec.atlassian.net", pageId="380665864", contentFormat="html")`
로 읽어 그 골격을 그대로 쓰고 **태그 사이의 글자만** 바꾼다.

표본은 전역 템플릿 **"모빌진 패치 티켓 정리"** 에서 나온 것이고, 템플릿은 MCP 로 읽을 수 없다
(`searchConfluenceUsingCql` 의 `type` 목록에 `template` 이 없다 — 서버가 직접 답했다).
표본이 바뀌면 그대로 따라간다. **이 문서에 골격을 베껴 적어 두지 않는다** — 베껴 두면 반드시 어긋난다.

크롬이 없는 세션에서 표본을 못 읽으면 비상용 사본 `references/page-skeleton.html` 을 쓴다.

#### 복제할 때 떼어내는 것 둘

| 떼어낼 것 | 왜 |
| --- | --- |
| `macroId` | **넣지 않는다.** Confluence 가 새로 만들어 준다. 공식 형식 안내에도 "Omit `macroId`" 라고 적혀 있다 |
| `_parentId` | `macroParams` 안에 **원본 페이지 번호**가 박혀 있을 수 있다. 지워서 `macroParams` 를 `{}` 로 둔다 |

#### 그래도 알고 있어야 하는 규칙

| 규칙 | 이유 |
| --- | --- |
| **행마다 `<th>`(이름) + `<td>`(값)** = 헤더**열** | 보고서 매크로는 `<th>` 를 속성 이름으로 읽는다. 둘 다 `<td>` 거나 `<th>` 만 있는 헤더**행**이면 속성으로 인식되지 않아 목록 표가 빈다. 일반 표(§1.1·§2.1 등)는 반대로 헤더행이다 |
| **`<thead>` 는 있어도 없어도 된다** | Confluence 가 저장할 때 모든 행을 `<tbody>` 로 합친다(실측). 예전 판에 "첫 행은 `<thead>` 안에" 라고 적었던 것은 **틀린 지침이었다** |
| **`schemaVersion` 은 `"1"`** (보고서 쪽은 `"3"`) | 두 매크로의 스키마 버전이 다르다. 틀리면 마이그레이터가 돌다가 깨진다 — SKILL.md 실측 함정의 `NullPointerException` 건이 그것이다 |
| **속성 20개, 이름·순서 그대로** | 표본 = 전역 템플릿 = 부모 페이지 안내, 셋이 같아야 한다. 한 글자만 달라도 그 열이 조용히 빈다 |

> 🔴 **`data-parameters` 의 따옴표.**
>
> JSON 이스케이프를 한 군데라도 빠뜨리면 파라미터가 **통째로 버려지고** 매크로가 "Corrupted content" 로 깨진다(실측).
> 가장 안전한 꼴은 **홑따옴표 속성 + 민낯 JSON** 이다 — `data-parameters='{"macroParams":{},"macroMetadata":{...}}'`.
> 발행 뒤 `getConfluencePage` 로 한 번 읽어 `__confluenceADFMigrationUnsupportedContentInternalExtension__` 가 **없는지** 확인한다.

> 📌 **라벨은 복제되지 않는다.**
>
> 부모의 목록 보고서는 `label = "patch"` 로 모은다. 라벨은 본문이 아니라 별도 메타데이터라
> **본문을 복제해도 따라오지 않고, MCP 로는 달 수도 없다**(2026-11-06 실험 확인).
> 새로 만든 페이지의 라벨은 **사용자가 직접 붙인다.** 스킬은 부모 페이지에 안내를 쓰지 않고,
> 일지의 "신규 페이지" 줄에 링크만 남긴다. 붙었는지는
> `searchConfluenceUsingCql("label = 'patch' and space = 'mobaseasec4'")` 로 확인할 수 있다.

## §2. 패치 출처와 변경 내역

머리에 한 줄: 티켓에는 한 줄만 있고 중간 버전을 모두 봐야 한다는 사실 + 조회 기준일.

**짝 패치와 모듈·버전이 같으면** 절 머리에 📌 blockquote 로 밝힌다 — "모듈과 버전이 짝 패치와 완전히 같다. 따라서 §2 전체와 §3.3 은 그 페이지와 내용이 동일하다 — **양쪽을 따로 조사해 같은 결과를 얻었다.** 고유한 것은 §3.1 설정 변경과 §4 논의다." 이 한 줄이 두 가지를 해 준다: 읽는 사람이 "왜 똑같은 내용이 또 있나" 를 묻지 않게 하고, **같은 결과를 베낀 것이 아니라 검증한 것**임을 밝힌다.

### §2.1 버전 경로

4열 표(`130`/`130`/`90`/`410`: 버전 · 릴리즈 노트 · 배포일 · 성격).

- 시작점은 "현재 형상"이라고 적는다.
- **중간 버전 행에는 ⭐ 와 "티켓에 전혀 안 나온다"를 쓴다.**

- 범위 밖의 다음 버전이 있으면 회색 행으로 "이번 패치 범위 아님"을 적는다.

### §2.2 중간 버전에 무엇이 들어 있나 ⭐ — **빼면 안 되는 절**

3열 표(`110`/`520`/`130`: 근거 · 내용 · **설정 영향**).

`설정 영향` 칸이 이 절의 핵심이다:

| 표기 | 언제 |
| --- | --- |
| ⚠️ **있을 수 있음** + 이유 | 설정 파라미터·권한 범위·의존성을 바꾸는 변경 |
| `해당 설정일 때만` | 특정 설정값에서만 영향 |
| `<기능> 미사용이면 무관` | 기능 조건부 |
| `없음 (주석)` | 주석·테스트·컴파일 |

중간 버전이 없으면 이 절을 **"중간 버전 없음 — 연속 버전이다"** 로 한 줄만 남긴다. 절을 지우지 않는다(확인했다는 사실이 정보다).

### §2.3 목표 버전의 변경

### §2.4 결함 상세 — 수평전개로 확인된 N건 ⭐

**결함을 열로, 12항목을 행으로** 두는 비교 표가 가장 읽기 좋다(`120`/`320`/`320`...). 결함이 1건이면 2열로.

행: 현상 · 원인 · 재현 · 발견 · 빈도 · 복구 · **수평전개 검토 대상** · 개선 내용 · **FBL 영향** · **R40/R44** · HAE 코멘트. 관련 ES 사양은 머리 문단에 묶어 쓴다.

- `복구: 없음` 은 🔴 를 붙인다.
- `수평전개 검토 대상` 은 **우리 제어기가 해당되는지** 바로 보이게 조건을 그대로 옮긴다.
- 재현 시나리오는 숫자(바이트 수 등)를 그대로 적는다 — **실기 검증 TC 로 쓴다**.

이 절 뒤에 **📌 통찰 blockquote** 를 하나 붙일 수 있다. 예: 이 결함이 다른 점검 항목과 증상은 같지만 원인이 다르다는 구분, 또는 두 결함이 같은 뿌리라는 설명. **추측은 쓰지 않는다** — 두 자료를 나란히 놓고 읽어 알 수 있는 것만.

### §2.5 자료가 없는 것 ⚠️ — **빼면 안 되는 절**

머리 한 줄: "찾아봤지만 오토에버 쪽에 기록이 없는 항목이다. **'내가 못 찾은 것'이 아니라 '없는 것'**이므로 더 찾지 않아도 된다."

2열 표(`250`/`510`). 전형적인 항목:

- 하위작업 N건 전부의 본문 (몇 건을 열어 확인했는지 숫자로)
- 결함 N건 중 M건의 상세 (부모는 "하위작업 보라", 하위작업은 비어 있음 = **순환**이라고 명시)
- 사전 공지 본문
- 404 인 ECM 페이지 (**페이지 id 를 적는다**)
- 🔴 **403 인 다른 과제 티켓** — 댓글이 조치 근거로 가리킨 티켓을 볼 수 없는 경우. "조치 내용이 우리 과제 어디에도 기록되지 않았다" 를 명시하고 대안(작업자 문의·커밋 diff)을 쓴다. **가장 아픈 공백이므로 맨 위에 둔다**
- 중간 버전의 설정 영향 판단 (HAE 가 명시하지 않은 것 → "적용 후 Generate 로 확인")
- **답이 간략한 당사 질문** — HAE 가 "기대됩니다" 처럼 답했거나 질문의 일부만 답한 것. 무엇을 직접 확인해야 하는지 쓴다

### §3.1 HAE 설정 변경 안내

2. *이유* (기울임)
3. ✅ **근거 확인**: ECM 에서 대조한 결과. "SAG `<문서>` **<절>** 절에 같은 내용이 있다 — 우리 MCU 는 `<모델>` 이므로 **해당된다**" 처럼 **우리 MCU 해당 여부를 결론으로** 쓴다.
4. 📌 **IM 에만 있는 항목**: HAE 안내에 없지만 IM 이 요구하는 설정을 찾으면 적는다. "이미 들어가 있는지 확인해 두면 좋다".

6. 📌 **당사가 추가로 찾아낸 항목**: 안내에 없는데 당사가 패치 파일과 현재 설정을 비교해 발견한 것이 있으면 별도 행(`⑩` 등)으로 적고 HAE 답변을 붙인다. 다음 회차에도 같은 비교가 필요하다는 신호다.

7. ⭐ **근거 문서의 형제 절을 전수로 쓴다** — 아래.

항목이 많으면 표에 `#` 열(`①②③…`)을 두어 §6 할 일 표에서 번호로 가리킨다.

#### ⭐ 근거 문서를 열었으면 그 문서의 설정 변경 절을 **전수로** 쓸어라 (2026-11-06 신설)

위 3번은 "HAE 가 말한 항목을 ECM 에서 대조"하는 것이다. 그것만으로는 **ECM 에 있는데 HAE 가
말하지 않은 설정**이 빠진다. HAE 안내문은 가이드의 일부만 옮겨 온다.

**실제로 빠졌다.** MCP1001-199(APP V2.1.11) 페이지는 SAG `210284000` 을 링크로 걸고
`3.3.1 SCons.arxml`(`__GHS__`) 한 절만 담았다. 그런데 같은 문서에 설정 변경이 `3.3.1`~`3.3.5`
다섯 절로 있었고, 그중 둘이 실제 패치 동작이었다.

```
3.3.3.1 DcmDspSecurity        DcmDspSecurityMaxAttemptCounterReadoutTime: 10
3.3.3.2 DcmDspSecurityRow     사용할 모든 Security Level 에 AttemptCounterEnabled: true
3.3.5.2 Ecud_EcuM.arxml(R44)  PMem_Driver(VOID, StartUp, Index 0, Used true)
                              + EcuMCalloutUserIncludeFiles (Mem_76_Pfls_Common 버전별로 헤더 갈림)
```

이 둘은 배포본 패치 스크립트가 **조건이 맞으면 자동으로** 바꾸는 것이어서, 페이지에 없으면
적용자가 **패치를 돌린 뒤에야** 설정이 변한 것을 발견한다.

| 할 일 | 어떻게 |
| --- | --- |
| 근거 문서를 열 때 **문서 전문**을 받는다 | `ecm_api.py read <id> --max 400000`. 기본값은 본문을 자르고 `(이하 N자 생략)` 을 붙인다 — 잘린 본문으로 "그 절만 있다"고 판단한 전례가 있다 |
| 설정 변경 절을 **전부 찾는다** | 표 머리가 `Location \| Description \| Image` 인 절이 설정 변경이다. `3.3.x`·`2.1.1.x` 꼴로 형제 절을 훑는다 |
| HAE 안내에 **없는 절**은 별도 행으로 | `#` 를 새로 붙이고 📌 로 표시. **조건을 함께 적는다** — "AttemptCounter 를 쓸 때", "Fota 모듈이 있을 때" |
| 당사 해당 여부를 모르면 **빼지 말고** | **"조건: … / 당사 해당 여부 미판정"** 으로 싣고 §4.4 확인 필요에도 올린다. 빼면 적용자가 모른다 |
| 번호·인덱스 값은 **예시임을 밝힌다** | IM 이 `중복되지 않는 순차적인 Index 설정 함 / 본 가이드에서는 42로 설정 함` 처럼 적은 것은 예시다. HAE 안내가 숫자(`55`)만 옮겨 왔으면 **"예시다, 베끼지 말 것"** 을 그 행에 적는다 — 안내의 숫자를 그대로 베껴 쓴 사례가 실제로 있었다 |

**설정 변경 안내에 섞여 온 점검 항목은 표 밖으로 뺀다.** HAE 표의 마지막 행에 `ValidationChecker 검증항목` 이 끼어 있는 경우가 있는데, 이것은 패치 설정이 아니라 **배포 때 함께 공유하는 잠재 이슈**다. 별도 표를 하나 만들어 ① HAE 가 적은 지시 ② 그 점검 문서의 **등급과 실제 지침** 을 나란히 적는다 — 등급이 Advisory 이고 지침이 "프로젝트에 맞추어 정한다" 인데 안내만 보면 "고쳐야 하는 일" 로 오해한다.

**harmonize 수행 절차가 안내돼 있으면 번호 목록으로 옮긴다.** 티켓 문답에서 나온 절차(Generate → 새로고침 → 폴더 확인 → Harmonize 등)는 적용자가 그대로 따라 하는 값이다.

### §3.3 패치 후 새로 뜨는 Validation ⭐ — **빼면 안 되는 절**

머리에 ⚠️ blockquote:

> **적용 후 첫 Generate 에서 처음 보는 에러가 뜰 수 있다 — 정상이다.** 이 패치는 설정을 바꾸지 않는 대신 Validation(설정 검증)을 N개 새로 추가했다. 기존에 조용히 넘어가던 설정 불일치가 이제 에러로 드러난다. 즉 **"패치가 깨뜨린 것"이 아니라 "원래 틀렸던 것이 드러난 것"**일 수 있다.

2열 표(`120`/`640`: ERR 코드 · 어떤 설정 불일치를 잡는가). IM 의 영문 메시지를 **한국어로 재서술**하고 파라미터명은 그대로 둔다. 짝을 이루는 코드(`false 인데 없음` / `true 인데 있음`)는 한 행에 묶어도 된다. 적용 대상 Service Id 처럼 구체적인 값은 반드시 옮긴다.

표 뒤에 ⭐ 한 줄: **가장 걸리기 쉬운 코드**와 그 이유. 그 코드가 어느 결함과 같은 뿌리인지 연결해 주면 좋다.

Validation 추가가 없는 패치면 이 절을 **"Validation 신규 없음 (IM `4.1.1.x` 확인)"** 한 줄로 남긴다.

## §4. 논의와 결론

댓글이 긴 티켓만. 머리 한 줄로 **"댓글 N건 중 M건이 이 주제다. 패치 본체와는 별개다"** 를 밝힌다.

### §4.1 점검 기준 (해당 점검이 있을 때)

ECM 문서 원문에서 뽑은 `목적` · `적용 범위` · `조치` 를 2열 표로. 이어서 FAIL 표 3열(`70`/`110`/`580`: FAIL · **등급** · 조건과 의미).

- 등급은 🔴 Error / 🟡 Advisory / 🟣 Exception 를 아이콘과 함께. **Advisory 는 "권고"임을 글로도 적는다** — Error 와 섞이면 과도한 대응을 부른다.
- 우리 제어기가 걸린 항목은 **굵게 + "여기 해당했다"** 를 적는다.

### §4.2 경과와 결론

3열 표(`80`/`130`/`550`: 일자 · 누가 · 내용). 질문-답변 순서대로. 판단을 바꾼 결정적 근거에 ⭐.

표 뒤에 ✅ **결론 blockquote**:
1. 한 문장 결론 (굵게).
2. **남는 위험**을 번호로. 전제가 깨지면 재검토해야 하는 조건을 명시한다 — "판단의 전제는 X 다. Y 한 파생 차종이 생기면 다시 판단해야 한다".

짝 패치가 있으면 **결론이 양쪽에서 같은지 다른지** 를 반드시 적는다. 실측에서 같은 점검이 APP·FBL 에서 **서로 다른 근거로** 닫혔다 — 한쪽 결론을 다른 쪽에 복사하면 틀린다.

### §4.3 적용 중 막힌 것 (빌드 실패 등)

티켓에 빌드 실패·Generate 에러가 남아 있으면 절을 따로 둔다. 2열 표(`170`/`590`):

| 행 | 담을 것 |
| --- | --- |
| **치명 오류** | 로그에서 꺼낸 에러 문구를 **그대로**(파일명·줄 번호 포함). 그리고 **어느 설정 변경이 원인인지** 🔗 로 연결한다 |
| 함께 나온 경고 | 치명은 아니지만 구조적 문제를 알려 주는 것(헤더 매크로 중복 정의, 함수 포인터 타입 불일치 등). "이번 실패의 원인은 아니지만 기록해 둔다"를 명시 |
| ✅ **조치** | 누가 언제 무엇으로 해결했는지. HAE 승인 여부 |
| 🔴 **남은 문제** | 조치 근거가 접근 불가한 곳(다른 과제 티켓 등)에 있으면 **그 사실을 적고** "작업자나 커밋 이력으로 확인해 여기에 적어 두는 것이 좋다"를 쓴다 |

### §4.4 문서 접근 권한

권한 문제로 작업이 막혔던 이력이 있으면 짧게 적고, **우회로를 📌 blockquote 로 남긴다** — ① 배포 zip 안 `Doc` 폴더, ② 같은 내용의 다른 ECM 페이지(당사가 실제로 쓴 문서 목록). 다음 사람이 권한을 기다리며 멈추지 않게 하는 것이 목적이다.

마지막으로 ⚠️ **확인 필요 blockquote** — 적용자가 직접 확인해야 하는 열린 항목(첨부 대조, 설정 영향, IM 에만 있는 항목, HAE 가 "기대" 로 답한 것, 접근 불가한 조치 근거 등)을 글머리로.

## §5. 함께 확인할 HAE 문서

IM 절 번호가 어긋났으면 **맨 위에 📌 blockquote** 로 그 사실을 먼저 적는다 — "안내는 `A` 라고 적었지만 현재 IM 에서는 `B` 에 있다. IM 이 장 번호를 재편했기 때문이다. **앞으로 안내의 IM 절 번호는 그대로 믿지 말고 제목으로 찾는 것이 빠르다.**"

2열 표(`250`/`510`: 문서 · **어디를 보나 / 확인 결과**). 문서 칸에는 제목·링크·버전·날짜. 결과 칸에는:

- ✅ 확인 완료 + **절 번호와 그 절에 무엇이 있는지**
- 📌 그 문서가 **이 패치 전용이 아닐 때** 그 사실 (별도 요구가 섞여 있다는 경고)
- 🔴 404 · 권한 없음 + 페이지 id + **문서 제목** + **그 문서를 가리킨 출처** + 확인 날짜 + "권한 요청 필요"
  - 푸터의 `ECM-MISSING` 은 **번호만** 준다. 제목과 출처가 없으면 다음 사람이 "이게 뭐였는지"를 매번 다시 찾는다. 예 — `364422955 [MCAL 보증 범위 안내] — 티켓 본문 링크, 2026-11-06 404(authorized:false)`
- 링크가 잘못된 항목은 올바른 접근 방법 (검색으로 찾으라는 안내)

ECM 링크 형식: `https://ecody-ecm.autoever.com/pages/viewpage.action?pageId=<id>`

3열 표(`60`/`560`/`140`: 순서 · 할 일 · **근거 절**). **실제 작업 순서대로** 번호를 매긴다.

## §7. 첨부 파일

**올린 쪽을 구별한다.** HAE 배포본만 있으면 2열 표(`260`/`500`), 당사가 올린 자료가 섞여 있으면 3열(`260`/`120`/`380`: 파일 · **올린 쪽** · 내용)로 하고 머리에 한 줄 — "HAE 배포본 N개 + 당사가 올린 M개로 되어 있다. 당사 첨부는 질문의 근거 자료이므로 이력으로서 가치가 있다".

담을 것: 파일명·크기, 업로드·**교체 이력**(삭제+추가가 같은 이름이면 재배포), 압축 PW 전달 경로, **zip 안 `Doc` 폴더에 설정 문서가 있다는 점**, 산출물 성격(설정 파일은 참고용).

당사 첨부는 **그것이 무엇을 끌어냈는지**를 적는다 — 예: "이 Harmonize 에러 로그가 HAE 의 절차 안내를 끌어냈다", "🔴 빌드 실패 로그 — §4.3". 빌드 로그는 특히 중요하다: **실제 실패 원인이 거기 있고 §4.3 의 재료가 된다.**

## §8. 참고 링크

출처별로 묶어 글머리로. **eCoDY-IMS** (딜리버리·짝 패치 / 수평전개 사본·원본 / 릴리즈 노트 전부 / 하위작업 전부 — 하위작업에는 "모두 본문 없음" 을 붙인다) · **eCoDY-ECM** (각 문서 + 핵심 절 번호) · **사내 참고** (형제 과제 페이지. **MCU 가 다르면 "함정은 다르다"를 명시**).

IMS 링크 형식: `https://ecody-ims.autoever.com/browse/<KEY>`
