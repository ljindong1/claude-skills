# 콘텐츠 기획 규약 (조사 → 목차 승인)

파이프라인의 ①②③ 단계 — "무엇을 얼마나 깊이 담을까"를 결정하는 규약.
스타일(어떻게 쓸까)은 writing-style.md, 발행(어떻게 올릴까)은 confluence-ops.md 담당.

---

## 1. 소스 판별 (조사 여부 분기)

컨플루언스 등록 요청이라고 항상 조사가 필요한 것은 아니다. 요청의 콘텐츠 소스를 먼저 판별한다.

| 유형 | 판별 기준 | 조사 단계 |
| --- | --- | --- |
| **외부 지식 조사형** | "○○ 조사해서 / 알아봐서 / 찾아서 정리해줘" — 소스가 외부 지식 | ⭕ 수행 — §2 깊이 확인 → §3 조사 |
| **대화·자료 정리형** | "지금까지 대화 정리해서", "이 파일 내용으로" — 소스가 이미 있음 | ❌ 생략 — 바로 §4 목차 승인으로 |
| **혼합형** | "이 자료 기반으로 하되 최신 동향 보강해서" | △ 부분 — 보강 범위만 §3 적용 |

판별이 모호하면 한 번 확인한다: "기존 자료 정리인가요, 아니면 제가 조사해서 채울까요?"

## 2. 깊이 프로파일 확인 게이트 (조사형 필수)

**조사형 요청은 본격 조사 전에 반드시 깊이 프로파일을 확인한다.** 사용자의 기본 방침은 "매번 다름 → 작성 전 확인"이다. 다음 3개 중 택일을 질문:

| 프로파일 | 수준 | 목차가 되는 축 |
| --- | --- | --- |
| **A. 개념 파악용** | 전체 구조 + 핵심 개념. "이게 뭐고 왜 필요한가" | 주제의 큰 구획 단위 |
| **B. 실무 적용용** | 절차·산출물·도구까지. "우리 프로젝트에 어떻게 적용하나" | 실무 활동/워크플로우 단위 |
| **C. 심층 분석용** | 조항·요구사항 단위. "감사/심사 대응, 조항별 해석" | 규격 조항/요구사항 단위 |

**깊이가 목차 분할 기준을 결정한다.** 예: "ISO 26262 조사해서 정리해줘"

```
A. 개념 파악용  → Part 개요 중심 6~7 페이지
   (기능안전 개념 / Part 구성 / ASIL / 안전 수명주기 / HW·SW 개발 개요 / 용어)

B. 실무 적용용  → 개발 단계별 활동·산출물 중심 8~10 페이지
   (HARA 수행 / 안전 요구사항 도출 / SW 아키텍처 설계 활동 /
    단위 검증(정적·동적) / 통합 시험 / 안전 케이스 / 도구 인증(TCL) / ...)

C. 심층 분석용  → Part 4/6 요구사항 조항 단위 10~12 페이지
   (Part 6 §7 아키텍처 설계 요구사항 / §8 단위 설계·구현 / §9 단위 검증 / ...)
```

**시리즈 내 재사용**: 같은 가이드 시리즈의 후속 요청("다음 페이지도 이어서")에는 처음 확인한 프로파일을 유지한다. 시리즈(대표 페이지)가 바뀔 때만 재확인.

## 3. 조사 규약

- **2차 정리 자료 허용.** 표준 원문·공식 문서만 고집하지 않는다. 단 신뢰할 만한 출처(공식 문서, 표준화 기구, 주요 기술 블로그·문헌)를 우선한다.
- **출처는 주요한 것만 명기.** 표준 번호("ISO 26262-6:2018"), 공식 문서명 수준. 문장마다 각주를 달지 않는다.
- **재서술 원칙 ⭐**: 조사 자료를 문단 단위로 옮겨 적지 않는다. 반드시 본 스킬의 구조(개념→비유→시각화→표→결론)와 톤으로 **재구성·재서술**한다. 사내 위키라도 외부 자료 통복사는 금지.
- **최신성 중심 검색.** 안정된 주제(예: ISO 26262 개념 구조)는 기존 지식으로 충분하되, 다음은 웹 검색으로 확인한다:
  - 개정판·최신 버전 발행 여부, 폐기/대체 여부
  - 도구·생태계 지원 현황 (버전, 신규 도구)
  - 주제 자체가 신기술(최근 릴리스된 프레임워크 등)이면 조사 비중을 크게
- **모르면 모른다고 쓴다.** 확인 안 된 내용을 확정 톤으로 쓰지 않는다 (writing-style의 솔직함 원칙과 동일).

## 4. ⭐ 목차 + 페이지 범위 승인 게이트 (소스 유형 무관, 항상)

본문 페이지를 하나라도 생성하기 전에, 다음 형식으로 초안을 제시하고 **명시적 승인**을 받는다.

```
[제시 형식]

가이드명(대표 페이지 제목): ○○○
깊이 프로파일: B. 실무 적용용        ← 조사형일 때만
트리: 대표 1 + 하위 N개

| # | 하위 페이지 제목 | 다룰 범위 (1~2줄) |
| --- | --- | --- |
| 1 | ... | 이 페이지가 어디부터 어디까지 다루는지 |
| 2 | ... | ... |

이대로 진행할까요? 항목 추가/삭제/범위 조정 의견 주세요.
```

- 각 항목의 **"다룰 범위"가 핵심**이다 — 제목만으로는 기대 수준을 확인할 수 없다.
- 사용자가 조정을 요청하면 반영한 수정안을 다시 제시한다. 승인 신호("좋아", "진행", "OK")가 명확할 때만 작성 시작.
- 단일 페이지 추가(유형 4)도 축약형으로 동일 적용: 제목 + 다룰 범위 제시 → 승인 → 작성.
- 승인받은 목차는 세션 관리의 진행 기준표가 된다 (SKILL.md §4 — "N개 중 M번째").

## 5. 목차 설계 원칙 (승인안 작성 시)

- 하위 페이지 5~12개. 13개 이상이면 가이드 분리 또는 항목 통합을 제안.
- 각 하위 페이지는 자체 완결적 한 편의 글이 될 수 있는 단위로 자른다 — "반쪽짜리 개념 + 나머지는 다음 페이지" 식 분할 금지.
- 분할 축은 깊이 프로파일이 결정한다 (§2 예시 참조).
- 페이지 간 내용 중복은 최소화하되, 각 페이지 리드에서 1줄 수준의 맥락 재진술은 허용.
- 제목 명명은 page-structure.md §5 규약 (Part/장 번호 접두 금지).
