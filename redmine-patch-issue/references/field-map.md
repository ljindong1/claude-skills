# 칸별 채움 규칙

본문을 채우기 **전에** 읽는다. 이 파일이 정본이고, 스크립트가 이와 어긋나면 이 파일이 맞다.

## 0. 출처 우선순위

같은 칸을 두 소스가 채울 수 있을 때 누가 이기는지를 먼저 정해 둔다.

| 순위 | 소스 | 왜 |
| --- | --- | --- |
| 1 | **배포본 자체** — `patch_manifest.json`, `Doc/`, 배포본 arxml | 해석이 섞이지 않은 1차 자료 |
| 2 | **첨부 폴더의 로그** — 빌드 로그, Generate 로그 | 실제로 돌린 결과. 예측이 아니다 |
| 3 | **eCoDY 정리 페이지** | 1차 자료의 해석. 넓지만 한 다리 건넌다 |
| 4 | **Redmine 선례** | 양식과 필드값의 근거일 뿐. **내용의 근거는 아니다** |

**1위가 이긴다고 4위를 버리지 마라.** 어긋나면 **양쪽 값을 다 적고 어긋남으로 표시**한다.
어느 쪽이 맞는지 고르는 것은 사람의 일이다. 고르면 그 판단이 일감에 사실처럼 남는다.

4위를 내용 출처로 쓰지 않는 이유는 따로 있다. 같은 패치를 **다른 사람이 먼저 해 둔 경우**가
흔한데, 그 본문을 베끼면 그 사람이 빠뜨린 것까지 그대로 물려받는다. 실제로 짝 패치(APP)의
설정 변경만 적고 FBL 고유 6건이 빠진 일감이 있었다.

값**에서 고르고, 없는 사람·값을 넣으면 422 "목록에 포함되어 있지 않습니다" 로 거부된다.

## 3. 빈칸 처리 — 가장 중요하다

| 상황 | 처리 |
| --- | --- |
| 소스에 없다 | **빈칸 + "확인 필요"에 올린다.** 추측으로 채우지 않는다 |
| 선례에 `- 필요 시 기재` 같은 안내문이 있다 | 내용이 없으면 **그 줄을 지운다**. 남겨 두면 빈 양식이 남은 것이 된다 |
| 두 소스가 다르다 | 둘 다 적고 어긋남 표시. 고르지 않는다 |
| 사람·일정·단계 | 혼자 정하지 않는다 |
| 첨부 | **본문에는 목록만 적는다.** 파일은 `redmine.py attach` 로 따로 올린다 — 본문을 보냈으면 **묻지 않고 이어서**, 폴더는 항목별 압축 (SKILL.md S9) |
| 읽을 수단이 없어 보이는 파일 | **먼저 변환을 시도한다**(아래). 그래도 안 되면 "읽지 못했음"을 명시한다. 조용히 빠뜨리지 않는다 |

빈칸을 그럴듯하게 메우는 것이 이 업무에서 가장 비싼 실수다. 일감 본문은 다음 회차의 근거가 되고,
리뷰어와 HAE 가 그것을 사실로 읽는다. **"모른다"가 적힌 일감은 고칠 수 있지만, 틀린 값이 적힌
일감은 아무도 의심하지 않는다.**

### "읽을 수단이 없다"고 말하기 전에

포기는 마지막에 한다. 한 번 그냥 넘겼던 `.xls` 가 **Harmonize 대조표**였고, 그 안에
설정 변경 안내와 Harmonize 가 서로 반대로 작용하는 자리가 들어 있었다. 넘겼다면 일감에
그 내용이 빠진 채 남았을 것이고, 작업자는 같은 빌드 실패를 다시 만났을 것이다.

| 막힌 것 | 먼저 해 볼 것 |
| --- | --- |
| 구형 `.xls`(OLE2/BIFF) | **엑셀 COM 으로 `.xlsx` 변환** — `harvest_attach.py` 가 자동으로 한다. 엑셀이 없으면 그때 사용자에게 재저장을 부탁한다 |
| `.docx` | python-docx. 없으면 docx 는 zip+xml 이니 직접 긁는다 |
| 암호 걸린 압축 | 사용자에게 암호를 묻는다(배포본 PW 는 메일로 온다) |
| 403·404 로 막힌 eCoDY 자료 | 매번 다시 두드린다. 권한은 풀린다 |
| 그래도 안 되는 것 | 그때 "읽지 못했음 + 왜"를 적는다. 그것도 정보다 |

변환본은 **스크래치패드에 두고 넘겨받은 폴더는 건드리지 않는다.**

## 3-1. 본문에 쓰면 안 되는 문자 — 500 이 난다

레드마인이 **4바이트 문자(비 BMP, `U+10000` 이상)를 저장하지 못한다.** DB 열이 3바이트
`utf8` 이라 삽입에서 예외가 나고, 검증을 통과한 뒤 터지므로 **422 가 아니라 500** 이 온다.
500 은 어디가 문제인지 말해 주지 않아서 찾는 데 오래 걸린다.

| 쓰지 마라 (4바이트) | 대신 (3바이트, 잘 들어간다) |
| --- | --- |
| 🔴 🟡 🟢 (U+1F534 등 색 동그라미) | ⚠ (U+26A0) · ★ · ● · 또는 그냥 **굵게** |
| 🚀 📌 ✏️ 등 대부분의 그림 이모지 | ⭐ (U+2B50) · ✅ (U+2705) · ⚠ · → · ※ |

**보내기 전에 전수 검사한다.**

```python
bad = {c for c in body if ord(c) > 0xFFFF}
```

하나라도 있으면 바꾼다. 이 규칙을 어겼을 때 실제로 500 두 번을 맞고 본문을
이분 탐색해서 `⚠` 한 글자를 찾아냈다.

## 3-2. 이미 올린 본문을 고칠 때 — 줄끝이 CRLF 다

올라간 본문 일부만 고치려면 **받아서 고쳐 다시 올린다**(`update --description` 은 전체 교체다).
그때 Redmine 이 돌려주는 본문은 줄끝이 **`
`** 이다. 내 스크래치패드 파일은 `
` 이라
`
` 으로 쓴 찾을 문자열이 **하나도 안 맞는다.** 2026-11-06 에 7곳 교체가 첫 줄에서 멈췄다.

```python
s = fetched_description.replace("
", "
").replace("", "
")   # 먼저 맞춘다
...                                                                  # 그다음 교체
```

그리고 고치기 전에 **방금 받아온 본문으로** 작업한다. 전송할 때 쓴 스크래치패드 사본은
그 뒤의 수정(코멘트로 고친 것, 다른 사람이 손댄 것)을 모른다.

## 4. 근거는 본문에 남기고, 추적 주석은 미리보기에만

출처를 두 종류로 가른다. 섞으면 본문이 지저분해지거나, 반대로 다음 작업자가 근거를 못 찾는다.

### 본문에 남기는 근거 — 지운다면 손해다

이 일감은 나중에 **`swp-delivery-patch` 가 읽어 실제 작업을 한다**. 그 스킬이 "왜 이렇게
적혀 있나"를 되짚을 수 있어야 하므로, 사람과 스킬이 **다시 찾아갈 수 있는 형태**의 근거는
본문에 남긴다. 선례 #48891 도 그렇게 쓰여 있다.

| 꼴 | 예 |
| --- | --- |
| IM 절 번호 | `Dcm IM 4.1.1.28 : 설정 변경 없음, Validation 신규 19개` |
| HAE 답변 날짜 | `PFee 설정 없음 -> PMem_Driver 추가하지 않음 (10-06 HAE 답변)` |
| IMS·수평전개 키 | `근거 : MCP0806-277 [수평전개] …` |
| 커밋 해시 | `[완료 36f72d49] Build/SCons.arxml DefineOption 에 DCM_FOTA_USED_FBL 추가` |
| 배포본 판정 | `09-07 재배포본 9.80MB — 09-04 파일은 무효 (CRC 대조 84/86 동일)` |

### 미리보기에만 붙이는 추적 주석 — 전송 전에 뺀다

내가 어느 파일 몇 번째 줄에서 값을 집었는지는 **승인용**이다. 본문에 남으면 다음 작업자에게는
의미 없는 경로가 된다(그 로그 파일은 내 스크래치에만 있다).

```
### 2.1 적용 모듈
Dcm_R44    2.1.1.0_HF2 -> 2.1.1.0_HF4      ← manifest.modules[0]
### 4. 빌드·Generate 결과
Rte Validation 0 errors / 376 warnings      ← log_Rte.log:1637
Csm CsmInOutRedirection 필수 컨테이너 누락   ← log_FW.log:2410
```

출처를 못 적는 칸이 있으면 그것은 **채우지 말았어야 할 칸**이다.

## 5. 항목에 번호를 매긴다

`swp-delivery-patch` 는 S11(기록·리뷰 대응)에서 **본문의 검토 항목마다 하나씩 결론을 적는다**.
결론 없이 남은 항목은 누락으로 집계된다. 그래서 항목은 뒤에서 가리킬 수 있어야 한다.

| 절 | 번호 꼴 |
| --- | --- |
| §2.2 설정 변경 | `(1) (2) (3) …` 또는 페이지 §3.1 의 `① ② ③ …` 을 그대로 승계 |
| §2.3 IA / VC | IA 번호 그대로 (`IA-079`, `IA-086`) |
| §2.6 HAE 확인 필요 | `(가) (나) (다) …` — 질문 초안의 번호와 일치시킨다 |
| §3 검증 계획 | `V1 V2 V3 …` — 결과 코멘트에서 이 번호로 통과 여부를 적는다 |

페이지 §3.1 의 번호를 그대로 쓰는 편이 좋다. 그러면 일감 · 페이지 · IMS 질문 세 곳에서
같은 항목이 같은 번호로 불린다.
