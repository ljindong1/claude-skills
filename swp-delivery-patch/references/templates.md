# 양식

## 1. Redmine 일감 본문

**정본은 `redmine-patch-issue` 스킬이다.** 이 스킬은 일감을 새로 쓰지 않고 읽어서 작업 지시로 쓴다. 현행 양식의 구성과 이 스킬이 쓰는 칸:

| 일감 절 | 이 스킬에서 쓰는 곳 |
|---|---|
| §0 한눈에 | 이번 회차 전체 그림 — 손이 닿는 군데 수, 가장 위험한 단계 |
| §1 목적 (승급 모듈 · 받는 이유 · 결함별 해당 여부) | 판정표의 "해당 없음" 사유, 실기 고유 시험 근거 |
| §2 작업 전 준비 `P1`~ | P 사전 점검과 그대로 대응(재배포본 확인, PW, 기준 형상, 도구 환경) |
| §3 변경 지도 (파일 · 군데 · 도구/사람) | **판정표 초기 행** — "다 했나"를 세는 자리 |
| §4 작업 단계 `S1`~ | 일감 번호다. 이 스킬 단계와 뜻이 다르다(SKILL 전체 흐름 아래 주의) |
| §5 멈춰서 확인할 것 `Q1`~ | C·B 경로 후보. 질문 초안과 리뷰 회신에서 번호마다 결론을 적는다 |
| §6 Generate 후 Validation | 정적 검수의 신규 Validation 사전 점검 대상 |
| §7 검증 `V1`~ · `X1` | 실기 케이스와 "돌리지 않을 것" 근거 |
| §8 완료 기준 | 결과 코멘트에서 닫을 체크박스 |
| §9 범위가 아닌 것 | 판정표 제외·보류 사유의 출처 |
| §10 참고 · 10.5 못 본 자료 | 근거 문서 링크, 권한 없는 자료(보고에 "미확인"으로 남길 것) |
| 본문의 `[기입]` (§0 마지막 줄 · `P9` 작업 브랜치 · `S10` 빌드 대상) | **이 스킬이 채운다** — 값은 gitea-jenkins-setup·사용자 확인에서 오고, 프로필을 먼저 갱신한 뒤 일감을 수정한다 |

본문을 고쳐야 하면 redmine-issue 스킬의 미리보기 → 승인 규칙으로 한다.

## 2. Redmine 코멘트 — 패치 작업 결과 (작업 전체가 끝난 뒤)

작업 **중**의 기록은 다르다 — 단계 완료는 본문 체크, 오류·확인 필요만 코멘트다(`issue-report.md`). 아래는 전체를 마친 뒤 한 번 올리는 최종 코멘트 양식이다.

등록 전 **원문 전체**를 사용자에게 보여 준다.

```
# <APP|FBL> V<x> 패치 작업 — HAE 요청사항과 <차종> 처리 결과

## 1. HAE 패치 요청 (eCoDY-IMS <키>)
- 배경 : <수평전개 키> — <결함 요약 1~2줄>, <차종> 적용 사유
- 배포 파일 : <유효본>, (재배포 시) 이전본 미사용 근거 — CRC 대조 결과
- 설정변경 안내 (<날짜> 개정) : 항목 나열, harmonize <모듈>

## 2. 요청별 처리 결과

| HAE 요청 | <차종> 이전 상태 | 처리 (파일) | 확인 근거 |
|---|---|---|---|
| ... | ... | ... | ... |

적용 제외 (사유)
- ...

기타
- 산출물명, ReleaseNote / ModuleList

## 3. 빌드 결과
- 커밋 <해시> → Jenkins <Job> #<n> <결과> (Auto commit <해시>)
- Generate : 생성기 Error 0 (Warning n, 직전 #m 은 k), 신규 Validation 에러 없음
- Rte Validation : … — #m 과 동일, SAFERTE_ERR 0
- 산출물 : <이름>
- 메모리 (map 섹션 합계, 직전 대비)
  ```
  RAM  a -> b Byte (+c)  원인 섹션
  ROM  a -> b Byte (+c)  원인 섹션
  ```

## 4. 남은 작업
- 실기 검증 …, ALL 빌드, PR, (FBL/APP 짝) 별도 진행
- 상세 분석 : <Confluence URL>
```

표 작성 수준: 열 4개, 칸마다 한 줄. XML 경로 전체·모듈 소스 파일 목록은 넣지 않고 커밋 해시로 대신한다.

다른 코멘트(실기 확인, H-OTA 결과)는 조건(코드블록) → 결과 표 → 판정 → 결과 파일 위치 순으로 쓴다.

## 2-1. 리뷰어 지적 대응과 회신

리뷰어(예: 플랫폼설계팀)가 Redmine 코멘트로 누락·수정 요청을 주면:

1. **항목 목록** — 코멘트를 번호별 항목으로 나눈다. 링크(다른 일감 note)와 첨부 캡처를 따라가 무엇을 하라는지 확정한다. 캡처는 사용자에게 받아 본다(이 스킬은 Redmine 첨부를 받지 않는다).
2. **항목마다 확인** — 현재 저장소 값(파일·행), 그 값이 들어온 커밋·일감, HAE 회차 이력(원칙 8), APP/FBL 중 대상. 질문형("기존에도 False 였나?")은 두 시점 값을 함께 본다(communication §4).
3. **처리 방향은 사용자가 정한다** — 바꿀지, 유지할지, 바꾸고 시험할지. 분석("바꾸면 실패할 것")은 결론이 아니라 근거로 보인다.
4. **처리·빌드** — 일반 절차(적용 → 정적 검수 → 빌드).
5. **회신** — 사용자가 "다 처리한 뒤 한 번에"를 원하면 그때까지 쓰지 않는다. 회신 전에 원문 요청과 항목별로 대조한다(communication §5-6).

회신 양식 (단답형, 지적 번호 그대로):
```
@<리뷰어> note-<n> 반영 결과입니다.

1. <항목> : <처리 결과 한 줄> (<근거 커밋·일감, 필요할 때만>)
2. <항목> : 변경 없음 — <사유 한 줄>
3. <항목> : 현재 <값>, <요청한 변경> 후 평가 진행 예정
   - 문의 : <예/아니오로 답할 질문>
...

빌드 : <Job> #<n> <결과> (RAM ±a, ROM ±b Byte), 실기 <완료 / 확인 예정>
```
- "유지"로 답할 때는 사유를 붙이고, 요청이 "변경 후 테스트"였다면 하지 않았다는 것과 다음 계획을 쓴다.
- 상세 근거는 사용자가 원할 때만 붙인다. 긴 결과 보고는 §2 양식으로 따로 쓴다.
- 등록은 redmine-issue 스킬의 미리보기 → 승인으로(내가 등록한 일감일 때만 가능).

## 3. IMS 질문 댓글

판단 경로 C 항목만 한 댓글에 모은다. 담당자 멘션·인사·맺음말은 쓰지 않는다(배정은 HAE 가 한다). 한 줄 서두 뒤 바로 번호 매긴 본론. Jira wiki 문법(`*굵게*`, `||머리||`, `#`/`##` 번호, `-`/`--` 글머리)으로 쓰면 그대로 붙여 넣어도 표·목록이 된다.

```
<FBL|APP> V<x> 패치 적용 중 아래 <N>건 확인 부탁드립니다.

*1. [<IA번호·모듈>] <항목 이름>*
- 차이: <MCP08xx-xxx 패치 파일(첨부명, 날짜) 안 경로> 에는 <항목> 이 들어 있는데, 당사 <차종> <경로> 에는 없습니다.   ← 비교 질문이면 이 줄을 먼저
- 대상: <파일 / 컨테이너(C Studio 경로) / 행>
- 당사 현황: <현재 설정·구성 (표 가능)>
- HAE 안내 / 배포본: <안내 문구·참고 설정 값·IM 절, 날짜>
- 당사 적용안: <잠정 처리와 이유>
- 문의
## <예/아니오 또는 선택지로 답할 수 있는 질문>
## ...

*2. ...*
```

예 (MCP0806-279, 2026-10-08 등록본을 `communication.md` 이름 규칙에 맞게 고쳐 쓴 것):
```
FBL V3.0.19 패치 적용 중 아래 4건 확인 부탁드립니다.

*3. [Com] FBL Com 모듈 제거*
- 차이: MCP0806-279 패치 파일(SP3I_PSU_3.0.19_FBL, 09-07) 안 Build/SCons.arxml 에는 ExcludeList Com_R44 가 들어 있는데, 당사 HE1i psu_fbl/Build/SCons.arxml 에는 없습니다. 같은 패치 파일에서 EcuM Com_Init, BswM AC_UserCallout_Com_DeInit, PduR PduRBswModules_Com, Rte BswInstance_Com 도 빠져 있습니다.
- HAE 안내: 설정변경 안내 표(09-07)에는 해당 항목이 없습니다.
- 당사 적용안: 안내 표에 없어 현재는 미적용(기존 유지)입니다.
- 문의
## 필수 적용 항목입니까, 선택 사항입니까?
```
(이 항목은 10-12 리뷰어 지적 "Com is not used in FBL Platform" 으로 적용했다 — 프로필 고유 판단 이력.)

### 수평전개 회신 표

수평전개(CPINFO) 티켓에 적용·미적용을 회신할 때. 미회신이면 HAE 가 독촉한다.

```
|| 구분 || 차종 (양산 차종 포함) || 미적용 시 현상 (제어기) || 미적용 시 현상 (실차) || 미적용 사유 || 수평전개 적용 ||
| <SWP 계열> | <차종 나열> | <현상> | <현상> | <없으면 N/A> | <적용 / 미적용 / 패치 티켓 키> |
```

## 4. 패치 커밋 메시지

```
[<제어기>][<차종>] SWP 모듈 패치 적용 (<APP|FBL> : V<x>)

#<일감> [R44][<차종>/<제어기>][...] Delivery_Patch (#<원일감> / <IMS키>)

- <모듈> <old> -> <new> (<근거>, <배포본> 폴더 교체)
- <파일> : <변경 요약>
- <파일> : <변경 요약> (<적용 제외 항목과 사유>)
- 산출물명 <이름>, ReleaseNote / ModuleList v<x> 추가
- 참조 : <배포본, 이전본 미사용 여부>
```
제목을 Hook 동작 단어(Rebuild 등) 하나로 쓰지 않는다. 커밋 꼬리말은 세션 규칙을 따른다.

## 5. Confluence 일감 페이지 골격

confluence-writing 규약(H3 시작, html + data-colwidth 표)으로:

```
요약 문단 (무엇을, 어디까지 했는지)
■ 일감 개요 (표)
■ 패치의 출발점 — 수평전개 (결함 표, 차종 적용 의미)
■ eCoDY-IMS 경과 (날짜 코드블록, 재배포·개정 표시)
■ FBL / APP 항목별 현황 (판정표)
■ eCoDY-ECM 가이드 확인 결과
■ 적용 순서 (FBL/APP 조합)
■ 검증 계획 / 실기 결과
■ HAE 확인 필요
■ 남은 조치 (주체 / 할 일 / 상태)
■ 참고
📌 이 문서의 범위 (근거 자료와 기준 시점)
```
