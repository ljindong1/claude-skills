# 일감 반영 — 단계 체크 · 오류 · 확인 필요

**들어가기 전** — 일감 번호와 그 일감의 단계 목록이 손에 있어야 한다. 일감이 없으면 반영할 곳이 없으니 요청 항목 목록으로 대신하고 그 사실을 보고한다.
**끝났다고 말하려면** — 끝낸 단계마다 본문 체크가 닫혀 있고, 멈춘 자리마다 코멘트가 있어야 한다. 체크가 열린 채 "끝났다"고 말하지 않는다.

## 1. 무엇을 어디에

**성공한 것은 본문에, 막힌 것은 코멘트에.** 잘된 일로 코멘트를 늘리지 않는다 — 일감을 열었을 때 코멘트에 있는 것은 전부 사람이 볼 일이어야 한다.

| 쓸 것 | 어디에 | 언제 |
|---|---|---|
| 단계 완료 | **본문** — 단계 머리의 `☐` → `☑`, 바로 아래 결과 한 줄 | 그 단계의 **단계 완료 조건**을 모두 충족한 직후 |
| 완료 기준 | **본문 완료 기준 절**의 `- ☐` → `- ☑` | 그 항목이 닫힐 때 |
| 진행률 | 일감 필드 `done_ratio` — ⚠ **먼저 쓸 수 있는지 본다** | 단계 완료마다 (끝낸 단계 ÷ 전체 단계) |
| **오류·막힘** | **코멘트** | 생긴 즉시. 다음 단계로 넘어가지 않는다 |
| **확인 필요**(사람이 정할 것) | **코멘트** | 발견 즉시 |
| 최종 결과 | **코멘트 하나** (양식 `templates.md` §2) | 작업 전체가 끝난 뒤 |

⚠ **`done_ratio` 가 읽기 전용인 Redmine 이 있다.** 관리 설정이 `Calculate the issue done ratio with: Use the issue status` 면 진척률은 **상태에서 계산**되고 `done_ratio` 를 보내도 **오류 없이 무시된다**(미리보기는 `0% → 85` 로 찍고, 전송 뒤에도 `0%`). 사내 ccm Redmine 이 이 설정이다 — 2026-11-10 확인, 같은 등록자의 일감 9건이 신규 0% / 해결 90% / 완료 100% 로 전부 1:1 대응. **쓰기 전에 같은 프로젝트 일감 몇 건의 (상태, 진척률) 분포를 보고** 1:1 이면 진척률 대신 **상태 전이**가 유일한 수단이다. 상태 전이는 사용자 확인 사항이므로(§5) 진척률을 올려 달라는 요청은 "상태를 바꿔야 올라갑니다" 로 되돌려 묻는다.

성공한 단계에는 코멘트를 달지 않는다. 그 단계의 상세(완료 조건 항목별 대조, 확인한 근거)는 **대화로 보고**하고, 일감에는 아래 한 줄만 남긴다.

**본문은 지시서다.** 바꾸는 것은 체크 표시와 결과 한 줄뿐이고, 할 일·함정·완료 조건·근거 문장은 고치지 않는다. 구조를 바꿀 일이 생기면 `redmine-patch-issue` 로 넘긴다.

본문 수정은 **본인이 등록한 일감에서만** 된다(redmine-issue 제약). 작성자가 다른 사람이면 본문은 손대지 않고, 단계 완료를 코멘트 한 줄로 적고 그 사실을 보고한다.

## 2. 단계 완료 — 판단과 본문 한 줄

판단 기준은 스킬이 아니라 **일감이** 정한다. 그 단계의 "단계 완료 조건" 문장을 항목마다 충족/미충족으로 대조한다. 하나라도 미충족이면 완료가 아니다 — 본문은 `☐` 로 두고 결과 줄에 어디까지 했는지 적는다.

결과 한 줄은 단계 머리 바로 아래에 둔다. **근거가 들어가야 한다** — 코멘트를 안 쓰므로 이 한 줄이 유일한 기록이다.

```
#### ☑ S1. 배포본 확보·대조
→ 결과 2026-11-09: 11-03 재배포본 기준(09-04 본과 CRC 2건 차이), PW 해제, Doc 위치 확인

#### ☑ S8. harmonize
→ 결과 2026-11-09: 에러 없이 완료, 되돌림 점검 ①②③ 끝(재삭제 2건·복구 1건, ECUC Compare 전수 대조), 커밋 a1b2c3d

#### ☐ S9. Generate·Validation
→ 진행 2026-11-09: ERR053310 2건 해결, 053311 1건 미해결 → 코멘트 [확인 필요] 참조
```

- 근거는 재현 가능한 것만 — 파일·행, 커밋 해시, 빌드 번호, 로그의 숫자. "확인했다"만 쓰지 않는다(기본 원칙 5·6, `communication.md`).
- 이전 회차와 달라진 값이 있으면 그 사실도 한 줄에 넣는다(기본 원칙 8).
- 두 줄 이상이 되면 그 단계는 완료가 아닌 경우가 많다 — 미충족 항목을 코멘트로 올린다.

## 3. 오류·막힘 — 즉시, 그 자리에서 멈춘다

```
## [오류] S<n> — <한 줄 증상>

**어디서** — <명령 / 단계 / 파일>
**증상** — <로그 원문 한두 줄>
**지금까지 확인한 것** — <사실만>
**원인 추정** — <추정이면 추정이라고 쓴다>
**멈춘 자리** — <무엇이 이미 적용된 상태인지. 되돌렸으면 되돌렸다고>
**필요한 것** — <사람이 정해야 할 것 / 받아야 할 자료>
```

- **고치기 전에 원인 분석을 먼저 보인다.** 로그의 첫 에러부터 따라가고 추정으로 고치지 않는다.
- 도구가 중간에 실패했으면 **무엇이 이미 적용됐는지**를 반드시 적는다 — "실패"는 "변경 없음"이 아니다(`apply.md` §2).
- 되돌렸으면 되돌린 방법(커밋·`git checkout` 대상)까지 적는다.
- 해결되면 그 코멘트에 답글로 결론 한 줄을 적고, 해당 단계 본문 체크를 닫는다.

## 4. 확인 필요 — 선택지를 주고 기다린다

```
## [확인 필요] <항목>  (일감 `Q<n>` 해당 / 신규)

**무엇이 걸렸나** — <사실>
**선택지**
1. <안> — 근거 / 위험
2. <안> — 근거 / 위험
**권고** — <어느 쪽, 왜>
**기다리는 답** — <질문 한 문장>
**그동안의 처리** — <잠정값(보수적) 또는 보류>
```

여기로 오는 것:

- 보호 설정이 바뀜 — "동작 차이 없음"이어도 확인을 받는다(기본 원칙 7, `protected-settings.md`)
- 판단 경로 **C**(HAE 질문) · **D**(회사 기준 보류) 항목 (`decision-rules.md` §0)
- 일감의 `Q` 항목 — **이미 번호가 있으면 그 번호를 쓴다.** 새로 생긴 것은 다음 번호를 붙이고 일감 질문 절에 한 줄 추가를 제안한다
- 자료끼리 어긋남(안내 ↔ 배포본 ↔ 이전 회차 보정 ↔ HAE 답변) — 어느 하나를 자동으로 우선하지 않는다
- 과거 회차 되돌림 의심 (`three-way-merge.md` §4.8)

답을 받으면 **질문 번호마다** 결론을 적어 닫는다. 빠진 번호는 다시 묻는다. HAE 에 물을 것이면 IMS 질문으로 옮긴다(`ims-workflow.md` §2).

## 5. 승인과 금지

- 코멘트·본문 수정은 **등록될 원문 전체를 보여 주고 승인받은 뒤에만** 등록한다(기본 원칙 4). 요약을 보여 주고 등록하지 않는다.
- **성공으로 코멘트를 달지 않는다.** 단계 완료는 본문 체크와 결과 한 줄로 끝낸다.
- 여러 단계를 한꺼번에 끝냈으면 본문 수정은 한 번에 모아서 한다(체크 여러 개 + 결과 줄 여러 개, 수정 1회).
- 이미 올린 코멘트는 **내가 쓴 것만** 수정한다. 잘못 쓴 내용은 지우지 말고 다음 코멘트에서 정정한다.
- 상태 전이(신규 → 진행 → 해결)와 담당자 변경은 사용자 확인 후. 규칙은 프로필.
