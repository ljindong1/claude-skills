# 사용자·HAE·사내 담당자에게 말하는 규칙

이 업무에서 생긴 재작업은 상당수가 기술 오류가 아니라 **말을 잘못 해서** 생겼다. 대표적인 경우는 네 가지다. 확인하지 않은 말을 사실처럼 함, 어느 파일·어느 차종인지 흐린 표현, 비교 방향이 거꾸로 읽히는 문장, 엉뚱한 기준 시점으로 설명함. 사용자에게 하는 답변, Redmine 코멘트, IMS 질문, 슬랙 답글에 모두 적용한다.

## 1. 확인한 것만 말한다

- 다른 차종·다른 저장소·HAE 파일의 상태는 **그 파일을 직접 열어 본 뒤에만** 말한다. 말할 때 파일 경로(또는 티켓·첨부·압축 안 경로)와 행을 같이 적는다.
- 열어 보지 않았으면 "확인하지 않았다"고 쓴다. "~일 것이다", "~때문에 들어 있다" 같은 이유 붙이기도 확인 전에는 하지 않는다.
- 추정이 꼭 필요하면 문장 앞에 **(추정)** 을 붙이고, 확인한 사실과 같은 표·같은 문장에 섞지 않는다.
- 사례 (2026-10-12): MCP0806-280 패치 파일의 Ecud_EcuM 을 열어 보지 않고 "SP3i(HAE 파일)는 EcuM 에서 CDD_Router 를 초기화한다"고 두 번 말했다. 그리고 이것을 IMS 질문의 전제로 넣었다. 실제로는 패치 파일에도, 당사 SP3i 에도 CDD_Router 초기화가 없었다.

## 2. 이름을 고정해서 쓴다

| 가리키는 것 | 이렇게 쓴다 | 쓰지 않는다 |
|---|---|---|
| HAE 가 IMS 티켓에 첨부한 배포 파일 | **"MCP0806-280 패치 파일(SP3I_PSU_3.0.29_APP, 10-06) 안 `<압축 안 경로>`"** | 참고 형상, 배포 참고 파일, HAE 형상, 참고 SCons |
| 당사 저장소의 파일 | **"당사 `<차종>` `<저장소/경로>`"** (예: 당사 HE1i `psu_app/Build/SCons.arxml`) | 우리 쪽, Ours |
| 당사 차종 | **SP3i·HE1i·BJ1·NQ6·SX3e 는 모두 당사 차종**이다. 저장소·브랜치를 함께 적는다 (예: SP3i PSU = psu_master `develop`, HE1i = `develop_he1i` 계열) | "SP3i(HAE 파일)" 처럼 차종을 HAE 것으로 쓰기 |
| 다른 담당자 작업 | **"유수진 책임 APSU v3.0.27 (`refs/ref-sjyoo/v3.0.27_sjyoo`, `apsu_app/...`)"** 처럼 사람·저장소·시점을 함께 | 다른 차종, 그쪽 |
| HAE 가이드 | **"[IM] Dcm - R44 (pageId 371179712) 2.1.1.2 SCons.arxml"** | IM 표준, 가이드 |

`Prev / Cur / Ours`, `참고 형상` 은 스크립트 내부 용어다. 사람에게 보내는 글에는 위 표의 이름으로 바꿔 쓴다.

## 3. 비교는 "A 에는 있고 B 에는 없다" 한 문장으로 먼저 말한다

- 첫 문장: **"<A 파일> 에는 <항목> 이 들어 있는데, <B 파일> 에는 없습니다."**
- 세 번째 기준(IM 등)은 그다음 문장에 따로 붙인다. 한 문장에 세 곳을 섞지 않는다.
- 금지 예: "패치 참고 SCons.arxml 의 일부 생성기 InputFilesList 에 IM 표준에 없는 항목이 있습니다." 사용자와 HAE 담당자 모두 "당사가 IM 항목을 누락했다"로 거꾸로 읽었고, HAE 가 "누락 근거가 어디 있냐"고 되물었다.
- 표로 비교할 때는 열 제목을 파일 이름으로 쓴다. 칸마다 "있음/없음"과 행 번호를 적는다.

## 4. 이력 — 두 종류를 구분해서 말한다

| 종류 | 언제 | 기준 시점 | 형식 |
|---|---|---|---|
| **당사 저장소 이력** | "원래부터?", "기존에도?" 같은 질문에 답할 때 | **사용자의 작업 브랜치 분기점**(프로필). 그 전의 이력(develop 생성 시점 등)은 "(참고)" 한 줄로만 | "패치 전에도 False 였습니다. (참고) #45070(2026-08-05)에서 설정" |
| **HAE 회차 이력** | 이전 대비 변경이 있는 **모든** 항목 (기본 원칙 8) | 이전 회차 배포본·보정본·HAE 답변, 당사 반영 커밋 | "3.0.18 08-31 보정본은 EcuM ListTwo, 3.0.19 배포본은 BswM — 이번 배포본이 보정 이전 값입니다." |

- HAE 회차 이력은 생략하지 않는다. 찾지 않았으면 "이력 미확인"이라고 쓴다. 절차는 `three-way-merge.md` §4.8.
- 이번 배포본이 이전 보정을 되돌린 경우(되돌림 의심)는 보고 맨 앞에 따로 둔다.
- "기존에"가 어느 시점인지 상대가 밝히지 않았으면 두 시점의 값을 함께 적는다(예: "이번 패치 전: False / #45070 이전: True").

## 5. 보내기 전 점검 (IMS·Redmine·슬랙 공통)

보내기 전에 초안을 다음 질문으로 한 번씩 읽는다.

1. 모든 사실 문장에 파일·행·페이지 근거가 있는가? 근거 없는 문장은 지우거나 **(추정)** 표시를 했는가?
2. 파일·차종 이름이 2절 표대로인가? "참고 형상", "HAE 형상", "SP3i(HAE)" 같은 말이 남아 있지 않은가?
3. 비교 문장이 "A 에는 있고 B 에는 없다" 순서인가? 읽는 사람이 "당사가 빠뜨렸다"로 오해할 여지는 없는가?
4. 질문이라면 받는 사람이 **예/아니오나 선택지로 답할 수 있는가?** 질문의 전제(당사 구성 설명)를 파일로 확인했는가?
5. 이력이라면 4절의 어느 종류인지 밝혔는가? 변경 항목에 HAE 회차 이력(또는 "이력 미확인")이 붙어 있는가?
6. 상대의 원문 요청(예: "변경 후 테스트 부탁")과 답이 맞는가? 하지 않은 일을 "유지" 같은 말로 덮지 않았는가?

하나라도 걸리면 고친 뒤 사용자에게 보여 준다.

## 6. 단계 보고 형식 (사용자에게)

단계를 마칠 때마다 짧게:

```
[S6 3-way 판정] 대상 6파일 · 요청 9항목
  되돌림 의심 1: Ecud_EcuM PMem_Driver — 3.0.18 08-31 보정본 EcuM / 3.0.19 배포본 BswM
  복사 가능 4 / 기존 충족 2 / 당사 전용 충돌 1 / 제외 2
  충돌: Ecud_EcuM ListTwo Index — 당사 3단 vs HAE 4단(PMem_Driver), 제안 …
  확인 못 함: IA-092 IM 링크 권한 없음, 이력 미확인 1
  다음: 충돌 1건 확인 → 확정되면 S8
```

- 변경 항목은 "이번 값 / 이전 회차 값(회차·티켓·댓글 날짜) / 당사 커밋·일감"을 함께 쓴다(4절).
- 사용자가 짧게 달라고 하면 번호별 단답으로 줄인다. 근거는 물어보면 그때 붙인다.
- 리뷰어 회신·Redmine 등록본은 `templates.md` 양식, 이 절은 사용자와의 대화용이다.
